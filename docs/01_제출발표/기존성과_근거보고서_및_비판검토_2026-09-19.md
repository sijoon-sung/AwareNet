# AwareNet 기존 구현·KOREN 실측 성과 보고서 및 비판적 검토

작성일: 2026-09-19 · 기준: `awarenet` 브랜치의 기존 구현과 보관 실험 자료

**검토 목적:** 넷챌린지 제출·발표에 사용할 수 있도록 기존 성과를 재구성하고, 증거가 지지하는 주장과 추가 검증이 필요한 주장을 구분한다. 이번에 새로 추가한 SuperSFL 계획기와 OS-Ken 코드는 기존 실측 성과에 포함하지 않는다. 원격 재실험 없이 코드, 조건 원장, 원자료 및 공개 결과 페이지를 대조했다.

## 요약

AwareNet은 기기별 연산 성능과 네트워크 상태가 다른 분할 연합학습 환경에서, 엣지 접속 경로·다중 경로 전송·모델 폭을 라운드별로 조정하는 시스템이다. 모델 폭은 FjORD의 Ordered Dropout과 중첩 부분모델 개념에 기반한다. 네트워크를 활용해 전송 병목을 완화하고, 필요한 경우 기기의 모델 폭을 줄이는 방식으로 동기식 학습의 라운드 완료 시간을 낮추고자 했다.

기존 구현에는 계측, 경로·폭 계획, 출구별 종점 변경, 양방향 조각 전송과 재조립, 폭별 학습·집계가 연결되어 있다. HPC와 KOREN VM을 연결한 시험 환경에서 회선 성능을 먼저 측정하고, 이를 바탕으로 tc 상한과 교란 조건을 정했다. 보관된 32개 논리 클라이언트의 네 시나리오 로그를 재계산한 결과, 기존 기준선 대비 평균 라운드 시간이 약 25~43% 감소했다. 별도로 8개 클라이언트의 결합 실험, 장기 λ 실험, 클라이언트를 KOREN VM에 배치한 실험이 존재한다.

이 결과가 직접 지지하는 것은 **설정한 시험 환경에서 네트워크·폭 결합 제어로 라운드 시간을 줄였다는 주장**이다. 동일 정확도까지의 학습 시간 단축, 실제 OpenFlow 기반 제어의 완성, 물리 장비 32대 배포, 임의의 망에서의 권한 문제 해결까지 입증한 것은 아니다. 넷챌린지에서는 현재의 강점인 실제 연구망 활용과 측정→진단→제어→재측정 과정을 전면에 두고, 학습 품질과 배포 범위의 한계를 명확히 설명하는 편이 설득력 있다.

## 1. 넷챌린지의 취지와 과제의 위치

2026년 공고의 행사명은 **K-디지털 챌린지: 넷 챌린지 캠프 시즌13**이다. 과학기술정보통신부가 주최하고 한국지능정보사회진흥원과 KOREN 연구협력포럼이 주관한다. 대학 공지에 게시된 모집 안내에서 AI·네트워크 응용분야 아이디어 공모임을 확인했다. [시즌13 모집 안내: 계명대학교 게시본](https://gmeng.kmu.ac.kr/gmeng/5337/subview.do?enc=Zm5jdDF8QEB8JTJGYmJzJTJGZ21lbmclMkYyNjglMkYyMzI4NDQlMkZhcnRjbFZpZXcuZG8lM0Y%3D)

KOREN 망을 활용한 네트워크·서비스 아이디어 개발과 구현 지원이라는 공모 방향도 확인된다. AwareNet은 분산 AI 학습의 통신 병목에 대응하는 네트워크 응용 시스템으로 이 방향과 연결된다. 이는 공고를 바탕으로 한 본 보고서의 적합성 판단이며, 공식 심사 결과나 수상 가능성 평가가 아니다. [시즌13 공고 재게시](https://linkareer.com/activity/324608)

저장소의 `심사표_대응전략.md`에는 개발과정 30·개발구현 30·KOREN 활용도 20·기대효과 20이라는 중간평가 배점이 있다. 그러나 이번 외부 확인에서 올해 **최종평가 원본 심사표**를 확보하지 못했다. 이 배점을 올해 최종평가 기준으로 확정하거나 예상 점수를 산정하지 않는다. 해당 내부 문서에는 이전 100노드 배분 시스템의 성과도 포함되므로 현재 폭·경로 시스템의 실적으로 합산해서는 안 된다.

## 2. 해결하려던 문제와 설계 근거

동기식 분할 연합학습에서는 가장 늦게 끝나는 참여자가 라운드 시간을 결정한다. 느린 이유는 연산 성능 부족, 제한된 접속 회선, 특정 엣지로의 트래픽 집중 등으로 나뉜다. 모든 지연에 폭 축소로 대응하면 전송 경로를 바꿔 해결할 수 있는 경우에도 모델 용량을 줄이게 된다.

AwareNet의 문제 설정은 이 차이를 구분하고 사용 가능한 제어를 결합한다는 데 있다.

1. 특정 엣지가 혼잡하면 여유 있는 종점으로 접속 경로를 옮긴다.
2. 복수 출구가 있으면 같은 activation/gradient를 조각으로 나누어 전송한다.
3. 연산 병목이 남으면 해당 클라이언트의 모델 폭을 조절한다.
4. 다음 라운드의 관측을 통해 결정을 갱신한다.

FjORD는 Ordered Dropout을 이용해 중첩된 폭의 부분모델을 학습하는 근거를 제공한다. 다만 현재 저장소의 FjORD 기준선은 지식 증류를 제외하고 라운드별 폭 표집을 사용한다. 원 논문의 학습 절차와 동일한 재현이라고 보거나, 원 논문의 정확도를 현재 SFL 구현에 대입할 수는 없다. [FjORD 원문](https://arxiv.org/abs/2102.13451), [로컬 구현과 차이 명세](../../sfl/baselines/baseline_fjord.py)

## 3. 구현 범위와 실행 구조

```text
계측(Sensor)
  → 경로·폭 계획(plan / WidthPath)
  → 라운드 지시(RSTART: 폭·출구 종점·분할 비율)
  → 클라이언트 모델 및 데이터 연결 설정
  → activation 조각 전송 → 서버 재조립·연산
  → gradient 조각 전송 → 클라이언트 재조립·역전파
  → 모델 집계와 다음 라운드 관측
```

| 요청 범위 | 기존 구현과 근거 | 현재까지의 판정 |
|---|---|---|
| 엣지 변경 | `policies.py` → `endpoints_for` → `fed_client._set_dp` | 종점 변경·재접속 구현. 현재 실회선 주 경로는 SSH 역터널·tc이며 OpenFlow 적용 실증과 구분 |
| 다중 분할 경로 전송 | `mpsend.py`의 지속 TCP 연결, 출구별 가중 배정, 양방향 전송 | 학습 코드에 연결되어 있음. 독립 물리 경로와 장애 복구 보장은 별도 검증 필요 |
| 전송 후 결합 | `chunker.py`의 tid/seq/off 기반 재조립, 완료 ACK | 정상 조각의 순서 변경·중복 처리 시험 통과. 잘못된 범위의 무결성 검사 결함 존재 |
| 폭 제어 | `models.py`, `Aggregator`, `plan.width_stage/opt_widths` | 폭별 모델·슬라이스·집계·라운드 지시 구현. 정확도 정합성 검증이 남음 |
| 유동적 결합 | 계측→계획→종점·분할 비율 적용→재측정 | 실제 폐루프 구현. CPU 상태 변화와 적용 실패 처리는 보완 필요 |

여기서 엣지는 데이터 경유 종점을 뜻하는 경우가 많다. 엣지 종점 변경을 서버 연산·모델 상태의 물리 엣지 간 이동이라고 표현하지 않는다. 모델 폭 조절, 모델의 클라이언트/서버 분할점 변경, 전송 바이트 조각화, 마이크로배치 연산 분할도 서로 다른 기능이다. 기존 실험에서는 분할점 cut이 고정되어 있다.

## 4. KOREN 시험 환경과 축소 실험

### 4.1 실제 사용한 자원

실회선 리그는 HPC의 클라이언트 프로세스 및 GPU 서버와 KOREN VM 두 대를 연결한다. VM별 역방향 SSH 터널 두 개로 논리 엣지 네 개를 만들고, HPC와 VM의 tc로 접속·엣지 용량을 제한한다. 데이터는 실제 KOREN 연결 구간을 경유한다. 별도 VMCLI 실행에서는 VM 두 대에 클라이언트 프로세스 네 개씩을 두고 서버만 HPC에 둔다. [실회선 배치 문서](../04_설계기록/설계_실회선_리그.md), [리그 스크립트](../../sfl/net/real_rig.sh)

따라서 보고서에서는 **물리 VM 수, 논리 엣지 수, 논리 학습 참여자 수**를 각각 써야 한다. 이 환경은 실제 망을 사용하는 제어된 실험 환경이며, 논리 클라이언트 수만큼 독립된 물리 기기를 배포했다는 의미는 아니다.

### 4.2 회선을 먼저 측정한 이유

9월 7일 실측 기록에는 HPC↔VM1 RTT 약 3.9ms, HPC→VM1 단일 흐름 453Mbps와 8흐름 2163Mbps, VM2→HPC 단일 흐름 310Mbps와 8흐름 275Mbps가 남아 있다. 방향과 VM에 따른 차이가 있어 한 개의 명목 대역폭으로 전체 경로를 설명하기 어렵다. iperf 원파일은 현재 확인되지 않으며, 최종 결과 페이지도 미보존 사실을 명시한다. 이 수치는 보관 문서의 기록으로 인용한다. [HPC–VM 실측 기록](../02_실험/실측_HPC_VM_연결.md)

이후 학습 없이 전송 패턴만 실행하며 참여자 수를 늘린 규모 측정 원자료가 남아 있다. `line_raw_run1.jsonl`, `line_scale.jsonl`, `line_scale_detail/`는 처리량 저하와 전송 시간 분포를 조사한 근거다. 단, 코드의 `aggregate_mbps`는 총바이트/공통 관측시간이 아니라 **참여자 수×기기별 속도 중앙값**이다. 이를 엄밀한 합산 goodput이나 KOREN 백본의 물리 최대용량으로 인용하지 않는다. [측정 코드](../../scripts/measurement/line_scale.py)

### 4.3 SHRiNK와 규모 해석

사용자는 OOM·CPU 제약 때문에 축소 실험을 수행했다고 설명했다. 기존 부하비율 문서에도 실측 환경을 4~8대 리그로 축소하고 부하 비율을 보존한다는 설계가 있다. 이 접근 자체는 현실적인 실험 설계다. [부하비율 설계](../04_설계기록/설계_KOREN_부하비율.md)

다만 현재 최종 페이지와 원자료는 다음 실행을 구분한다.

| 실행 계열 | 기록된 규모·조건 | 구분해야 할 점 |
|---|---|---|
| scen32 | 논리 클라이언트 32, 24R, 3시드, 출구 5/2Mbps, 엣지 56Mbps×4 | 50/20을 0.1배로 줄인 대역폭 축소. 물리 장비 32대라는 뜻은 아님 |
| r8mix 결합 | 클라이언트 8, 느린 2·접속 제한 2·정상 4, 목표 10초 | 기능을 따로·같이 사용하는 결합 비교 |
| r8mix_acc | 8개 클라이언트, 200R, 2시드 | λ 변화에 따른 시간·평균 폭 비교 |
| vmcli | VM 두 대에 총 8개 클라이언트, 1시드 | 실제 원격 CPU 배치의 영향 확인 |

현재 확인한 자료만으로 scen32를 8개 클라이언트로 치환한 동일 실행이라고 확정하지 않는다. 최종 페이지에는 scen32의 인위 지연이 없고 교란은 특정 라운드에 엣지 용량을 변경하는 것으로 기재되어 있다. 따라서 모든 실험에 무작위 노이즈가 주입됐다고 쓰지 않는다.

SHRiNK는 흐름 표본화와 링크·버퍼·큐 관리 설정을 적절히 축소해 네트워크 성능을 추정하는 방법이다. 같은 부하 비율만으로 학습 수렴, CPU 경합, GPU 메모리까지 보존된다고 해석할 수는 없다. 네트워크 재현의 범위와 학습 품질 검증을 나누어 설명해야 한다. [SHRiNK 원문](https://web.stanford.edu/~balaji/papers/03shrinkaCONF.pdf)

**표기 정정:** 최종 결과 페이지의 '5/2 올리기/내리기'는 리그 코드와 다르다. `aA/aB`는 두 출구의 상한이며, 리그는 각각을 양방향에 적용한다.

## 5. 기존 성과의 재계산

### 5.1 네 시나리오의 라운드 시간

출처는 `out/wp_scen32_<장면>_s<1,2,3>_bothmp_{uniform,widthpath}.jsonl`이다. 각 실행의 라운드 행에서 앞 네 라운드를 제외한 makespan 평균을 구하고 세 시드를 평균했다. 아래 감소율은 두 평균의 비율로 계산했다. 원래 페이지 생성기는 시드별 감소율을 평균하며, 반올림한 결론은 같다.

| 장면 | 기준선 평균 | 결합 스케줄러 평균 | 감소율 | 직접 확인되는 의미 |
|---|---:|---:|---:|---|
| 정상 | 63.19초 | 47.64초 | 24.6% | 복수 출구 사용을 포함한 시스템 구성의 시간 이득 |
| 트래픽 몰림 | 109.51초 | 62.87초 | 42.6% | 엣지 용량 교란 조건에서 결합 시스템이 더 짧은 라운드를 유지 |
| 연산 느림 | 79.12초 | 47.26초 | 40.3% | 느린 참여자 조건에서 폭 제어 등을 포함한 시간 이득 |
| 용량 변동 | 72.97초 | 53.48초 | 26.7% | 단계적 용량 변화 조건에서 평균 라운드 단축 |

공개 최종 페이지의 반올림 값과 일치한다. 이 숫자는 새 SuperSFL 또는 OS-Ken 구현의 결과가 아니다. [최종 결과 페이지](https://claude.ai/artifact/9xrQS2YZkkQJA4HjHFdvtm), [원래 생성기](../../scripts/analysis/final_results_page.py), [대표 원자료](../../out/wp_scen32_normal_s1_bothmp_widthpath.jsonl)

### 5.2 다른 기존 실험이 보완하는 부분

8대 결합 실험은 같은 라운드 목표에서 네트워크 제어를 함께 사용하면 모델 폭을 더 보존할 수 있는지 살핀다. VMCLI 실험은 클라이언트 계산을 HPC 밖 KOREN VM에 둔 경우를 다룬다. 이들은 시간 단축표의 반복이 아니라 각각 **제어 수단의 결합 효과**와 **배치 환경 변화**를 보완하는 자료다. 다만 폭 보존을 정확도 보존으로 동일시하지 않는다. [8대 사전등록·판정](../02_실험/실험_결합_3번_사전등록.md), [VMCLI 로그](../../out/wp_vmcli_normal_s1_bothmp_widthpath.jsonl)

### 5.3 개발 과정의 성과

기존 기록에는 정적 용량 추정으로 혼잡을 놓친 문제, 잘못된 피드백으로 경로 복귀가 지연된 문제, 총시간 합만 줄이다 최장 기기를 남겨 둔 문제, 이동 상한 설정 오류가 남아 있다. 원인별로 수정·재실행한 기록은 개발과정의 강점이다. 단, 탐색 중 조정한 시나리오와 판정 기준은 최종 검증용으로 처음부터 고정된 조건과 구분해야 한다. [문제와 해결 기록](../04_설계기록/문제와_해결_2026-09.md), [후속 실험 기록](../02_실험/실험_후속_사전등록_2026-09-10.md)

## 6. 비판적 검토

### 6.1 시간 단축의 근거는 있으나 기여 분리가 부족하다

기준선은 한 회선·고정 배정·전폭이고 제안 방식은 복수 회선·동적 배정·폭 제어를 사용한다. 완성된 시스템 간 비교로 유효하지만 25~43% 전체를 경로 알고리즘 하나의 효과로 귀속할 수 없다. 특히 정상 장면의 이득은 복수 출구 사용이 주요 설명이다.

이미 수행한 8대 절제 실험을 함께 제시하고, 같은 회선 수를 허용한 정적 분할 기준선과 비교해야 한다. 보고서에는 '기존 단일 출구 구성 대비 결합 시스템의 개선'이라고 비교 대상을 명시한다.

### 6.2 학습 정확도가 가장 큰 미해결 지표다

라운드 시간이 줄어도 목표 정확도까지 필요한 라운드가 늘면 전체 학습 이득이 사라질 수 있다. 현재 자료는 평균 폭을 품질의 대리 지표로 사용하고 자체 정확도 해석을 유보한다. 이 선택은 측정 잡음을 정직하게 드러내지만, 정확도 유지 주장을 완성하지는 못한다.

FjORD 결과는 폭 제어를 선택한 연구 근거로 사용한다. 현재 시스템의 정확도를 대신하는 실험 결과로 사용하지 않는다. 우선 고정폭 단독 학습, 고정폭 SFL, 혼합폭 SFL, 동적폭 SFL의 차이를 확인하고, 같은 평가 모델·데이터·학습량에서 비교해야 한다.

### 6.3 SDN과 권한에 대한 표현을 좁혀야 한다

현재 측정으로 확인되는 집행은 출구 종점 변경과 tc 제어다. 중앙 정책이 데이터 경로를 바꾼다는 구조는 SDN으로 발전시킬 수 있지만, 이를 OpenFlow 제어 완료나 KOREN 백본 라우팅 제어로 표현하면 구현 범위를 넘는다.

현재 관리 가능한 HPC/VM의 설정 권한과 외부 기기·기관망의 제어 권한도 다르다. 기기 신원 인증, 허용 엣지 접근, 정책 철회, 적용 실패 복구가 부족하다. KOREN을 쓴다는 사실만으로 이 권한들이 확보되는 것은 아니다.

### 6.4 정확도 관련 코드 결함과 실험 영향은 구분한다

9월 19일 검사에서 다음을 확인했다.

- 재조립기가 겹친 바이트 구간을 다른 seq로 받으면 길이 합만으로 완료를 인정하는 결함을 최소 입력으로 재현했다. 정상 조각 생성기의 출력에서 발생한 것으로 확인한 것은 아니다.
- micro 모드에서는 서버의 loss 정규화로 gradient가 이미 1/m이 된 뒤 클라이언트에서 다시 1/m로 나뉜다. 양쪽 경로의 정적 검사 결과이며 torch 수치 시험은 미실행이다. 확인한 대표 실행은 micro=1이라 이 결함으로 그 결과를 설명하지 않는다.
- 서버 폭별 모델 동기화가 사용 폭이 둘 이상일 때만 수행되어, 한 폭만 학습한 뒤 다른 폭으로 전환할 때 캐시 상태가 오래될 가능성이 있다. 정확도 원인으로 확정하려면 전환 시험이 필요하다.
- BN 통계 혼합, optimizer 상태 유지 방식, 평가 폭 선택도 함께 점검해야 한다.

이 사항들은 기존 네트워크 시간 측정 전체를 무효화하는 근거가 아니다. 학습 품질과 일반적인 운영 신뢰성을 주장하기 전 해결할 구체적인 항목이다. [상세 코드 검사](../04_설계기록/구현범위_검사_2026-09-19.md)

### 6.5 축소 실험의 타당성과 일반화 범위

실측을 기반으로 상한을 정하고 반복 가능한 교란을 주입한 점은 강점이다. 그러나 tc 용량 변화는 자연 발생한 실사용 혼잡 전체를 대변하지 않으며, 공유 CPU·SSH 암호화·터널 구성의 영향이 남는다. 반복 시드가 셋이라는 사실도 날짜별 회선 변동이나 여러 사이트 환경까지 검증했다는 뜻은 아니다.

추가 검증은 장비 수를 무조건 늘리기보다, 현재 감당 가능한 두 규모에서 부하 비율을 맞췄을 때 정책 순위·반응 시간·큐 지연이 유지되는지 확인하는 방식이 효율적이다. 이는 후속 제안이며 이미 완료한 결과가 아니다.

### 6.6 재현성과 문서 관리

조건 원장·인자·프로파일·라운드 로그가 존재하는 것은 강점이다. 반면 일부 iperf 원파일의 미보존, 회선 요약파일 덮어쓰기, 같은 보고서 안의 이전·최종 결과 혼재는 추적을 어렵게 한다.

대표 수치에 실행 파일·시드·집계 구간을 연결하고, 실행 ID와 코드 커밋을 함께 보존해야 한다. 현재 README의 정확도 표와 최종 페이지의 정확도 유보 입장도 맞춰야 한다. 기존 내부 문서의 '문서만 잘 쓰면 특정 배점을 확보한다'는 주장은 삭제 또는 수정 대상이다. 문서는 실제 수행과 증거를 설명하며 점수를 보장하지 않는다.

KOREN의 기여는 '이 망에서만 가능한 알고리즘'이라는 독점적 주장보다, **실제 원격 자원의 성능과 제약을 계측하고 제어 정책을 실행·관찰한 시험 기반**으로 설명하는 것이 정확하다. 현재 실험은 KOREN 백본 자체의 혼잡 문제를 해결했다고 입증하지 않는다. 실제 연결 위에 제어된 병목을 만들고 대응을 관측했다.

## 8. 제출에 사용할 수 있는 성과 문안

> 본 과제는 기기별 연산 성능과 접속 경로 상태가 다른 분할 연합학습 환경에서, 엣지 접속 경로·다중 경로 전송·모델 폭을 함께 조정하는 AwareNet을 구현하였다. HPC와 KOREN VM을 연결한 환경의 회선 특성을 사전 측정하고, 그 결과에 따라 접속·엣지 용량을 축소한 반복 실험 조건을 구성하였다. 32개 논리 클라이언트의 정상·트래픽 몰림·연산 지연·용량 변동 시나리오에서, 단일 출구·고정 배정·전폭 기준선 대비 평균 라운드 시간을 약 25~43% 단축하였다. 별도 8개 클라이언트 실험에서는 제어 수단의 결합과 원격 VM 배치의 동작을 확인하였다. 현재 성과는 통신·연산 제어에 따른 시스템 시간 개선에 있으며, 학습 정확도 유지와 실제 SDN 제어기의 통합은 후속 검증 과제로 남아 있다.

피해야 할 표현과 대체 문안:

| 피해야 할 표현 | 근거에 맞는 표현 |
|---|---|
| 정확도를 유지하며 학습을 43% 가속 | 특정 몰림 시나리오에서 평균 라운드 시간을 약 43% 단축; 정확도 영향은 미확정 |
| 물리 기기 32대·엣지 서버 4대 실증 | 논리 클라이언트 32개·VM 두 대의 논리 엣지 네 개 |
