# 요 약

본 과제는 중간보고서까지 "회선을 나눠주는" 설계였고, 8월 말에 "학습량을
나눠주는" 설계로 방향을 바꿨다. 바꾼 근거는 측정과 조사다 — 같은 회선 안에서
몫을 재분배해도 완료 시각이 변하지 않았고(실측), 실제 연합학습 배치에는 나눠줄
공용 회선 자체가 없었다(구글·병원 20곳·제약사 10곳 조사).

챌린저데이에서 외부 멘토는 구판 보고서를 보고 "배분 장치가 효과가 있으면 왜
연합학습에만 쓰는가, 전체 네트워크에 적용하라"는 의견을 주었다. 이 의견을 따르면
과제에서 연합학습이 빠지고, 따르지 않으면 과제 제목("KOREN SDN 기반")의 SDN이
본문에서 사라진다 — 어느 쪽이든 대가가 있다.

본 보고서는 두 방향의 한계를 정직하게 정리하고, 각각의 한계를 줄이는 발전안을
제시한다. 분석의 끝에서 두 발전안이 같은 부품(큐 우선순위·경로 배정·전송 시차·
마감 규칙)으로 수렴한다는 것을 확인했고, 남는 결정은 하나로 좁혀진다 —
**학습량 조절(폭)과 언어모델을 본체로 두느냐, 축소하느냐.** 팀 의견은 본체
유지이며(근거: 과제의 새로움이 학습 쪽 층에 있음), 이 결정을 지도 교수님과
확정하고자 한다.

# Ⅰ. 배 경

## 1. 과제의 원래 목표

여러 기관·기기가 데이터를 넘기지 않고 AI를 함께 학습(연합학습)할 때, 네트워크는
그 트래픽이 무엇인지 모른다. 그래서 마감을 넘긴 기기가 라운드에서 버려지고, 누가
버려질지는 회선 경합의 운이 정한다. 본 과제의 원래 목표는 이 문제를 푸는
**"연합학습에 특화된 네트워크"**를 만드는 것이었다.

## 2. 중간보고서까지의 설계 — 회선을 나눠주기

KOREN VM 위에 100대(클라이언트)–엣지 5개–서버의 토폴로지를 만들고, 제어용과
데이터용 VXLAN 터널을 분리했으며, 엣지 송신 큐(HTB)에 매 라운드 배분값을
내려보내는 컨트롤러를 구현했다. 핵심 실증은 완료했다 — 한 회선(45Mbps)에 흐름
3개를 경합시키고 큐 비율을 8:1:1로 지정하니 실제 처리량이 7.93:1.01:1.00으로
나왔고, 집행 정확도는 96~100%였다. 즉 "큐 정책으로 회선을 원하는 비율로 나눌 수
있다"는 것은 실제 장비에서 증명이 끝났다.

# Ⅱ. 방향 전환의 경위와 근거

## 1. 무엇을 발견했나

장치는 증명됐지만, 그 장치가 필요한 무대가 문제였다. 회선을 나눠주는 장치가
효과를 내려면 여러 참가자가 **하나의 회선을 같이 써야** 한다. 그런데:

1. **재분배의 무효(실측).** 같은 회선 안에서 몫을 재분배해도 완료 시각이 변하지
   않았다(32.0초 대 34.7초, 오차 범위 안). 현대 TCP는 남는 회선을 놀리지 않으므로,
   손대지 않아도 이미 물리적 하한에 닿아 있었다.
2. **전송 시점 조절의 무효(실측).** 느린 쪽을 당기지 못하고 빠른 쪽만 52% 늦췄다.
3. **공용 회선의 부재(조사).** 실제 연합학습 배치(구글 상용 시스템, 병원 20곳의
   EXAM, 제약사 10곳의 MELLODDY)를 조사한 결과, 참가자들이 함께 쓰는 공용 회선
   자체가 없었다. 기관과 기기가 저마다 자기 회선을 쓴다. **나눠줄 것이 없었다.**

## 2. 그래서 무엇으로 바꿨나 — 학습량을 나눠주기

회선은 못 나누지만, 서버가 각 기기에게 **얼마나 큰 숙제를 줄지**는 나눌 수 있다.
느린 기기에게 모델의 일부(학습 폭)만 학습하게 하면 마감 안에 들어오고, 데이터도
버려지지 않는다. 이 방향으로 8월 말에 검증을 완료했다 — 속도가 제각각인 환경에서
라운드 시간 40% 단축, 달리는 중의 악화에 1라운드 반응, 언어모델(LoRA) 이식과
3기관 연합 학습 성립, 폭과 경로의 동시 결정(예측 오차 3%).

## 3. 전과 현의 대비

**표 1. 전과 현 — 무엇이 바뀌었나**

| | 전 (중간보고서까지) | 현 (전환 후) |
|---|---|---|
| 한 줄 목표 | 학습 가치를 반영해 **회선을 배분**하는 SDN 계층 | 망·기기를 실측해 **학습량을 배분**하는 컨트롤러 |
| 네트워크의 역할 | 제어 대상 (VXLAN 토폴로지·큐 배분) | 측정 대상 (제어하지 않음) |
| 연합학습의 역할 | 응용 (트래픽을 만드는 쪽) | 본체 |
| SDN | 본체 | 사실상 소멸 — 경로/접속 지점 배정만 흔적 (아직 모의 검증) |
| 전환 근거 | — | 공용 회선 부재(조사) + 재분배 무효(실측) |

# Ⅲ. 외부 멘토링 의견과 쟁점

## 1. 의견의 내용 (2026-08-28 챌린저데이, 구판 보고서 기준)

멘토의 논리 흐름을 그대로 옮기면 이렇다: "연합학습에서 네트워크가 트래픽을
인지하지 못하는 문제를 풀겠다고 시작했고, 배분층에서 효과가 나왔다. 그렇다면 이
장치가 꼭 연합학습에서만 되는 것인가? 도메인을 한정하지 말고 전체 네트워크에
적용하라." 학습 폭 이야기에는 관심을 보이지 않았다. 보고서의 가독성 문제("모르는
사람이 알아들을 수 있게")도 함께 지적받았다 — 이것은 방향과 무관하게 수용하여
보고서를 전면 재작성했다(완료).

## 2. 쟁점

이 의견은 방향에 관한 실질적 갈림길을 만든다. 의견을 그대로 따르면 과제에서
연합학습이 빠지는데, 원래 목표는 "연합학습에 특화된 네트워크"였다 — 과제 제목이
일반 SDN 과제처럼 읽혀 오해를 산 면이 있다. 반대로 현 방향을 유지하면 과제
제목("KOREN SDN 기반")의 SDN이 본문에서 사실상 사라진다. 멘토는 일회성 외부
조언자(지도 교수님과 무관)이므로 반영 여부는 팀이 근거를 갖고 정하면 되지만,
심사위원으로 참여할 가능성이 있어 반영 기록의 문안은 신중히 준비한다(Ⅴ-3).

# Ⅳ. 두 방향의 분석

## 1. 두 방향의 한계 (정직하게 — 둘 다 한계가 있다)

**연합학습 치중(현 방향)의 한계.** 네트워크 과제로서의 필요성이 약해진다. 학습
폭(Ordered Dropout)과 SDN 제어는 물리적으로 섞이지 않는다 — 유일한 접점은
경로/접속 지점 배정인데 아직 모의 검증뿐이다. 과제 제목과의 거리가 생긴다.

**네트워크 집중(멘토 제안)의 한계.** 연합학습을 버려야 한다. 그리고 일반 트래픽을
알아보고 나눠주는 일은 이미 표준 기술이 있다(리눅스 큐, 통신사 QoS, 5G 슬라이싱)
— 일반화하는 순간 과제가 "기존 기술의 재확인"이 되어 새로움이 약해진다. 최근
2주의 검증 자산(폭 컨트롤러·언어모델·실시간 시연)도 발표에서 대부분 빠진다.

## 2. 부품 구분 — 일반 네트워크에서도 되는 것과 연합학습에서만 되는 것

두 방향을 가르기 전에, 우리가 만든 부품들이 어디까지 일반적인지 먼저 구분한다.

**표 2. 부품 구분표**

| 일반 네트워크에서도 되는 것 (조절: 언제·어디로·누구 먼저) | 연합학습에서만 되는 것 (조절: 얼마나) |
|---|---|
| 큐 우선순위·배분 (누구 먼저) | **학습 폭 조절** — 보내는 양 자체를 줄여도 결과가 성립 |
| 전송 시차 — 몰림 회피 (언제) | LoRA 랭크 조절 (언어모델판) |
| 경로/접속 지점 배정 (어디로) | 어댑터만 모아 평균하는 연합 집계 |
| 마감 기준선 — 중앙값×1.2 (얼마나 기다릴지) | 시간↔정확도 거래의 판단 |
| 파이프라이닝 — 기다림 숨기기 | 최소 폭 참여 보장 (배제 없는 학습) |
| 인밴드 측정 (상황 인지) | |

가르는 본질은 한 줄이다. **일반 트래픽은 내용이 깨지면 안 된다** — 파일은 반만
보내면 쓸모가 없으므로, 조절할 수 있는 것은 타이밍과 경로뿐이다. 반면 **학습
트래픽은 양을 줄여도 품질이 점진적으로만 떨어진다** — 그래서 학습에서만 네 번째
손잡이("얼마나 보낼지")가 열리고, 본 과제의 폭 조절이 그 자리에 서 있다. 왼쪽
열은 표준 기술과 겹치는 영역이라 본 과제의 새로움이 아니며, **새로움은 오른쪽
열에 있다.**

## 3. 발전안 ① — 연합학습 치중을 유지하면서 SDN을 되살리는 세 연결

한계였던 "폭과 SDN이 물리적으로 안 섞임"을 줄이는 연결 지점이 셋 있다. 셋 다 새
시스템이 아니라 이미 있는 부품을 잇는 것이다.

1. **큐 우선순위를 세 번째 조절 수단으로.** 현재 컨트롤러의 단계는 "폭 축소 →
   (부족하면) 양자화"인데, 여기에 "(관리형 망이라면) 게이트웨이 큐에서 그 기기의
   업로드 우선순위 상향"을 추가한다. 학습 손잡이(폭)와 망 손잡이(큐)를 같은 마감
   규칙이 함께 산출하게 되고, 중간보고서의 큐 집행 실증(8:1:1)이 그대로 집행층이
   된다. 성립 조건(기관 게이트웨이 — 병목 큐를 우리가 소유)은 명시한다.
2. **폭×경로 동시 결정의 실WAN 승격.** 이미 통과한 폭×경로 동시 결정(현재 모의)을
   KOREN 다지점에서 실제 경로로 실증한다. SDN으로 연합학습 경로를 배정하는
   선행(SmartFLow)이 있으므로 "최초" 주장은 하지 않는다 — 차별점은 경로를 폭과
   **함께** 정한다는 것이다(선행은 경로만 정한다).
3. **전송 시차의 망층 집행.** 라운드 경계에 전송이 몰리는 문제(실측: 13대 동시
   업로드에 지연 5배)를 푸는 시차를 앱 계층이 아니라 게이트웨이 큐로 집행하면
   망층의 기여가 된다.

셋을 합치면 "하나의 컨트롤러가 학습 손잡이(폭)와 망 손잡이(큐·경로·시차)를 같은
규칙으로 함께 결정"이 되어, **과제 제목의 SDN이 본문으로 돌아온다.**

## 4. 발전안 ② — 네트워크 집중을 "일반"이 아니라 "연합학습 특화"로

멘토 제안을 그대로 하면(일반 트래픽 배분) 표준 기술의 재확인이 되지만, 범위를
**"연합학습의 트래픽 구조를 아는 네트워크"**로 좁히면 새로움이 살아난다. 연합학습
트래픽에는 일반 트래픽에 없는 구조가 있다 — 라운드 경계의 다대일 몰림, 마감,
주기적 벌크 전송, 참여자 집합의 변동. 이 구조를 아는 망 제어는 실재하는 연구
영역이다(망 내 집계와 경로의 공동 스케줄링, SDN 기반 기관 간 연합학습 경로 배정,
혼잡 인지 집계 스케줄링). 이 판이라면 연합학습을 버리는 것이 아니라 **특화
대상으로 유지**된다 — 원래 목표였던 "연합학습에 특화된 네트워크"와 정확히
일치하고, 제목의 오해도 해소된다. 대가는 폭·언어모델의 비중 축소다.

## 5. 수렴 — 남는 결정은 하나다

발전안 ①과 ②는 같은 부품(큐 우선순위·경로 배정·전송 시차·마감 규칙)을 쓴다.
차이는 하나뿐이다 — **폭(학습량 조절)과 언어모델을 본체로 두느냐, 축소하느냐.**

# Ⅴ. 결론 및 건의

## 1. 팀 의견

팀 의견은 **본체 유지(발전안 ①)**다. 근거는 표 2다 — 일반 네트워크에도 적용
가능한 부품들은 표준 기술과 겹치는 영역이라 본 과제의 새로움이 아니고, 새로움은
학습에서만 열리는 층(폭·랭크·배제 없는 학습)에 있다. 이 층을 축소하면 검증
자산의 대부분(라운드 시간 −40%, 언어모델 3기관 연합, 실시간 시연)이 발표에서
빠지고, 남은 두 달 안에 일반 트래픽 실험을 새로 채워야 한다. 반대로 발전안 ①은
기존 부품을 잇는 것이라 추가 구현 부담이 작고, 제목의 SDN도 회복된다.

## 2. 교수님께 여쭙고 싶은 것

1. **방향**: 폭·언어모델을 본체로 유지(발전안 ①)할지, 축소(발전안 ②)할지, 그
   사이 어디쯤일지.
2. **과제 제목**: "KOREN SDN 기반"이 현 방향과 거리가 생겼는데, 제목을 조정할지
   본문의 SDN 접점(발전안 ①의 세 연결)을 강화하는 쪽으로 갈지.
3. **멘토 반영 기록**: 아래 문안이 심사에서 충분한지.
4. **전환 서술 수위**: 중간보고서와 최종보고서 사이의 설계 전환을 가설-검증-기각
   형식으로 정면 서술하는 방안에 대한 의견.

## 3. 멘토 반영 기록 (준비 문안)

> "외부 멘토링에서 일반 네트워크로의 확장 의견을 받았다. 검토 결과, 일반 트래픽을
> 알아보고 나눠주는 일은 이미 표준 기술(QoS·슬라이싱)이 있어 확장 시 과제의
> 새로움이 사라진다고 판단했다. 학습 조절 방향을 유지하되, 지적의 취지를 받아
> 망 쪽 접점(큐 우선순위·경로 배정·전송 시차)을 강화했고, 일반 트래픽으로의 확장
> 가능성은 향후 과제로 기재했다. 이 반영 범위는 지도 교수님과 협의해 확정했다."

## 3-1. 과제명 변경 사유 (신청서·보고서용 문안)

새 과제명(안): **AwareNet — 학습은 더 빠르게, 참여는 빠짐없이: 기기마다 알맞은 학습량과 접속 경로를 정하는 연합학습 네트워크 (KOREN 실측 기반)**

> "본 과제는 당초 KOREN 의 SDN 제어 기능을 활용해 회선을 측정·제어하는 것을 계획하였습니다. 그러나 수행 과정에서 현실적인 제약으로 해당 기능(L2VPN 개통, T-SDN OpenAPI 등)을 제공받기 어렵다는 것을 확인하였습니다. 이에 OVS(Open vSwitch)로 가상 경로를 직접 구성해 SDN 제어를 대신하는 방안도 검토하였으나, 이는 저희가 만든 가상 환경 안에서만 성립하고 실제 운영 환경으로 이어질 수 없다고 판단하여 채택하지 않았습니다. 이에 따라 과제의 초점을 연합학습의 학습 환경 — 학습 트래픽의 측정과 기기별 학습량·접속 경로의 조절 — 으로 옮겼습니다. SDN 의 개념이 사라진 것은 아니며, 중앙 제어부가 망 전체를 관측해 기기의 접속 지점을 바꾸는 재접속의 형태로 이어집니다. 이러한 변경 내용을 과제명에 반영하여 정정하고자 합니다."

절차: ① 사무국에 과제명 변경 가능 여부 확인(선행) ② 가능 시 위 문안으로 신청
③ 불가 시 등록명 유지 + 표지에 새 문구를 부제로 병기.
