# 본실험 설계 정정 — "원 대역폭"의 근거와 서사 재정립

작성: 2026-08-11. 계기: "기업이 데이터를 수집해야 하는 노드를 일부러 느리게 설정한다는
전제가 말이 안 된다"는 팀 내부 비판. 검토 결과 **비판이 옳았고, 구현 결함도 함께 발견**됐다.

---

## 1. 무엇이 이상했나 (인정)

### 1-1. 현행 구현의 암묵적 전제

지금 에뮬레이션은 이렇게 돈다.

```
기준선(static):  노드 i의 tc 캡 = 트레이스값 b_i          (0.23 ~ 35.85Mbps)
우리(full):      노드 i의 tc 캡 = 배분값 a_i  ← b_i를 덮어씀
```

배분이 원 대역폭을 **덮어쓴다**는 것은 b_i를 "관리자가 걸어둔 정책 캡"으로 취급한다는
뜻이다. 그러면 서사가 이렇게 된다 — "기업이 자기 학습 노드들을 0.23Mbps로 묶어놨고,
우리가 그 캡을 풀어준다." **데이터를 모으려고 배치한 노드를 스스로 마비시키는 관리자는
없다.** 전제가 이상하다는 비판이 정확히 이 지점을 찌른다.

### 1-2. 더 심각한 것 — 물리 위반

배분값이 원 대역폭을 **초과할 수 있다.** 0.23Mbps 노드에 10Mbps를 배분하면 현실에서는
불가능한데 에뮬레이션에서는 그대로 전송된다. 이는 우리 스스로 세운 원칙
("물리 한계는 배분으로 못 살린다 — 범위 밖", 보고서 6.5절 `실효 BW = min(물리, 정책, 경합 몫)`)
을 **에뮬레이션이 위반**하고 있는 것이다. 발견 즉시 수정한다.

## 2. 근거 있는 숫자 체계 (모든 값의 출처)

| 숫자 | 값 | 근거 |
|---|---|---|
| **노드별 원 대역폭 b_i** | 5G 실측 분포 0.23~35.85Mbps (P50 6.93) | Zenodo 13754300 실측, 원본 재현 검증 완료(P5 오차 0.5%), FedScale 50만과 중앙값 수렴(14%) |
| **b_i가 낮은 이유** | 무선 접속 품질의 이질성 | 셀 가장자리·간섭·장애물·단말 성능 — **관리자의 설정이 아니라 전파 환경.** 원본 데이터 자체가 캠퍼스 5G의 위치·구성별 실측 |
| **공유 상향 용량 C** | 100Mbps | 게이트웨이 공유 업링크 모델. 검증: 현행 방식 13노드 무작위 선발의 합계 P50 = **108Mbps** → 같은 총량의 재배분임이 성립(우리가 오히려 8% 적게 씀) |
| **마감 τ** | 균등 배분 P50 도착 × 1.5 (실측) | 사전 등록 규칙. 워크로드 바뀔 때마다 재측정 (컨테이너+9.38MB 기준 재보정 예정) |
| **구제 필요 속도 r\*** | payload×8/(τ−comp) | 유도값. 9.38MB·τ=10s면 ≈7.5Mbps. **"3Mbps" 같은 임의 문턱을 대체한다** — 어떤 노드가 살 수 있는지는 r\*와의 비교로 결정되는 원리적 값 |
| 혼잡 수준 | 배경 트래픽 0→극단 스윕 | 사전 등록된 실험축. 단일 지점을 고르지 않음 |

※ 기존 문서의 "3Mbps 미만 32%"는 소실 확률 분석의 서술용 문턱이었다. 실험 설계에서는
r\*로 대체하고, 3Mbps 문구가 남는 곳에는 "당시 분석의 예시 문턱"임을 명시한다.

## 3. 정정된 서사 — 경합이 주인공이다

### 3-1. 문제 (원인이 관리자가 아니라 구조)

동기식 연합학습은 라운드마다 선발 노드들의 업로드를 **같은 순간에 출발**시킨다
(자기 경합 — 13대 동시 업로드에서 제어 지연 P95 5.2배, 완료 시간 2.6배 편차 실측).
이 버스트가 게이트웨이 공유 상향 C를 나눠 갖는데, 기본 동작은 두 가지뿐이다.

- **TCP 경쟁(현행)**: 몫이 운에 좌우된다 — 같은 조건 13플로우가 4.8~12.7초로 갈렸다.
  누가 마감을 넘길지 예측 불가, 그리고 **데이터 가치와 무관**하게 결정된다.
- **균등(공평 분배)**: 예측은 되지만, 혼잡이 커지면 **전원이 같이 느려져 전원이 마감을
  넘긴다** (경합 50%에서 전원 탈락 실측).

### 3-2. 해법 (한 문장)

> **경합 상황에서 모두가 비슷하게 느려지는 대신, 데이터 가치가 높은 노드가
> 마감 안에 도착하도록 같은 총량 C를 재배분한다. 그 도착이 모델 품질을 끌어올린다.**

- 가치 높은 노드에 r\* 이상을 보장하고(유용성 캡 — 그 이상은 낭비이므로 회수),
  나머지는 잔여분과 최소 보장을 받는다.
- 합계는 항상 C 이하 — 대역폭을 만들지 않고 **순서를 바꾼다.**

### 3-3. 원 대역폭 b_i의 새 역할 — 상한이지 대상이 아니다

b_i는 "풀어줄 캡"이 아니라 **무선 물리의 상한**이다. 배분은 그 아래에서만 유효하다.

```
실효 전송률 = min( b_i(무선 상한),  a_i(경합 몫 배분) )
```

- b_i ≥ r\* 인 노드: 경합에서 몫만 확보되면 산다 → **구제 대상**
- b_i < r\* 인 노드: 어떤 배분으로도 못 산다 → **물리 한계, 범위 밖**
  (배분기가 자동 판별해 최소 몫만 배정 — 기존 계산 병목 판별과 동일 원리)
- 살릴 수 있는 비율 = |{i : b_i ≥ r\*}| 를 **결과로 보고** — 기존 사전 등록 항목 그대로,
  이제 에뮬레이션도 같은 규칙으로 돈다.

이 프레임에서는 "기업이 왜 느리게 설정했나"라는 질문 자체가 사라진다 —
**아무도 느리게 설정하지 않았다. 무선이 원래 고르지 않고, 버스트가 원래 몫을 쪼갠다.**

## 4. 구현 수정 (3건)

| # | 수정 | 위치 |
|---|---|---|
| 1 | **물리 상한 클램프**: tc 적용값 = min(배분 a_i, 원 대역폭 b_i). b_i는 bandwidth_assignment_local.json에서 읽음 | tc 에이전트 (pangyo_tc_agent.py) |
| 2 | **희귀 노드 배치 규칙 변경**: "가장 느린 노드"가 아니라 **구제 가능 대역** — b_i ≥ r\* 이면서 균등/경쟁 몫으로는 τ를 못 지키는 노드. (가장 느린 노드에 두면 물리 한계라 어떤 방법으로도 못 살림 → 실험이 아무것도 비교하지 못함) | placement 생성 |
| 3 | **경합 주입**: 배경 트래픽 스윕(0→극단)을 주 실험축으로. 공유 링크 C에서 가용분이 줄어드는 것을 모사 | 실행 스크립트 |

## 5. 실험 순서 (향후 방향)

1. **셰이핑 충실도** (진행 중) — "요구한 몫이 실제로 나온다" 실측. 재배분 주장의 전제
2. **수정 1~3 반영** 후 τ 재보정 (EMNIST + MobileNetV2 9.38MB, 균등 3라운드)
3. **본실험**: 4방식(static/equal/selection_only/full) × 혼잡 스윕 × 시드 3회
   - 1차 지표: 희귀 데이터 노드의 마감 내 도착률, 희귀 클래스 정확도(EMNIST 실학습)
   - 함께 보고: 살릴 수 있는 비율, Σ배분 ≤ C 로그, 가치 자기상관 ρ
4. **문서 정정**: ① 5G 트레이스 인용을 Zenodo 13754300으로 (현행 IEEE DataPort 인용은 오류)
   ② 격차 수치를 "원본 41배 / 주입 34배"로 구분 ③ 본 문서의 서사(경합 중심)로 배경 설명 정렬

## 6. 발표 방어에 주는 효과

- "기업이 왜 노드를 느리게 설정하나?" → **설정한 적 없다. 무선 이질성(실측)과 라운드
  버스트(실측)가 원인이고, 우리는 그 경합의 분배 규칙만 바꾼다.**
- "그 대역폭 숫자들 어디서 났나?" → 전부 출처표(2장)로 답한다. 임의 상수는 r\*로 대체되어
  유도 가능하다.
- "물리적으로 느린 노드도 살릴 수 있나?" → **못 살린다. 그래서 min()으로 강제했고,
  살릴 수 있는 비율 자체를 결과로 보고한다.** (기존 답변과 일치, 이제 구현도 일치)
