# 절제 5판 — 병목 유형 혼합 집단 사전 등록 (2026-09-06 개정 2판)

> 목적: 두 손잡이 체제의 정의 — **연산 병목 → 폭, 공유 구간 혼잡 → 경로, 접속 회선 병목 → 폭(또는 분할 전송)** —
> 를 실장비에서 확인한다. 판정은 "둘다가 얼마나 빠른가"가 아니라 **"기기마다 맞는 손잡이가 갔는가"**다.
> 2판은 연산이 동질이라 폭이 할 일이 없었고(폭만 0%), 경로 이득 +23%는 리그(`paths.sh`)가 옮기면 공짜 용량을 주는
> 구조였다. 둘 다 현실이 아니다. 5판은 hairpin 리그(접속 회선 + 공유 경로)에서 병목 유형을 섞는다.
>
> 이 문서는 **돌리기 전에** 쓴다. 조건마다 출처 유형을 붙인다. 계획기는 2026-09-06 개정판(`plan_two_stage`, 병목 유형 우선)이며
> 구판(`two-stage-v1`)은 혼합 집단에서 연산 낙오자의 폭을 복귀시키는 결함이 있어 비교 팔로만 둔다(`설계기록_컨트롤러.md` §8).

## 3. 판정 (사전 등록)

1. **손잡이 대응 (주 판정)**: 둘다(개정판) 3시드 모두에서 표 1 의 기대가 성립 — c0 폭 ≤ 0.5 로 수렴 후 복귀 없음, c1 경로 2, c2 폭 < 1.0, c3 폭 1.0. 하나라도 어긋나면 그 기기 유형에 대해 규칙이 틀린 것 — 기록하고 규칙을 고친다.
2. **상호 보완 (부 판정)**: 둘다 ≤ min(경로만, 폭만) − 3%p (단위 작업당). 성립하지 않으면 "따로보다 낫다"는 주장을 내린다.
3. **구판 결함 재현**: 구판 팔에서 c0 폭이 1.0 으로 복귀하는 라운드가 있는가. 재현되면 §8 기록의 실장비 증거.
4. **무효**: 팔이 자기 손잡이 밖을 쓴 흔적(폭만 로그에 "경로 이동", 경로만 로그에 폭<1.0) → 시드 폐기. `test_two_stage.py` 통과가 실행 게이트. 실행 인자는 `.args.json` 으로 확인.
5. **정확도**: 12라운드 정확도 차 −5%p 이내면 잡음. c0 폭 0.5 의 대가는 별도 표기.

### 읽기 — 세 시드가 같은 말을 한다

**① 개정판은 사전등록한 손잡이 대응을 3/3 맞췄고, 구판은 3/3 틀렸다.** 구판의 c0 폭 복귀(§8 결함)가 시드 2 실장비에서 재현됐고, 시드 1·3에서는 c0 이 0.75 에서 멈추는 변형으로 나타났다(연산 4배·6.7배인데 바닥 0.5 까지 안 감).

**② 그런데 makespan 은 구판이 앞선다 (+43.7% vs +24.8%).** 이유는 구판이 **c2 를 경로 2 로 옮기고 0.5 로 깎았기 때문**이고, 이것이 이 리그에서는 **c2 에게 맞는 대응이었다.** 경로만 팔에서 c2 를 경로 2 에 혼자 두자 전송이 11.3 → 7.7s 로 줄었다. 즉 c2 는 사전등록에서 가정한 "접속 회선 병목(경로를 옮겨도 안 풀림)"이 **아니었다.**

**③ 원인은 리그의 물리다 (관찰 B 의 진짜 정체).** `hairpin_lo.sh` 는 접속 회선을 `HTB rate a ceil c` 로 만든다. 경로 1 에 4대가 몰리면 보장 합(50+50+20+50=170) > 경로(60) 이라 HTB 가 **rate 에 비례해서** 나눈다 → c2 는 60×20/170 ≈ 7~12 Mbps, 나머지 ≈ 27 Mbps (실측 비 2.3 ≈ 50/20). 즉 이 리그에서 "접속 회선 20M"은 독립된 상한이 아니라 **공유 구간에서의 낮은 가중치**로 작동한다. c2 는 접속 회선 병목이 아니라 **혼잡의 가장 큰 피해자**였고, 그러니 경로 이동이 맞는 손잡이였다. 경로 2 단독 7.7s = 17.5 Mbps 로 상한 20M 에 근접 — 큐 33패킷의 영향은 ~12% 로 부차적.

**④ 개정판이 c2 를 못 옮긴 이유는 `--access-caps` 오라클이 리그와 다른 물리를 알려줬기 때문이다.** 모형은 "c2 는 어디로 가도 20M 이 상한이라 이동 이득 없음"으로 계산했고(접속 회선 항 = 3.4s), 실제 리그는 옮기면 빨라졌다. 오라클이 틀린 물리를 주입한 셈이다. 그리고 잔여 단계는 **모형 t_k 기준**이라 실측 11s 짜리 c2 를 경계선(0.75↔1.0 진동)으로만 다뤘다(관찰 A). 폭만 팔은 c2 를 아예 못 잡았다(+0.3%).

**⑤ 결론.** 규칙의 방향(연산→폭, 혼잡→경로)은 맞고 실장비에서 확인됐다. 틀린 것은 둘이다 — (a) **리그**: 접속 회선을 독립 상한으로 만들지 못했다. (b) **잔여 단계**: 모형이 아니라 관측으로 판단해야 하고, 잔여 폭 복귀에 재확인이 없다. 구판의 makespan 우위는 "틀린 이유로 맞는 손잡이"에 도달한 결과이며 정확도 −2.7%p 를 냈다.

### 다음 (재사전등록 후 재실행)

1. **리그 수정** `hairpin_lo.sh`: 접속 클래스를 `rate c/n ceil min(a_k, c)` 로 — 공유 구간은 기기 수로 균등, 접속 회선은 **하드 상한**. 검증: 4대 동시 흐름에서 클래스별 처리량이 (min(a_k, 균등몫)) 을 따르는지 `tc -s class show` 로 확인. c2 접속 회선은 균등몫(15M) 아래인 **10M** 으로 낮춰야 "경로를 옮겨도 안 풀리는" 유형이 된다.
2. **잔여 단계 수정** `plan_two_stage` 2단: 초과 판정을 관측 기반 t_k(cpu1·net1 EWMA, 현재 폭·배정에서 관측된 값)로. 잔여 폭 복귀는 2라운드 연속 "초과 아님"일 때만. 시험: 전원 경로 1 에서 접속 회선 낙오자가 잡힌다 · 한 번 내린 잔여 폭이 매 라운드 흔들리지 않는다.
3. `--access-caps` 오라클은 리그 수정 후에만 의미 있음. 리그 수정 전 5판 결과는 **리그 결함 하의 결과**로 보존(이 절), 대외 인용 금지.
4. 재실행 조건은 §1 표를 갱신하고(c2 access 10M), 스모크 §3-1 점검에 "c2 단독 처리량 ≈ 접속 상한, 4대 동시에 c1·c3 ≈ 균등몫" 항목을 추가한다.
