# 연합학습 표준 시스템 정리 — 재설계 0번 문서

> 재설계의 출발점. **표준이 실제로 어떻게 생겼는지**를 문헌으로 못박고, 그 위에서 우리 가정을 판정한다.
> 근거: McMahan et al. AISTATS'17 (FedAvg 원 논문) · Bonawitz et al. MLSys'19 (구글 프로덕션 시스템) ·
> Google Research Blog (Gboard) · Hard et al. (Gboard CIFG) · NVFLARE/OpenFL/Flower 문서 · TCP incast 문헌.

---

## 1. 한 라운드의 해부 — 무엇이 어디서 계산되고, 선 위로는 무엇이 지나가나

| 단계 | 어디서 | 무슨 계산 | **선 위로 지나가는 것** | 방향 |
|---|---|---|---|---|
| ① 선발 (Selection) | 서버 | 접속해 온 후보 중 라운드 참여자 선택 | 참여 지시 + 학습 설정(plan) — 수 KB | ↓ |
| ② 배포 (Configuration) | 서버 → 클라이언트 | — | **전역 모델 가중치(체크포인트) 전체** | ↓ |
| ③ 로컬 학습 (Training) | **클라이언트** | **로컬 SGD 수 에폭 — 가중치 갱신은 전부 여기서 계산된다** | 없음 | — |
| ④ 보고 (Reporting) | 클라이언트 → 서버 | — | **학습된 가중치 또는 델타(Δ = 새 가중치 − 받은 가중치)** | ↑ |
| ⑤ 집계 (Aggregation) | **서버** | **표본 수 가중평균 하나** — `W ← Σ (n_i/n) W_i` | 없음 | — |

**핵심 두 줄:**
- **원시 데이터는 절대 이동하지 않는다.** 이동하는 것은 모델(↓)과 모델 갱신(↑)뿐이다.
- **무거운 계산(SGD)은 전부 클라이언트에서, 서버는 평균 하나만 한다.** 서버의 병목은 연산이 아니라 **수신(인입)**이다.

### 올라가는 것의 세부 — FedSGD vs FedAvg vs 실제 프로덕션

| 방식 | 클라이언트가 보내는 것 | 로컬 계산량 | 비고 |
|---|---|---|---|
| FedSGD | **그래디언트** (1스텝) | 1 배치/에폭 | 통신이 너무 잦아 실용 안 됨 |
| **FedAvg (표준)** | **학습된 가중치** (여러 에폭 후) | 수 에폭 | 통신 횟수를 줄인 것이 FedAvg의 발명 자체 |
| 구글 프로덕션 | **델타 + 압축** — 랜덤 회전 + 양자화로 업로드 **최대 100배 축소** | 수 에폭 | 업링크가 다운링크보다 느리다는 걸 전제로 설계 |
| + Secure Aggregation | **마스크를 씌운 델타** — 서버는 개별 갱신을 못 보고 **합만** 복원 | 동일 | 클라이언트 쌍끼리 난수 마스크 교환, 합산 시 상쇄 |

## 2. Cross-device 표준 — 구글 (Bonawitz MLSys'19 + Gboard)

**구조** — 단말 수백만 · Coordinator – Selector – Aggregator 서버 계층.

**접속 방향이 핵심이다: 단말이 먼저 접속한다(check-in).** 서버가 단말을 호출하지 않는다.
단말은 **유휴 + 충전 중 + 비과금 Wi-Fi** 일 때만 접속해 "일 있습니까"라고 묻는다.

| 항목 | 수치 (문헌) |
|---|---|
| 일일 활성 단말 | ~1,000만 대 |
| 라운드당 참여 | 100~500대 (근래 실험은 6,500대까지) |
| 모델 크기 (Gboard CIFG) | 양자화 후 **1.4MB** |
| 수렴까지 | ~3,000라운드 · 클라이언트 150만 · 문장 6억 개 |
| 낙오 처리 | **초과 선발 130%** 후 마감 내 도착분만 집계 |
| 재참여 제한 | 단말당 며칠에 1회 수준으로 제한 |

**네트워크 사실:**
- 단말은 **각자 자기 Wi-Fi/셀룰러**로 접속한다. **단말끼리 공유하는 회선은 없다.**
- 유일한 공유 지점은 **구글 서버 인입**이고, 구글은 **Pace Steering**으로 접속 시각을 분산해 관리한다 — *"동시에 몰리는 것을 피하려고 접속 시각을 무작위화"*.
- 즉 표준의 경합 대응 = ① 접속 시각 분산(무작위) ② 업로드 압축(100배) ③ 초과 선발 + 마감 폐기.

## 3. Cross-silo 표준 — NVFLARE · OpenFL · Flower (병원·기관 연합)

**구조** — 기관 2~수십 곳. 각 기관에 FL 클라이언트(기관 서버, 보통 GPU 보유). 중앙에 집계 서버.

- 연결: **상시 gRPC/TLS**. 기관별 인증서(PKI). 기관 클라이언트가 서버에 연결을 유지하고 작업을 받아 간다.
- 참여: 라운드마다 **전원 또는 대부분 참여**가 흔하다 (cross-device의 극소수 표집과 다름).
- 모델: 의료 영상 등은 **수십~수백 MB** — 페이로드가 크고 라운드가 길다.
- 계산 위치는 동일 — 학습은 각 기관 안에서, 집계는 중앙에서.
- **각 기관은 자기 WAN/인터넷 회선으로 직결된다. 기관 간 회선 공유는 없다.**

## 4. 네트워크 관점 총정리 — 공유 병목은 정확히 어디에 있나

```
[단말/기관] ──자기 회선── ┐
[단말/기관] ──자기 회선── ┼──▶ ★ 집계 서버 인입 ──▶ [서버]
[단말/기관] ──자기 회선── ┘        (유일한 공유 지점)

(계층형일 때만) 한 사이트 안: [클라이언트들] ──공유 LAN/캠퍼스 업링크──▶ [엣지]
```

| 구간 | 공유되나 | 근거 |
|---|---|---|
| 클라이언트 접속 회선 | **아니오** — 각자 것 | 구글·NVFLARE 배치 구조 |
| 사이트 내부 (클라이언트→엣지) | **예** — 그 사이트 안에서만 | HierFAVG 계열, 캠퍼스 업링크 |
| 중간 백본 | 일반적으로 **아니오** (전용망·연구망·슬라이스 같은 특수 배치에서만 예) | 인터넷 경로는 서버 앞까지 분리 |
| **서버 인입** | **예 — 항상.** 모든 갱신이 여기로 모인다 | many-to-one **incast**, 파라미터 서버 병목 문헌 확립 |

업링크 < 다운링크 비대칭도 표준 전제다 — 다운은 같은 모델의 배포(멀티캐스트성), 업은 서로 다른 갱신의 유니캐스트라 **병목은 언제나 올라가는 쪽**이다.

## 5. 우리 가정 판정

| 우리가 깔았던 가정 | 판정 | 무엇으로 |
|---|---|---|
| 라운드 경계 동시 업로드가 경합을 만든다 | **✔ 표준도 인정** | pace steering의 존재 이유 · incast 문헌 · 우리 32배 버스트 실측 |
| 사이트 안(클라이언트→엣지) 회선 공유 | **✔ 성립** | HFL 표준 구조 |
| 초과 선발 + 마감 폐기 | **✔ 표준 그대로** | Bonawitz 130% |
| **엣지→서버가 공유 백본이며 그 몫을 송신측에서 조각낼 수 있다** | **✘ 표준 배치에 없는 전제** | 기관 회선은 독립. 공유는 서버 인입에서 발생. 워터필링은 이 전제 위에서만 의미가 있었다 |
| 워터필링이 시간을 줄인다 | **✘ 이중으로 무너짐** | 전제 붕괴 + work-conserving 하 makespan 불변 (자체 수치 32.0 vs 34.7초) |

**살아남는 자산** — 선별층·커버리지 하드 보장, 초과 선발 구조, HTB 집행 기술, 버스트·incast 실측, FedCS/Oort 비교 체계, 100노드 배포 자동화.
**은퇴하는 것** — 엣지→서버 공유 백본 가정과 그 위의 마감 워터필링.

## 6. 재정의된 문제 문장

> 모든 갱신은 각자의 경로를 지나 **서버 회선 하나로 합류**한다. 경합은 서버 안이 아니라
> **그 회선 앞 — 스위치/게이트웨이의 서버 방향 출력 큐 — 에서** 발생한다(incast).
> 도착 합이 서버 회선 용량을 넘으면 그 버퍼가 넘치고, 손실 → 재전송 → 붕괴로 이어진다.
> 서버 내부 계산(가중평균)은 병목이 아니다. 우리 32배 버스트 실측이 정확히 이 지점이다.
>
> 제어 지점은 둘이다 — ⓐ **큐 집행**: 그 출력 큐에서 순서·비율 (이미 도착한 것을 줄 세움),
> ⓑ **근원 제어**: 클라이언트가 먼저 접속(check-in)하므로 서버가 응답에
> **업로드 시각·순서·참가**를 실어 애초에 몰리지 않게 함. 표준의 pace steering이 ⓑ인데 **무작위**다.
>
> 재정의 — 표준이 무작위로 하는 ⓑ에 정책을 넣고 ⓐ로 뒷받침한다:
> **업로드 시각·순서·참가를 학습 가치·마감·커버리지가 정하게 한다.**

개입 지점이 **운영자 소유의 서버 측**이므로 "경로 중간 소유 불필요"보다 강한 전제이고,
구글이 무작위로 하는 그 자리에 정책을 넣는 것이라 **표준 문헌 위에 정확히 앉는다.**

## 7. 다음 — 죽여야 할 새 가설 (전부 실측으로)

| # | 가설 | 실측 방법 |
|---|---|---|
| N1 | 서버 인입에서 incast형 경합이 실제 FL 트래픽으로 재현된다 | KOREN VM 서버 인입에 N개 실 gRPC 업로드 동시 도착 — 지연·재전송·완료 시각 분포 |
| N2 | 무작위 분산(pace steering 모사) 대비, 가치·마감 인지 스케줄이 마감 내 도착 구성을 바꾼다 | 동일 조건에서 무작위 지터 vs 정책 스케줄 A/B |
| N3 | 수신자 주도 admission(가망 없는 업로드 차단)이 남는 흐름의 완료를 앞당긴다 | work-conserving 큐에서 admission on/off |
| N4 | 커버리지 보장은 인입 스케줄 체계에서도 0회 0대를 유지한다 | 선별층 이식 후 재실험 |
| N5 | 사이트 내부(클라이언트→엣지) 공유 구간의 기존 결과는 재정의와 독립적으로 성립한다 | 기존 LAN 축 결과 재검토 |

**순서: 조사(본 문서) → N1 실측으로 문제 존재 증명 → 그 다음에 설계.** 설계가 먼저 오지 않는다.

### 사후 기록 (2026-08-25) — 이 가설들의 운명

**N1은 FL에서는 사망했다.** 추가 조사 결과 FL 인입은 라운드당 1회·소형 모델·압축·pace steering으로
실문제 실측이 없고(실 5G 테스트베드 논문도 서버 인입을 명시적 비병목 처리), incast '붕괴'는
µs-RTT·얕은 버퍼·동기 플로우라는 DC 3전제가 필요해 WAN에 성립하지 않는다.
→ 재정의 문장(§6)의 "무작위 ⓑ에 정책을 넣는다"는 FL 형태로는 폐기.
**단 분할 학습(SFL)로 승계됐다**: 배치마다 상시 다대일 스트림이라 구조가 다르고, 서버 병목 주장은
문헌에 실재(ParallelSFL MobiCom'24)하나 혼잡 실측이 전무 — N1의 후신이 재설계 3번 문서의
"서버 회선 포화 실측"(관문 ①②)이다. N2·N3은 토큰 admission으로, N4는 폭 하한 p_min으로,
N5는 무관하게 유효한 채로 각각 승계. 상세: docs/04_설계기록/재설계_설계서.md §10, docs/04_설계기록/실증플랫폼_계획.md §2.
