# SuperSFL × AwareNet: 분할 깊이와 KOREN 경로의 공동 결정

> **9/22 우선순위 변경:** 이 문서는 후속 가변 깊이 후보로 보존한다. 현재 구현·검증 방향은 [기기 연산 예산 SFL](문제정의_기기연산예산_SFL_2026-09-22.md)이다. 아래 제안을 현재 학습 런타임의 기능으로 읽지 않는다.

> 상태: **알고리즘과 순수 함수 구현·단위시험 완료, 분할 깊이 가변 학습 프로토콜 및 KOREN 실측 미완료** (2026-09-19). 현행 `widthpath` 실험 결과에 이 알고리즘의 성능을 귀속하지 않는다.

## 1. 선행 연구와 우리의 추가 부분

[SuperSFL v2 (Asif 외, 2026)](https://arxiv.org/html/2601.02092v2)는 하나의 가중치 공유 supernetwork에서 기기마다 다른 **앞부분 깊이**를 학습한다. 자원 기반 초기 깊이, 로컬 분류기와 서버 감독을 합치는 Three-Phase Gradient Fusion(TPGF), 연결 단절 시 로컬 학습, 깊이가 다른 갱신의 층별 집계를 제안한다. 이 연구의 기여를 우리 것으로 쓰지 않는다.

AwareNet의 현행 구현은 **모델 폭, 접속 엣지, 두 출구 분할 전송**을 실측 기반으로 고른다. [코드 지도](../../sfl/ARCHITECTURE.md)와 [결합 정식화](정식화_결합_시스템.md)에 구현 경로가 있다. 그러나 모든 기기의 분할 위치(`cut`)는 실행 인자로 고정되어 있다. 이번 연구의 **주 손잡이는 동적 SFL 분할 깊이**다. 깊이에 따른 연산·활성값 트래픽이 달라질 때, AwareNet의 경로 용량 모형과 SDN 집행층이 그 결정을 지원한다. 기존 폭 조절은 비교군과 안전한 보조 손잡이로 남긴다.

| 구성 | 출처 | 이번 구현 범위 |
|---|---|---|
| 가중치 공유, 가변 prefix 깊이, TPGF, 층별 집계 | SuperSFL | 수식에 맞춘 초기 깊이·기울기 융합·집계 함수 |
| 경로별 물 채우기, 접속 상한, 경로 변경 비용 | AwareNet | 기존 `sfl.plan.effective_rate` 재사용 |
| 깊이별 활성값 크기와 KOREN 경로를 함께 고르는 결정 | 이번 결합 | `sfl/supersfl_net.py`의 `plan_supernet_round` |
| 보유 엣지 OVS의 OpenFlow 집행 | 이번 결합 | OS-Ken 앱과 검증된 정책 내보내기 (`sfl/sdn/`) |

## 2. 라운드 계획 문제

기기 *i*의 후보 분할 깊이 *d*마다 사전 프로브에서 `(연산 초, 왕복 활성값 바이트, 메모리 GB, 검증 손실 대가)`를 잰다. 활성값 크기는 깊이에 따라 반드시 줄지 않으므로 실측 표를 사용한다. 엣지 경로 집합 *Sᵢ*와 해당 경로의 KOREN 실측/설정 용량을 넣어 기존 AwareNet 물 채우기에서 실효 속도 *Rᵢ(S)*를 얻는다.

```text
Tᵢ(d,S) = Cᵢ(d) + 8 Bᵢ(d) / Rᵢ(S)
min d,S  maxᵢ Tᵢ(dᵢ,Sᵢ) + λ · meanᵢ Qᵢ(dᵢ) + δ · 경로변경수
subject to Mᵢ(dᵢ) ≤ 기기 가용 메모리,
           dᵢ ∈ 측정된 prefix 후보, Sᵢ ∈ 허용 경로.
```

*λ*는 초 단위의 품질 대가이고 *Q*는 **실측 검증 손실 또는 보정된 대리지표**여야 한다. 현재 테스트의 예시 값은 성능 근거가 아니다. *δ*는 경로 전환 비용이다. 풀이기는 기기별 깊이·경로 후보를 반복 탐색하는 결정적 휴리스틱이므로 전역 최적을 보장하지 않는다. SuperSFL 식 (1)의 메모리·지연 기반 깊이는 초기 후보로만 쓰며, 최종 깊이는 실제 메모리·바이트·회선 제약으로 다시 판단한다.

SuperSFL의 TPGF 식 (2)~(4)와 층별 집계 식 (5)~(7)을 `fusion_weights`, `fuse_gradients`, `aggregate_prefix_layers`로 구현했다. 로컬 분류기 장애 대체와 서버/기기 간 가변 깊이 파라미터 전송은 아직 현행 `fed_client.py`/`fed_server.py`에 연결되지 않았다.

## 3. 실행 연결 순서

1. `sfl/models.py`의 CNN을 동일한 전체 파라미터 공간의 여러 prefix 깊이로 쪼개고, 깊이별 텐서 모양·파라미터 키 계약을 검증한다.
2. 기기에서 깊이별 연산·최대 메모리·왕복 활성값 바이트를 측정한다. 엣지별 유효 용량은 `sense.py`의 관측을 쓴다. 값마다 실측/설정/추정 태그를 로그에 남긴다.
3. `fed_server.py` 라운드 체크인에 `{depth, route}`를 싣고, 기기가 그 깊이의 prefix를 실행하게 한다. 로컬 분류기와 서버 기울기 응답을 TPGF로 합친다. 연결 장애는 별도 대조군으로 검증한다.
4. 서버는 도착한 prefix 갱신만 해당 층에 집계한다. 우리 엣지 VM의 OVS에 붙은 OS-Ken이 서비스 트래픽의 OpenFlow 경로를 집행한다. 경로 집행이 실패하면 기존 AwareNet처럼 직전 배정을 유지한다. [권한 경계와 전제](../05_KOREN_장비/KOREN_기여_실증전략.md)를 지킨다.
5. 동일 데이터·초기 가중치·연결 조건에서 고정 깊이 SFL, SuperSFL식 정적 깊이, AwareNet 고정 깊이 경로 계획, 결합형을 비교한다. 정확도·목표 정확도 도달 시간·전송 바이트·라운드 꼬리시간·전환 횟수를 보고한다.

## 4. KOREN에서 검증할 것

핵심 가설은 **같은 기기에서도 어느 KOREN 엣지로 보내느냐에 따라 적절한 분할 깊이가 달라진다**는 것이다. 맨 회선의 기기별 전송률, 두 VM 엣지의 혼잡/복구, RTT와 왕복 활성값 바이트를 함께 기록한다. 정적 깊이와 결합 계획기의 깊이·경로 변경을 라운드별로 대조한다. SDN은 **보유 엣지 VM의 OVS/OpenFlow 제어**로 구현하고, 기기↔첫 엣지 구간은 기기의 명시적 엔드포인트 선택으로 연결한다. KOREN 백본 제어권은 전제하지 않는다. [KOREN 실증 전략](../05_KOREN_장비/KOREN_기여_실증전략.md)에 측정·주장 경계를 정리했다.
