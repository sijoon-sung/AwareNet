# awarenet 구현 범위 검사 — 2026-09-19

검사 대상: awarenet 작업 트리. 기존 FjORD 기반 폭 제어와 이번에 추가된 SuperSFL/OS-Ken 초기 구현을 구분한다. 이 문서는 코드·보관 로그 검사 결과이며, KOREN 원격 재실험 결과가 아니다. 실행 코드는 이번 검사에서 수정하지 않았다.

## 먼저 정정할 점

- 기존 시스템에는 폭 제어, 경로 종점 변경, 양방향 조각 전송, 재조립, 라운드별 결합 제어가 실제로 연결되어 있다. 이것들을 새 SuperSFL 계획기의 미연결 상태와 혼동하면 안 된다.
- KOREN 실측 자료가 존재한다. 9월 회선 규모 원자료, 학습 실행 인자·프로파일·라운드 로그와 8대 VM 실행 자료를 확인했다.
- 사용자는 32대 대상 조건을 OOM/CPU 제약 때문에 8대와 tc·노이즈로 축소했다고 설명했다. 이를 실험 의도로 기록한다. 다만 현재 확인한 `scen32` 파일은 clients=32이고 라운드마다 32개 논리 ID가 있으며, 별도 `vmcli` 파일은 clients=8이다. 특정 32→8 대응 실행은 아직 식별하지 못했다. 32개 논리 ID를 물리 장비 32대로 해석하지 않는다.

## 1. SDN 기반 엣지 변경

**기존 구현:** `sfl/policies.py:WidthPath._apply_plan` → `fed_server.endpoints_for` → RSTART의 dp → `fed_client._set_dp` → 기존 조각 연결 flush/close → 새 종점 재연결.

- 실회선은 `sfl/net/real_rig.sh`의 SSH 역터널과 tc로 구성된다. VM 2대의 포트 구간을 논리 엣지 4개로 사용한다.
- 이 경로에서 바뀌는 것은 데이터가 경유하는 종점이다. 서버 연산 모델을 다른 물리 엣지로 이동시키는 기능은 아니다.
- `--path-exec`를 사용하는 별도 집행 경로도 있다. 실회선 `edges` 모드에서는 종점 갱신 분기가 먼저 실행된다.
- 새 `sfl/sdn/osken_controller.py`는 OS-Ken을 사용하지만 기존 정책→실제 학습 트래픽으로 연결한 실행 근거는 확인하지 못했다.

**부족:** 정책 적용 확인, 새 연결 성공 확인 후 확정, 실패 시 이전 설정 복구, 기기 신원과 허용 엣지의 인증된 연결. `allowed` 후보 제한은 정책 제약이며 자체로 인증이 아니다. `_set_dp`는 flush 오류를 무시하고 연결을 닫는다.

**완료 기준:** 학습 중 경로 변경을 요청하고 OpenFlow 오류/Barrier 응답·흐름 통계·실제 출구 바이트를 같은 실행 ID로 확인한다. 실패 시 기존 경로 유지와 중복 학습 방지를 검증한다.

## 2. 다중 경로 분할 전송

**구현됨:** `sfl/mpsend.py`의 ChunkLinks/ChunkPeer/ChunkServer와 `sfl/chunker.py`의 Scheduler.

- 출구마다 TCP 연결을 유지하고, activation과 gradient를 양방향으로 분할한다.
- 출구별 계획 가중치로 조각 몫을 나누고 송신 버퍼 제한으로 배압을 얻는다.
- 완료 ACK를 비동기로 확인하고 라운드 끝에 flush한다. 송신 중 감지한 오류의 해당 조각은 큐로 되돌린다.
- `fed_client._send_act`, `fed_server`의 `chunks.wait/send_back`에 연결되어 있다.

**부족:** 서로 다른 종점이 물리적으로 독립된 회선을 뜻하지는 않는다. SSH 터널과 HPC 출구의 공유 병목을 포함해야 한다. `sendall` 성공 뒤 연결이 끊겨 수신되지 않은 조각을 찾는 조각별 수신 확인·재전송은 확인되지 않았다. 다음 전송의 재접속과 진행 중 전송의 복구를 구분해야 한다.

**완료 기준:** 동일 자원에서 단일 경로/균등 분할/가중 분할을 비교하고, 지연·비대칭·전송 중 단절에서 완료 시간과 원본 바이트 일치를 확인한다.

## 3. 분할 후 결합

### 3-A. 전송 바이트 재조립

`Reassembler`는 tid별 버퍼, seq 중복 제거, off 기반 배치, fin 후 대기로 정상 송신 조각을 복원한다. 기존 시험에서 순서 뒤바뀜·중복·fin 선도착·전송 분리 검사가 통과했다.

**이번에 재현한 결함:** 서로 다른 seq가 같은 바이트 구간을 덮어쓰면 길이 합만으로 완료를 인정한다.

```python
r = Reassembler()
r.feed(dict(tid='x', seq=0, off=0, ln=2, total=4), b'ab')
r.feed(dict(tid='x', seq=1, off=0, ln=2, total=4), b'cd')
r.feed(dict(tid='x', total=4, fin=1))  # (True, 4)
r.pop('x')                          # b'cd\x00\x00'
```

정상 `split()` 출력으로 발생한다고 확인한 것은 아니다. 잘못된 메타데이터를 수신했을 때 무결성을 보장하지 못하는 결함이다. 음수 범위·total 일관성·중복 seq의 내용 충돌·전송 크기 상한·미완성 버퍼 만료도 함께 검증해야 한다.

### 3-B. 학습 gradient 결합

전송 바이트 분할과 `--micro`로 배치를 나누는 연산 분할은 별개다.

**정적 코드에서 확인한 이중 스케일링:** `fed_server.micro_step`은 `(loss/of).backward()`로 activation gradient도 1/of로 만든다. 서버는 그 `act.grad`를 전송한다. `fed_client._batch_micro`는 이를 다시 `/m`으로 나누어 역전파한다. 동일 크기 m개 조각에서 클라이언트 gradient는 의도한 배치 평균보다 추가로 1/m 작아진다. m=4이면 의도값의 1/4이다. 기존 `test_micro_srv.py`는 서버 파라미터를 확인하며 이 클라이언트 경로를 포함하지 않는다.

이번 환경에 torch가 없어 수치적 종단 시험은 실행하지 못했다. 확인한 scen32 및 vmcli 인자에서는 micro=1이므로 그 실행의 정확도 저하를 이 결함으로 설명할 수 없다. 불균등 조각에서는 1/m 대신 표본 수 가중도 검토해야 한다.

**완료 기준:** 정규화·확률 연산을 통제한 작은 모델에서 단일 배치와 분할 배치의 양쪽 gradient/업데이트를 비교하고, 이후 BN과 여러 클라이언트의 실행 순서 영향을 별도로 측정한다.

## 4. 폭 제어 시스템과 알고리즘

**구현됨:** `models.py`의 앞 채널 슬라이스 및 `nested_average`, `fed_server.Aggregator`, 라운드별 RSTART 폭 전달, `plan.width_stage/opt_widths`.

- 실제 참여한 파라미터 위치만 표본 수로 가중 평균한다.
- 시간 모델은 폭에 따른 연산 지수와 전송량 변화를 사용한다.
- opt 모드는 시간과 평균 폭 감소의 가중 비용을 비교한다. 폭 감소 항은 측정 정확도 자체가 아니다.
- 기존 `opt_widths`에는 근접 동률 병목들을 함께 낮추는 처리가 있다. 앞선 새 SuperSFL 계획기의 동률 정체 문제를 이 기존 알고리즘의 결함으로 전가하지 않는다.

**정확도 조사 우선순위:**

1. `Aggregator.aggregate`는 사용 폭 종류가 둘 이상일 때만 서버 폭별 모델들을 동기화한다. 한동안 한 폭만 학습하다 다른 폭으로 전환하면 캐시된 다른 폭 뒷단에 최신 업데이트가 반영되지 않는 구간이 생길 수 있다. 앞단은 매 라운드 집계되므로 앞/뒤 상태의 정합성을 시험해야 한다.
2. 기본 BN 이동 통계를 폭 간 평균한다. 코드와 과거 조사 문서에도 위험이 기록되어 있다. 폭별 통계, 평가 전 재보정 등과 비교해야 한다.
3. 클라이언트 SGD는 라운드마다 생성되고, 서버는 폭별 optimizer를 유지한다. 파라미터 동기화 때 momentum을 어떻게 취급할지 명시해야 한다.
4. 평가는 역사적으로 학습된 최대 폭을 선택한다. 조건별 평가 폭과 업데이트 횟수가 같지 않으면 정확도 비교가 뒤섞인다.
5. `baselines/baseline_fjord.py`는 명시적으로 w/o KD이며, 폭 표집도 배치별이 아니라 라운드별이다. FjORD 전체 재현 결과로 표현하면 안 된다.

근거: [FjORD 원문](https://arxiv.org/abs/2102.13451). 폭 제어의 설계 근거는 타당하지만 현재 SFL 이식 구현의 정확도 문제와 원 논문의 한계를 분리한다.

**완료 기준:** 고정폭 단독 학습 → 고정폭 SFL → 혼합폭 SFL → 동적폭 SFL 순서로 검증한다. 각 폭의 평가 정확도, 실제 업데이트 수, 정규화 상태, 전체 학습량을 함께 기록한다.

## 5. 유동적 결합

**이미 연결됨:** 측정 Sensor → 현재 폭으로 경로 결정 → 폭 선택 → 종점/분할 비율 집행 → 다음 라운드 재측정. 용량 추정이 5% 이상 바뀐 라운드에는 폭을 유지하고 경로 대응을 먼저 한다.

**부족:**

- Sensor.observe는 네트워크 관측을 갱신하지만 CPU 프로파일은 고정으로 취급한다. 시작부터 느린 기기 실험과 실행 중 CPU 부하가 바뀌는 실험은 다르다.
- 경로 집행 실패 시 경로는 되돌려도 실패한 목표 경로에 맞춰 구한 폭을 그대로 적용할 수 있다.
- 경로 최적화에는 관측 용량을 쓰지만 분할 가중치는 정적 용량을 쓴다. 코드에 추정 피드백 진동 방지라는 이유가 명시되어 있다. 이는 알려진 절충이며, 지속적인 출구 용량 변화에 최적인 분할을 보장하지 않는다.
- 실측 xfer는 라운드 시간에서 클라이언트 연산을 뺀 값이라 서버 대기 등도 섞인다. 이를 순수 망 시간으로 해석하지 않는다.
- OS-Ken 및 새 SuperSFL 깊이 계획기는 기존 폐루프와 아직 별개다.

**완료 기준:** 동일 자원으로 경로만/분할만/폭만/결합 절제를 수행하고, 망·CPU·서버 부하를 각각 변경한다. 결정값·실제 적용값·반응 시간·변경 비용을 연결한다.

## SHRiNK 및 규모 해석

### 사용자 제공 최종 페이지 대조

[AwareNet 최종 실험 결과](https://claude.ai/artifact/9xrQS2YZkkQJA4HjHFdvtm)를 브라우저에서 직접 읽었다. 생성기는 `scripts/analysis/final_results_page.py`이다. 페이지는 다음을 별도 실험으로 설명하며 현재 저장소의 인자·로그와 일치한다.

- 32대 시나리오: 논리 클라이언트 32, 엣지마다 8개로 시작, 접속 대역폭 50/20→5/2로 0.1배 축소, 엣지 용량 56×4, CPU 스레드 1, 24라운드·3시드. 인위 지연은 없음이라고 명시한다.
- 8대 결합: 느린 2·회선 약한 2·정상 4, CPU 스레드 2, 목표 10초, 24라운드·3시드.
- 8대 λ 스윕: 200라운드·2시드.
- VM 배치: VM1/VM2에 클라이언트 프로세스 4개씩, 서버 HPC, 1시드.

따라서 해당 페이지는 32→8을 같은 실행의 전후라고 설명하지 않는다. 사용자의 OOM/CPU 제약 설명은 보존하되, 이 페이지를 근거로 동일 실행의 변환이라고 확정하지 않는다. 페이지는 iperf 원파일 미보존 및 초기 상한 측정 원파일 덮어쓰기 사실도 명시한다.

원자료에서 앞 4라운드를 제외하고 3시드의 평균 라운드 시간을 다시 계산했다. 정상 63.19→47.64초, 몰림 109.51→62.87초, 연산 느림 79.12→47.26초, 용량 변동 72.97→53.48초로 페이지의 반올림 수치와 일치한다. 이는 시간 수치 확인이며 정확도나 각 구성요소의 인과 효과까지 입증하는 검사는 아니다.

추가 표기 오류: 페이지의 회선 열은 5/2를 '올리기/내리기'로 적지만, `real_rig.sh`의 `aA/aB`는 **출구 A/B 상한**이며 양방향에 적용된다. 후속 제출 문서에서 고쳐야 한다.

[기존 부하비율 설계](설계_KOREN_부하비율.md) §6에는 실측 조건을 4~8대 리그로 축소하고 부하비 ρ를 보존한다는 의도가 있다. [scen32 조건](../02_실험/실험_시나리오_32대_사전등록.md)에는 50/20→5/2 Mbps, 엣지 56 Mbps×4, 스레드 1, 정해진 라운드의 용량 교란이 기록되어 있다. 이는 사용자가 말한 축소 실험의 근거이며 결함 자체가 아니다.

다만 인원 축소, 대역폭 축소, 물리 호스트 수, 논리 학습 참여자 수를 각각 기록해야 한다. 현재 확인한 32 조건의 0.1배 대역폭 축소와 별도 8대 VM 실행을 자동으로 같은 실행으로 간주하지 않는다. OOM/CPU로 정확히 32→8 전환한 실행 기록과 무작위 노이즈의 분포·시드는 이번 검색에서 연결하지 못했다. 확인한 시나리오 드라이버는 정해진 라운드별 용량 변경이다.

[SHRiNK 원문](https://web.stanford.edu/~balaji/papers/03shrinkaCONF.pdf)은 흐름 표본화와 링크·버퍼·큐 관리 매개변수의 적절한 축소를 다룬다. 같은 ρ만으로 학습 수렴·CPU 경합·GPU 메모리까지 보존된다고 확대 해석하지 않는다. 네트워크 재현과 학습 정확도 검증을 분리하면 기존 실측 자료를 더 정확히 활용할 수 있다.
