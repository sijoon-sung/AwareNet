# 다중 경로가 있다면 SDN이 개선할 수 있나 — 고민 노트 (6번 문서)

> ⚠ **범위 확인 — 이 과제는 망을 통제하는 과제가 아니다.**
> 망은 ① 관측 대상 ② 실증 무대이고, 통제는 '바깥 트래픽에서 학습 몫 지키기' 하나뿐이다.
> 아래는 **"만약 경로가 여럿이면"이라는 가정 위의 고민**이지 계획이 아니다. (7번 문서 참조)
>
> ⚠ **고민 노트다. 지금 하지 않는다.** 우선순위는 여전히 우리 가설(폭 p 컨트롤러) 검증이다.
> 다만 "만약 경로가 여럿이면 SDN이 뭘 할 수 있나"는 답할 가치가 있는 질문이라 원리로 답한다.

---

## 1. 핵심 — 왜 단일 경로에서는 죽고 다중 경로에서는 살아나는가

배분층이 죽은 이유를 다시 정확히 쓰면 이렇다:

```
단일 경로:  makespan ≥ 총 바이트 / C
            ★ 그리고 TCP(work-conserving)가 **가만 둬도 이 하한에 닿는다**
            → 우리가 개입할 여지가 없다. 나눠봐야 이미 최적인 것을 흔들 뿐
```

**여기가 진짜 이유다.** 하한이 있다는 것만으로는 개입이 무의미하지 않다.
**기본 동작이 이미 하한에 닿기 때문에** 무의미했던 것이다.

그런데 경로가 여럿이면 이 성질이 깨진다:

```
다중 경로:  makespan ≥ 총 바이트 / (C₁ + C₂ + ...)
            ★ 그런데 TCP는 **가만 두면 이 하한에 못 닿는다**
              — 흐름 하나는 경로 하나만 쓴다. 나머지 경로는 논다
            → **기본 동작과 하한 사이에 틈이 생긴다. 그 틈이 개입의 자리다.**
```

| | 단일 경로 | 다중 경로 |
|---|---|---|
| 하한 | 총바이트 / C | 총바이트 / ΣC |
| **가만 두면 하한에 닿나** | **닿는다** (TCP가 알아서) | **안 닿는다** (흐름은 경로 하나만) |
| 개입 여지 | **없음** ← 배분층 사망 원인 | **있음** ← SDN의 자리 |

> **한 줄**: work-conserving은 **한 회선 안에서만** 최적을 보장한다.
> **경로들 사이에서는 아무것도 보장하지 않는다.**

## 2. 그래서 SDN이 할 수 있는 일 셋

### ① 경로 배정 — 누가 어느 길로 가나 (매칭 문제)

경로가 K개, 클라가 N명이면 **누구를 어디에 태우는지가 결정 변수**다.
그리고 **배정에 따라 makespan이 크게 달라진다** — 단일 회선의 재분배와 결정적으로 다른 점이다.

간단한 예 (경로 100M·20M, 클라 2명, 각 50MB):

| 배정 | 계산 | makespan |
|---|---|---|
| 둘 다 100M 경로 | 각자 50M씩 나눠 씀 → 50MB/50M = 8초 | **8초** |
| 하나씩 나눠 태움 | max(50MB/100M, 50MB/20M) = max(4초, 20초) | **20초** |

**같은 자원인데 배정에 따라 2.5배 차이가 난다.** 단일 회선에서는 이런 일이 없었다
(어떻게 나눠도 총량이 같으니 makespan이 같았다). **경로 배정은 재분배가 아니라 매칭이다.**

### ② 경로 분할 — 한 클라의 흐름을 여러 경로에 나눠 태우기

한 클라가 여러 경로를 동시에 쓰면 그 클라의 실효 용량이 커진다.

- 필요한 것: MPTCP(엔드포인트) **또는** 망 안에서의 흐름 분할(SDN)
- ⚠ 경로마다 지연이 다르면 **재조립 비용**이 든다 (늦게 온 조각을 기다림).
  문헌상 이 비용이 이득을 갉아먹는 경우가 흔하다 → **80% 규칙**(합계의 80% 못 내면 폐기)

### ③ 경로 상태 보고 — 컨트롤러의 새 입력

SDN 컨트롤러는 경로별 부하를 안다. 그게 우리 관측 루프의 새 입력이 된다.
**우리 컨트롤러 구조가 이미 그 모양이다** — 관측 → 결정 → 집행에서 관측 항목이 하나 느는 것뿐.

## 3. 가장 흥미로운 것 — 폭과 경로를 **같이** 정하는 문제

여기가 이 고민의 진짜 결론이다. 두 노브가 **상호작용**한다:

```
느린 경로에 탄 클라  →  좁혀야 한다 (폭↓)
그 클라를 빠른 경로로 옮기면  →  좁힐 필요가 없어진다 (폭 유지 = 학습 보존)
```

즉 **경로를 잘 배정하면 폭을 덜 깎아도 된다.** 폭을 깎는 것은 학습 손실이므로,
**경로 배정은 학습 손실을 줄이는 수단**이 된다. 두 노브가 같은 목적함수 안에서 만난다:

```
minimize  makespan(폭 벡터, 경로 배정)
subject to  폭 ≥ p_min           (배제 없는 학습)
            경로 용량 제약
maximize  Σ 폭                    (학습 보존)
```

- **폭만 있을 때**: 느린 클라는 좁히는 수밖에 없다 → 학습 손실 감수
- **경로가 더해지면**: 먼저 옮겨보고, 그래도 안 되면 좁힌다 → **손실을 덜 낸다**

이 조합(**폭 × 경로 공동 최적화**)은 조사 범위에서 선례를 못 찾았다.
SmartFLow는 경로만, FjORD/HSF는 폭만 다룬다. 다만 **"못 찾았다"는 "없다"가 아니다** —
주장하려면 별도 조사가 필요하다.

## 4. 현실 점검 — 우리가 지금 할 수 있는 것과 없는 것

| 필요한 것 | 상태 |
|---|---|
| KOREN에 실제로 경로가 둘 이상 있나 | **모른다.** 확인 필요 |
| 경로를 고를 권한 (SDN 컨트롤러 접근) | **없다.** 못 받았다 |
| 우리가 망을 만들기 | **범위 밖** |
| **알고리즘을 로컬에서 시험하기** | **된다** ← 아래 |

**핵심: 알고리즘 검증에는 KOREN이 필요 없다.**
우리는 이미 루프백에 클라별 회선을 HTB 클래스로 만들고 있다.
**경로도 같은 방법으로 만들 수 있다** — 클라마다 경로 후보를 두 개 두고,
컨트롤러가 어느 쪽에 붙일지 정하게 하면 된다. 실제 라우팅이 아니라 **주소를 바꿔 접속**하는 것이지만,
**배정 알고리즘의 이득을 재는 데는 충분하다.**

| 무엇을 주장할 수 있나 | 무엇을 주장할 수 없나 |
|---|---|
| "경로 배정 알고리즘이 makespan을 X% 줄인다" | "KOREN에서 실증했다" |
| "폭만 쓸 때보다 학습 손실이 적다" | "실제 SDN 컨트롤러로 집행했다" |

## 5. 만약 한다면 — 사전 등록 실험

| # | 실험 | 판정 |
|---|---|---|
| M1 | **경로 배정 이득 (에뮬)** — 경로 2개 × 클라 4대, 무작위 배정 vs 컨트롤러 배정 | makespan **15% 이상** 개선 없으면 폐기 |
| M2 | **폭 손실 절감** — 경로를 쓸 때 평균 폭이 얼마나 덜 깎이나 | 평균 폭이 **유의미하게** 안 오르면 ①만 남기고 폐기 |
| M3 | 경로 분할(한 클라가 두 경로) | 합계 용량의 **80%** 못 내면 폐기 (재조립 비용) |
| M4 | (KOREN 권한이 열리면) 실경로 확인 | 경로가 하나면 M1~M3의 주장을 **에뮬 한정**으로 명시 |

**우선순위: 낮다.** 조건 4·5(기기 8대·진짜 모델)가 먼저다.
이건 그 뒤에 여유가 있을 때, 그리고 **KOREN 권한이 열릴 가능성이 보일 때** 착수한다.

## 한 문단 요약

배분층이 죽은 진짜 이유는 "하한이 있어서"가 아니라 **"TCP가 가만 둬도 그 하한에 닿아서"**다.
경로가 여럿이면 이 성질이 깨진다 — **흐름 하나는 경로 하나만 쓰므로 나머지 경로가 논다.**
기본 동작과 하한 사이에 틈이 생기고, **그 틈이 SDN의 자리**다.
할 수 있는 일은 셋 — 경로 배정(매칭) · 경로 분할 · 경로 상태 보고.
가장 흥미로운 것은 **폭과 경로를 같이 정하는 것**이다:
경로를 잘 배정하면 폭을 덜 깎아도 되므로 **학습 손실이 줄어든다.**
그리고 **알고리즘 검증에는 KOREN이 필요 없다** — 로컬에서 경로를 에뮬레이션할 수 있다.
다만 "실증했다"고는 못 하고 "알고리즘이 이만큼 낫다"까지만 말할 수 있다.
