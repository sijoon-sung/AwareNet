# AwareNet 방향 정리: 지연 원인을 구분하는 SFL 기기 연산 예산 제어

> **같은 날 후속 요청 반영:** 이 정책은 폭 제어 대조군으로 보존한다. 전체 과제의 현재 방향은 [네트워크 중심 아키텍처·경로 주장](네트워크중심_아키텍처_및_경로주장_2026-09-22.md)이다. PyTorch/CUDA 설치와 실제 텐서 집계 검증도 후속 작업에서 완료했다.

작성: 2026-09-22 · 기준 브랜치: `awarenet` · 상태: **실험용 정책을 런타임에 연결, 새 학습·KOREN 성능 검증 전**

## 1. 선택한 문제

**접속망이 변하는 SFL에서, 통신 대기를 기기 연산 부담으로 오인해 모델 폭을 과도하게 줄이는 문제에 집중한다. 기기의 연산 시간 예산을 만족하는 큰 폭을 먼저 고르고, 그 폭에서 허용된 엣지 종점을 배정한다.**

대상은 고정 분할점에서 동기식으로 학습하는 이질적 기기다. 각 기기는 일반 소켓으로 서버가 등록한 엣지 종점에 연결한다. Wi-Fi·이동통신·ISP 내부의 라우터를 과제 운영자가 제어한다고 가정하지 않는다. 이번 구현의 예산은 라운드당 기기 순·역전파 경과 시간이다. CPU 사용률, 에너지, 메모리 상한을 강제로 보장하는 기능은 아니다.

제출 제목 제안: **“접속망 변동 환경에서 기기 연산 예산을 고려하는 분할 연합학습 제어”**.

### 기존 설명이 약했던 이유

| 기존 설명·가정 | 문제 | 이번 기준 |
|---|---|---|
| 연합학습에 최적화된 네트워크 | 학습 목적과 일반 부하 분산의 차이가 불명확 | 기기별 연산 예산 위반과 불필요한 폭 축소를 측정 |
| 늦은 기기의 폭을 줄이면 된다 | 늦은 원인이 전송·서버 대기일 수 있음 | 기기 순·역전파 계측만 폭 축소 판단에 사용 |
| 두 연결이면 두 회선의 용량을 합산 | 같은 Wi-Fi/ISP 병목을 공유할 수 있음 | 공유 접속망 기본값, 독립 회선은 명시적 실험 조건 |
| SDN으로 기기–엣지 경로를 선택 | 무선 접속망·외부 라우터에 제어 권한이 없음 | 앱의 종점 선택과 보유 게이트웨이의 제어 권한을 구분 |
| 폭을 보존하면 정확도가 좋아진다 | 폭은 학습 품질의 대리변수일 뿐 | 같은 평가 모델의 정확도·목표 정확도 도달 시간을 측정 |
| FjORD를 FedRolex로 교체하면 기여가 생긴다 | 모델 추출 방식 변경은 문제 정의를 만들지 못함 | 원인 구분·제어 범위·실제 효과를 먼저 검증 |

**현재 자료만으로 “FL 전반에 최적화된 네트워크”라는 주장은 성립하지 않는다.** 현재 구현은 SFL의 배치별 activation/gradient 왕복, 폭에 따른 바이트 변화, 라운드 동기화를 활용하는 스케줄러다. 이러한 학습 정보를 쓰는 이득은 같은 자원 조건의 일반적인 종점 분산과 비교해야 한다.

## 2. 기존 자료가 주는 근거와 반례

아래는 새 정책의 결과가 아니라 **기존 원자료의 시간 구성 재검토**다. 시드 1, 라운드 번호 4~23, 실행별 20라운드의 기록을 사용했다. 기기 연산 비중은 `Σ(cli_fwd+cli_bwd) / Σ(t_round)`이며 라운드 임계경로 비중과 다르다.

| 보관 실행 | 평균 라운드 | 평균 폭 | 축소된 기기·라운드 / 전체 | 기기 연산 비중 |
|---|---:|---:|---:|---:|
| r8mix rho1 / width3 | 9.364초 | 0.5344 | 160 / 160 | 15.51% |
| r8mix rho1 / bothmp | 10.322초 | 0.9406 | 20 / 160 | 36.38% |
| scen32 normal / bothmp | 47.345초 | 1.0000 | 0 / 640 | 7.86% |
| scen32 slow / bothmp | 47.291초 | 0.9688 | 80 / 640 | 10.48% |

원자료: [8대 폭만](../../out/wp_r8mix_rho1_s1_width3_widthpath.jsonl), [8대 결합](../../out/wp_r8mix_rho1_s1_bothmp_widthpath.jsonl), [32개 논리 참여자 정상](../../out/wp_scen32_normal_s1_bothmp_widthpath.jsonl), [32개 논리 참여자 연산 느림](../../out/wp_scen32_slow_s1_bothmp_widthpath.jsonl). 재계산: [device_budget_report.py](../../scripts/analysis/device_budget_report.py).

해석은 다음 범위로 제한한다.

- 8대 결합 실행은 폭을 크게 유지하지만 평균 시간이 10초 목표를 넘는다. “같은 목표를 만족하면서 정확도까지 향상”했다고 쓰지 않는다.
- 이미 폭을 줄인 뒤의 연산 시간이다. 낮은 연산 비중만으로 이전 축소가 불필요했다고 역추론할 수 없다. 전폭 프로파일과 같은 부하의 대조군이 필요하다.
- `width3`와 `bothmp`는 사용하는 출구도 다르다. 위 차이는 시스템 구성의 차이이며 순수 계획기 효과가 아니다.
- 이 네 실행에서 기록된 서버 연산·락 대기의 합은 `xfer`의 약 0.12~0.74%다. 서버 대기를 제외하는 계측 수정은 의미상 필요하지만, **기존 정확도 문제의 주원인으로 입증된 것은 아니다.**
- 오래된 `xfer`에는 서버 시간이 포함된다. GPU 비동기 타이밍과 합성 `--speed` 지연의 영향도 있어 이를 순수 물리 연산 시간으로 부르지 않는다.

전체 3시드의 기존 성과, 물리 장비와 논리 참여자, 32→8 축소 해석은 [기존 성과 보고서](../01_제출발표/기존성과_근거보고서_및_비판검토_2026-09-19.md)에 정리했다. 새 설명을 위해 보관 로그나 기존 조건을 바꾸지 않았다.

## 3. 제어 범위와 SDN의 위치

```mermaid
flowchart LR
    D[기기 앱: 모델 폭·소켓 종점 선택] --> A[Wi-Fi·셀룰러·ISP: 관측 대상]
    A --> E[허용된 KOREN VM·게이트웨이]
    E --> S[학습 서버: 모델 뒷부분·집계]
    C[라운드 정책] --> D
    C -. 보유 OVS에서만 가능한 후속 연결 .-> E
```

| 구간·주체 | 실행 가능한 일 | 권한·현황 |
|---|---|---|
| 기기 앱 | 폭 변경, 등록 종점으로 TCP 연결 | 일반 사용자 소켓. 런타임 기기에 tc/root를 요구하지 않음 |
| Wi-Fi·셀룰러·외부 라우터 | 지연·처리량 관측 | 경로 설치·대역폭 예약을 가정하지 않음 |
| 보유 KOREN VM·게이트웨이 | 리그 tc·터널 사전 구성, OVS 설치 가능 시 흐름 제어 | 관리 권한은 운영자 영역. KOREN 백본 권한과 다름 |
| 현재 학습 런타임 | 허용 종점 변경·조각 전송 | `--edges`, 기기별 `--edge-groups`. **앱 수준 종점 배정** |
| OS-Ken 코드 | 보유 OVS 대상 OpenFlow 1.3 프로토타입 | [SDN 코드](../../sfl/sdn/README.md), 런타임 연결·실 OVS 검증 전 |

**권한 문제의 해결 범위:** 기기가 남의 라우터를 제어해야 한다는 배포 전제를 제거하고, 제어 요청을 운영자가 등록한 종점으로 제한했다. 새 모드는 모든 기기에 허용 목록이 없으면 실행을 거부한다. 이는 종점 선택 범위 검사이며, 클라이언트 신원 인증이나 통신 암호화를 제공하지 않는다. 현재 HELLO의 ID만으로 다중 사용자 보안을 보장할 수 없다. 외부 기기 공개 서비스화에는 인증된 채널, ID–권한 결합, 적용 ACK·타임아웃·복구가 추가로 필요하다.

같은 데이터가 두 소켓을 지나도 독립된 물리 경로를 쓴다는 뜻은 아니다. 공유 접속망 기본 모드에서는 두 단독 프로브의 최대값을 **합산하지 않은 접속 용량 대리값**으로 쓴다. 이것도 가용 대역폭 보장이 아니다. 독립 모드는 실제 NIC·회선 독립성과 교란 응답을 따로 확인한 경우에만 사용한다.

## 4. 이번에 구현한 정책

실행 선택: `--policy widthpath --planner device-budget`.

기기 k의 폭 w에서 라운드 연산 시간 예측은 다음과 같다.

```text
C_k(w) = 배치 수 × 전폭 배치 연산 추정값_k × w^gamma_k
w*_k   = {허용 폭 중 C_k(w) ≤ 연산 예산_k인 가장 큰 폭}
```

이번 CLI는 모든 기기에 같은 `--compute-budget-s`를 적용한다. 순수 계획 함수는 기기별 예산 사전을 받지만 기기별 SLA 입력 UI는 추가하지 않았다. 예산은 허용 가능한 학습 점유 시간에서 정하고 실험 전에 고정해야 한다. 좋은 결과를 내는 숫자를 사후 선택하면 안 된다.

1. **인지:** 사전 진단으로 시작하고, 이후 `cli_fwd+cli_bwd`를 실제 적용 폭으로 정규화해 매 라운드 연산 추정을 갱신한다. 최근 3회 중앙값과 최신값 중 큰 값을 사용해 부하 증가는 즉시 반영한다. gamma 기본값 1.2는 모형 가정이며 폭별 추가 프로파일링 대상이다.
2. **폭:** 예산 안의 가장 큰 사다리 폭을 선택한다. 부하 증가에는 필요한 단계까지 줄이고, 회복 시에는 두 번 연속 가능할 때 한 단계 올린다. 계측 누락 때 복귀하지 않는다. 최소 폭도 예산을 넘으면 `infeasible`을 기록한다.
3. **경로:** 선택한 폭을 고정하고, 기기별 허용 종점 안에서 예상 라운드 최댓값을 낮추는 제한된 탐욕 탐색을 한다. 최댓값이 같은 경우 총시간 감소를 허용한다. 이동 기기 수 상한·전환 시간·5% 이득 문턱을 적용한다. 전역 최적해를 보장하지 않는다.
4. **접속망:** 기본 `shared`는 동일 접속망의 총 상한을 둔다. `independent`는 두 회선 값을 별도로 사용하며 `--multipath`가 필요하다. 기존 양방향 분할·재조립을 재사용한다.
5. **계측:** 새 모드만 서버 연산·락 대기를 뺀 잔여 시간을 Sensor에 전달한다. 여전히 직렬화·제어 오버헤드가 남는다. 원래 `per_client_detail.xfer` 값은 보존한다. 연산·통신 겹침의 영향을 피하기 위해 새 모드는 `pipeline off / micro 1 / stagger off`를 요구한다.
6. **감사 기록:** `budget_decision`은 결정 전 예측, `budget_outcome`은 끝난 라운드의 실제 예산 위반·예측 오차다. 종점 상태는 `endpoint_requested`로 기록한다. 이를 OpenFlow 설치 확인이라고 표시하지 않는다.

`--deadline-s`는 새 모드에서 **전체 라운드 목표와 위반 진단**이다. 통신 문제 때문에 이 값을 넘겼다고 자동으로 폭을 축소하지 않는다. 따라서 네트워크가 심하게 나빠지면 기존 시간 우선 정책보다 느릴 수 있다. 이것은 숨길 결과가 아니라 실험에서 측정할 비용이다.

이 구현은 **기기 예산 제약을 먼저 만족시키고 경로를 고르는 단계적 제어**다. 폭·경로·정확도를 동시에 최적화한 수학적 해라고 주장하지 않는다. 네트워크 상태가 폭에 다시 영향을 주는 정책은 향후 별도 가설로 비교한다.

**집계 결함 수정 이유:** 기존 `Aggregator.aggregate`는 한 라운드에 두 폭 이상이 학습됐을 때만 캐시를 동기화했다. 한 폭만 학습한 뒤 다른 폭으로 돌아가면 예전 서버 상태를 사용할 수 있었다. 이제 학습된 폭이 하나라도 있으면 전역 뒷부분과 캐시를 갱신한다. 이 수정은 기존 계획기에도 적용되며, 이후 재실험 결과는 이전 커밋의 결과와 구분해야 한다.

이것만으로 FjORD 계열의 정확도 문제를 해결했다고 단정하지 않는다. 폭별 옵티마이저 이력, BN 통계, 최대 학습 폭으로 바뀌는 평가 기준, 마이크로배치 기울기 배율 등은 [구현 검사](구현범위_검사_2026-09-19.md)의 남은 검증 항목이다. 새 모드의 `micro=1`은 마이크로배치 문제를 사용 범위 밖에 둔다. 메모리 예산과 OOM 대응은 구현하지 않았다.

|---|---|---|
| 기기 연산 부하만 증가 | 해당 기기 폭 감소, 연산 예산 위반 감소 | 다른 정상 기기의 폭까지 감소하거나 위반 지속 |
| 접속 회선만 악화 | 폭 유지, 허용 종점 조정 또는 목표 시간 초과를 명시 | 통신 악화만으로 폭 감소, 공유 회선의 허위 용량 증가 |
| 서버 대기만 증가 | 기기 폭 유지, 서버 시간 증가 기록 | 서버 대기를 기기 부하로 판단 |
| 부하 증가 후 회복 | 계측 갱신 후 단계적으로 폭 복원 | 오래된 프로파일·서버 캐시로 복구 실패 |

### 최소 비교 구성

같은 8개 논리 참여자, 같은 데이터 분할·시드·모델·정규화·분할점·배치 수·활성 회선·교란에서 비교한다.

- 기존 시간 목표 정책: `planner=plan, deadline=fixed`.
- 새 연산 예산 정책 + 고정 종점: `planner=device-budget, max-moves=0`.
- 새 연산 예산 정책 + 종점 조정: `planner=device-budget, max-moves=1`.
- 전폭 기준선은 학습 품질의 기준으로 함께 둔다. 예산을 못 맞추면 그 사실을 기록한다.

한 연결 기준선과 두 독립 회선 제안의 차이를 계획기 성능이라고 부르지 않는다. 다중 경로를 비교할 때도 **이용 가능한 회선 용량은 모든 팔에 동일하게 제공**한다. 공유 접속망 실험은 NIC/클래스 하나의 합산 상한이 실제 적용되는지 리그에서 먼저 검증해야 한다. 소프트웨어 예측 상한만 바꿔서는 물리 실험 조건이 바뀌지 않는다.

우선 보고할 지표는 ① 실제 기기 연산 예산 초과율, ② 통신만 교란했을 때의 폭 축소 횟수, ③ 라운드 p50/p95·목표 초과율, ④ 같은 평가 모델의 정확도와 목표 정확도 도달 시간, ⑤ 이동 횟수·실패·바이트다. 평균 폭은 보조 지표다. 최소 두 시드는 방향 확인용이며 일반화 주장의 충분한 증거가 아니다. 가능하면 기존처럼 세 시드를 유지한다.

연산 예산·시간 목표·정확도 목표·회선 조건은 기존 [조건 원장](../../scripts/exp/conditions.json)과 별도 새 조건으로 사전등록한다. 이 문서의 예시 수치를 측정된 최적값으로 넣지 않는다. 기존 최종 실험 조건을 새 정책에 맞춰 덮어쓰지 않는다.

### 실행 옵션 예시

아래는 **기존 리그와 클라이언트가 준비된 환경의 서버 옵션 예시**다. 예산 4초·목표 10초는 사용법 설명용이며 권장 실험값이 아니다. 종점·허용 그룹·용량은 실제 리그 설정으로 지정한다.

```bash
python sfl/fed_server.py \
  --policy widthpath --planner device-budget \
  --clients 8 --batches 4 --cut 2 --preflight --solo \
  --compute-budget-s 4 --deadline-s 10 \
  --access-mode shared --max-moves 1 --ladder 0.5,0.75,1.0 \
  --edges "$EDGES" --paths "$CAPS_MBPS" --edge-groups "$ALLOWED_GROUPS" \
  --pipeline off --micro 1 --log out/device_budget_trial.jsonl
```

`EDGES`는 기존 리그가 제공하는 `1=host:base,...`, `CAPS_MBPS`는 같은 번호 순 용량, `ALLOWED_GROUPS`는 예를 들어 `3,4:0-3;1,2:4-7`이다. 실제로 도달 가능한 종점만 등록한다. 통신·학습 서버와 기기 코드를 함께 갱신해야 새 타이밍 메타데이터가 적용된다.

```bash
python -m unittest tests.test_device_budget
python -m unittest tests.test_aggregate_width_sync  # PyTorch 필요
python scripts/analysis/device_budget_report.py out/device_budget_trial.jsonl
```

## 7. KOREN과 넷챌린지에서 설명할 기여

KOREN의 역할은 **서로 다른 거점의 실제 접속 지연·처리량과 엣지 혼잡을 SFL 배치 왕복으로 관측하고, 그것을 기기 연산 부하와 분리해 제어 효과를 검증하는 실험 기반**이다. 리그의 tc는 연구망 전체를 바꾸는 SDN 제어가 아니라 소유 자원의 부하 조건을 재현하는 장치다.

기존 HPC↔KOREN VM 측정, 논리 엣지 네 개, VM 두 대에 배치한 클라이언트 실험을 증거로 연결한다. OOM·CPU 제약에 따른 축소는 물리 자원·논리 참여자·회선 축소비·tc/노이즈 설정을 각각 제시한다. SHRiNK의 부하 축소 논리가 학습 수렴이나 GPU 메모리 동등성까지 증명해 주지는 않는다. 자세한 원자료 위치와 넷챌린지 공고 대조는 [기존 성과 보고서](../01_제출발표/기존성과_근거보고서_및_비판검토_2026-09-19.md)를 따른다.

## 8. 논문과의 관계, 남은 연구적 약점

- [FedCS](https://arxiv.org/abs/1804.08333)는 모바일 엣지 환경의 이질적인 연산·통신 자원을 고려한다. “기존 FL은 모두 유선을 가정한다”는 배경 설명을 쓰지 않는다.
- [FjORD](https://arxiv.org/abs/2102.13451)는 Ordered Dropout과 자기 증류를 함께 사용한다. 현재 폭 슬라이싱 구현의 한계를 논문 전체의 실패로 일반화하지 않는다.
- [FedRolex](https://arxiv.org/abs/2212.01548)는 순환 부분모델 추출로 학습 파라미터의 편중을 완화한다. 이 기법은 정확도 대조 후보지만 접속망 제어 권한이나 예산 기준을 대신 정해 주지 않는다.
- [AdaptSFL](https://arxiv.org/abs/2403.13101)처럼 자원 제약과 학습 지연을 함께 다루는 연구가 이미 있다. 여러 제어 변수를 결합했다는 사실만으로 새로운 기여라고 주장할 수 없다.
- [SuperSFL 검토](SuperSFL_AwareNet_결합알고리즘.md)는 후속 후보로 보존한다. 가변 깊이·새 집계·서버 배치까지 동시에 바꾸면 현재 한 문제의 효과를 분리하기 어렵다.

**가장 큰 남은 약점은 새 규칙의 독창성과 학습 효용이 아직 검증되지 않았다는 점이다.** 예산 기반 최대 폭 선택 자체는 간단한 규칙이다. 주장할 차별점은 실제 접속망의 제한 아래에서 지연 원인 혼동을 얼마나 줄이고, 그 결과 같은 학습 품질까지의 비용을 개선하는지에 있다. 새 정책이 정확도나 목표 도달 시간을 개선하지 못하면 “SFL 최적화”로 포장하지 않고 기기 부담과 모델 용량 사이의 제어 결과로 범위를 낮춘다.

## 9. 이번 검증 범위

표준 라이브러리 기반 정책·인자·상태 전달 **19개 검사 통과**, 기존 `test_plan2.py` 검사 전부 통과. 변경 Python 7개 파일의 구문과 현재 안내 문서의 로컬 링크를 검사했다. 실제 텐서 집계 검사 1개는 PyTorch 부재로 건너뛰었다.

이 검사는 규칙의 작동을 확인하며 정확도·KOREN 성능·OpenFlow 집행의 증거가 아니다. **후속 작업에서 PyTorch를 설치해 실제 텐서 집계 검사도 통과했다.** KOREN 원격 재실험은 수행하지 않았다.
