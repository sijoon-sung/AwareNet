# KOREN 실험 설계 — 장애를 넣지 않고 부하를 키운다 (2026-09-06 초안)

> 문제: KOREN 은 너무 빠르다. HPC↔VM 한 줄기 500 Mbps, 8줄기 2 Gbps, 왕복 4.2ms 가 3일 내내 고정.
> 우리 한 라운드 전송량(기기당 16.8 MB)은 0.3초면 끝나 아무 병목도 안 생긴다.
> 가짜 장애(tc 로 지연·손실 주입)를 넣으면 "그건 KOREN 이 아니라 tc 실험"이라는 말을 듣는다.
> 해법: **회선은 그대로 두고 트래픽을 진짜로 키워서 실제 회선이 병목이 되게 한다.** 병목은 만든 게 아니라 생긴 것이 된다.

## 1. 원리 — SHRiNK 를 거꾸로

SHRiNK(Pan·Prabhakar·Psounis·Wischik, INFOCOM 2003 / ToN 2005)의 주장: 트래픽과 회선을 같은 비율로 줄여도
대기 시간·손실 확률은 보존된다 (scaling hypothesis, Psounis et al., CCR 2003). 성능을 정하는 것은 절대 크기가 아니라
**부하 대 용량의 비율(ρ)** 이다. 그러므로 우리는 회선을 줄이는 대신 부하를 키워 같은 ρ 에 도달한다.

실험 조건은 ρ 로 등록한다:  ρ = (기기 수 × 기기당 라운드 전송량 / 라운드 목표 시간) ÷ 실측 회선 상한.
- ρ 0.5 : 여유 — 손잡이가 할 일이 없어야 정상 (무개입 자격시험)
- ρ 0.8 : 혼잡 시작 — 엣지 선택이 듣기 시작
- ρ 1.2 : 과부하 — 엣지 선택 + 분할 전송 + 폭이 모두 필요
근거 수치는 우리 실측(§2)이므로 조건의 출처가 "KOREN 실측"이 된다.

읽기: (1) VM↔HPC 는 2 Gbps 급이라 부하를 **20배** 키워야 ρ≈1 이 된다. (2) 짧은 전송은 회선의 30~60% 만 쓴다 —
비용 모형에 "전송량이 작을수록 실효 처리량이 낮다"는 항이 있어야 한다(8월 실측 55 vs 24 Mbps 와 같은 현상).
(3) 기기↔엣지 구간(집·캠퍼스·무선)은 우리가 건드리지 않고 실제 회선을 그대로 쓴다 — 이질성은 여기서 온다.

## 3. 부하를 키우는 손잡이 세 개 (전부 실험 설계상 정당)

|---|---|---|---|---|
| 배치 크기 | 32 | 256 | 16.8 MB → 134 MB (활성값 ∝ 배치) | 절단면 텐서 크기는 배치에 비례 |

계산 예: 배치 256 · 절단 1 · 기기 8대 → 8 × 240 MB = 1.9 GB/라운드. 라운드 목표 10초면 1.5 Gbps → ρ ≈ 0.77.
기기 16대(HPC 클라이언트 8 + VM2 클라이언트 8)면 ρ ≈ 1.5. **가짜 회선 없이** 세 수준을 다 만들 수 있다.

## 4. 정해야 할 것 (사용자 결정)

1. ρ 세 수준의 값 — 0.5 / 0.8 / 1.2 제안. 근거는 §2 상한.
2. 부하를 무엇으로 키울지 — 배치 크기(가장 단순, 학습 의미 바뀜) / 절단점(모델 구조 바뀜) / 즉시 내보내기(구현 필요, 가장 현실적) / 기기 수(자원 필요). **제안: 즉시 내보내기 + 기기 수**, 배치·절단점은 고정(학습 조건 보존).
3. 라운드 목표 시간 — ρ 계산의 분모. 제안 10초(2판 실측 라운드 12~17초 근처).
4. 엣지 배치 — VM1·VM2 가 같은 지점이라 "두 사이트"가 아님. 다른 PoP VM 신청 여부.

## 5. 필요한 구현 (③ 순서상 나중)

- 즉시 내보내기: 클라이언트가 배치 계산 후 곧바로 활성값을 보내는 모드(`fed_client --stream`). 지금은 배치 끝에 보낸다(확인 필요).
- 부하 비율 자가 검사: 실험 전 실제 회선 상한을 다시 재고(iperf 또는 thr_ 도구) ρ 를 계산해 원장 값과 ±15% 안인지 확인. 리그 자가 검사와 같은 자리.
- 조건 원장에 `rho`, `load_knob`, `round_target_s` 항목 추가.

## 6. KOREN 활용성 서술 (초안)

우리가 KOREN 에서만 할 수 있는 것: 지점이 다른 엣지를 실제로 놓고(판교·대전) 그 사이 경로가 투명하다 · 오버레이를
마음대로 구성해 엣지 선택과 분할 전송을 실제 회선 위에서 돌린다 · 회선이 빠르고 안정적이라(4.2 ms 고정) 관측된
차이를 우리 시스템 효과로 돌릴 수 있다. 상용 클라우드는 셋 다 안 된다.
KOREN 을 쓰는 다른 기관에 줄 수 있는 것: 링크 프로브·Grafana 대시보드·짧은 전송 실효 처리량 실측(망 진단 도구와 데이터) ·
집계 지점 선택 규칙(라이브러리) · "빠른 연구망에서 병목을 만들지 않고 검증하는 절차"(이 문서). 구체적 사례 12건과 도움 예 3개: `docs/03_리서치/KOREN_활용사례_타기관.md` (숭실대 FL 오케스트레이터, FourLeaves 의료 FL, NIA AI CLOUD 서울-대전).

## 7. "기기가 늘면 병목이 생긴다"를 보이는 순서 (2026-09-06 밤, 사용자 지시)

1. **실망(VM↔HPC) 실측이 먼저다.** 기기 수 N 을 늘려 가며(HPC 클라이언트 + VM2 클라이언트) VM↔HPC 구간의 라운드 전송 시간·실효 처리량을 잰다. 어느 N 부터 라운드 시간이 N 에 비례해 늘기 시작하는지(= 회선이 병목이 되는 점)를 실측으로 찾는다. 이 점이 "부하 비율 ρ≈1" 의 실측 정의다.
2. **그 실측을 축소해 시뮬레이션 리그에 넣는다.** SHRiNK 원리(§1): 회선과 트래픽을 같은 비율로 줄이면 대기·손실이 보존된다. 실측한 (N, 회선 상한, 기기당 전송량)을 리그가 감당하는 크기(4~8대, 60~120 Mbps)로 같은 ρ 가 되게 줄인다. 8대 조건 h8n 이 이미 이 원리를 쓴다 — 접속 합/경로 비 2.67 을 4대와 같게 유지.
3. **리그에서 규칙을 검증한 뒤 실망으로 되돌아간다.** 리그에서 성립한 결정(경로 이동·폭)이 같은 ρ 의 실망에서도 같은 방향인지 확인 — 수치 일치가 아니라 방향 일치(K1 판정 기준과 동일).

필요한 것: VM SSH 키 등록(사용자) → VM2 에 클라이언트 배치 → N 스윕 드라이버(`scripts/exp/nsweep_real.sh`, 작성 예정) → `conditions.json` 에 `real_n*` 조건(출처 = 실측).
