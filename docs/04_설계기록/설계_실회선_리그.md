# 설계 — 실회선 리그 (HPC ↔ KOREN VM), 2026-09-07

사용자 결정: "1층(실망 소수)·2층(반실망 축소)부터. 2층도 VM↔HPC 로, tc 를 걸어서."

## 1. 제약과 사실
| 사실 | 결과 |
|---|---|
| HPC(10.246.246.33, 공인 출구 116.89.174.50)는 사설 IP — VM → HPC 인바운드 **불가** (오늘 12345 로 재확인) | 모든 연결은 HPC 가 연다. 엣지(VM)가 HPC 로 되돌려 보내려면 **HPC 가 미리 열어 둔 역방향 터널**을 탄다 |
| HPC → VM: 22·26022·10000~15000·5201·ICMP 열림, 왕복 3.9~4.2 ms, 1줄기 400~450 Mbps, 8줄기 1.3~2.2 Gbps | 엣지 회선을 150~300 Mbps 로 tc 로 잘라 써도 배경 회선은 여유 |
| VM 2대(8코어, GPU 없음), HPC 16코어+GPU | 서버(뒷단 연산)는 HPC. VM 은 **엣지 = 데이터 경로의 중계·병목 지점** |
| HPC 가 VM 에 SSH 가능(오늘 키 등록), VM sshd GatewayPorts clientspecified | `ssh -N -R 0.0.0.0:P:localhost:P vm` 로 VM 의 포트 P 가 HPC 의 P 로 되돌아온다 |

## 2. 구조 — 제어면은 고정, 데이터면은 엣지를 지난다
```
[HPC]  클라이언트 c_i (에뮬, 8대)                      [VM1]  엣지 1 = 포트 묶음 E1, 엣지 2 = 포트 묶음 E2
        ├─ 제어 연결(메타만, 작음) ─────────────→ HPC 서버 :PORT (직접, 고정)
        └─ 데이터 연결(활성값·기울기 조각) ──KOREN──→ VM_k : P(e,i,x) ──역터널(KOREN)──→ HPC 조각 서버 :PORT+1
                                                           ↑ tc: 엣지 e 의 공유 용량 c_e (VM egress·ingress 양방향)
       HPC egress tc: 클라 i 출구 x 의 접속 상한 a_{i,x}  (목적지 포트로 구분)
```
- **모든 페이로드는 조각 채널로** 보낸다(출구 1개면 연결 1개). 제어 연결은 메타만 나르므로 어느 경로든 무방하다.
- **엣지 변경 = 데이터 연결을 다른 엣지 포트로 다시 연다.** tc 필터 교체가 아니라 실제 재접속이다(전환 비용이 실측된다).
  계획 층은 그대로(출구별 경로 튜플), 집행 층의 `assign` 이 "tc 필터 교체" 대신 "클라에 새 엣지 주소 통보 → 클라가 ChunkLinks 를 다시 연다".
- 포트 규약(VM 쪽, 10000~15000 안): P(e, i, x) = 12100 + e·500 + i·2 + x  (12005~12007 은 VM 의 iperf3 가 점유)  (e 엣지 0..3, i 클라 0..99, x 출구 0/1).
  엣지 0·1 은 VM1, 엣지 2·3 은 VM2. 역터널은 엣지마다 하나(SSH 연결 4개) — 터널 하나가 한 TCP 흐름이라 ≈400 Mbps 상한, 엣지 용량 150~300 이면 충분.
- tc 배치:
  - HPC egress(ens160): 클라 i 출구 x 의 접속 상한 a_{i,x} — u32 match dst port P(·,i,x) 들 → 클래스 1:(100+2i+x). (올리기 방향 상한)
  - VM ingress(ifb0): 엣지 e 용량 — 목적지 포트 P(e,·,·) 들 → 클래스 (올리기). VM egress: 같은 포트를 **발신 포트**로 (내리기).
    내려받기 바이트는 터널이 아니라 "전달된 클라 연결"(VM:P → HPC)로 나가므로 발신 포트로 갈린다. 터널 연결 자체(26022)는 안 건드린다.
    (처음엔 터널의 HPC 쪽 포트로 걸려 했는데 HPC 가 NAT 뒤라 VM 이 보는 포트가 다르고, 무엇보다 내려받기 바이트는 그 연결로 안 나간다 — 자가 검사 E 가 잡음)
  - 내리기 방향의 접속 상한: **VM egress 에서 건다** (2026-09-09). 엣지 클래스 아래 (기기, 출구)별 자식 클래스, 발신 포트 P(e,i,x) 로 구분, ceil = 접속 상한.
    (9/7 에는 "못 건다"고 적었는데 HPC ingress 만 본 판단이었다 — 거기선 전부 sshd 트래픽이라 기기를 못 가르지만, VM egress 는 전달된 클라 연결이라 가를 수 있다.
    이전 실험(2차 스윕·3번 결합)의 내리기는 엣지 용량만 걸린 상태였고, 접속 병목 기기가 모형보다 빠르게 나온 이유가 이것. 자가 검사 E 가 이제 판정한다.)
- 지연: 실제 KOREN 왕복 4 ms × 2 (엣지 경유) ≈ 8 ms. 리그의 30 ms 보다 짧다 — 필요하면 HPC egress netem 으로 접속 지연 10 ms 를 더한다.

## 3. 부하 비율 ρ 스윕
ρ = Σ_i (a_{i,A}+a_{i,B}) / Σ_e c_e. 8대 × (50+20) = 560 Mbps 수요. 엣지 4개 용량을 280 / 140 / 70 Mbps 씩 두면 ρ = 0.5 / 1 / 2.
- ρ < 1: 접속이 병목 → 분할 전송이 이긴다 (예측 +23%).  ρ > 1: 엣지가 병목 → 엣지 변경이 이긴다.
- 실규모 100대·엣지 4개 = 같은 ρ 에서 엣지 용량 × 12.5 (1.9 Gbps 급). 3층(fluidsim)은 여기서 잰 효율로 보정.

## 4. 단계
1. 터널 처리량 실측 (HPC → VM:P → 역터널 → HPC) — 1줄기·4줄기, 왕복.  ← 오늘
2. 집행 층: 조각 채널 전면 사용(출구 1개 포함) + 엣지 주소 통보·재접속. 리그 스크립트 `sfl/net/real_rig.sh` (터널 4개 기동, HPC/VM tc, 포트 규약). 자가 검사(A 접속 상한, B 엣지 공유, C 왕복, D 두 출구).
3. 2층 실험: 8대 × 엣지 4 × ρ {0.5, 1, 2}, 팔 path3 / mp (/ +micro).
4. 1층: 이 PC(집, 유선+무선) 또는 연구실 PC 를 진짜 클라이언트로 — 두 출구가 물리적으로 다른 회선.

## 6. VM 클라 판 (VMCLI) — 기기가 KOREN VM 에 산다 (2026-09-12)
사용자: "VM ↔ HPC 로 실험을 해도 크게 달라지지는 않겠지만 하는 게 좋을 것 같아". 지금까지는 기기(클라) 8~32대가 HPC 안에서 돌고 데이터면만 터널로 VM 을 지나 HPC 로 돌아왔다. VM 클라 판은 **기기 프로세스 자체를 VM 두 대에 4대씩 올리고** 서버만 HPC 에 둔다(진짜 원격 기기 + 진짜 회선).
- **배치**: VM1 c0~c3 → 엣지 3·4(VM2 의 터널), VM2 c4~c7 → 엣지 1·2. 같은 VM 의 엣지는 루프백이라 tc 가 안 걸리므로 금지 — 서버 `--edge-groups "3,4:0-3;1,2:4-7"` → 계획기 후보 경로도 허용 안에서만(`prof["allowed"]`).
- **제어 연결**: 클라 → VM:BASE−100(12000) → 역터널 → HPC 서버 포트. (엣지 짝수 번 터널 세션에 `-R` 하나 추가.)
- **접속 상한**: 내리기는 기존대로 VM egress 자식 클래스. 올리기는 HPC egress 가 아니라 **클라가 있는 VM 의 egress** 에 목적지 포트 P(e,i,x) 로 건다(다른 VM 의 엣지 포트로 나가는 트래픽).
- **조건 v8mix**: r8mix_rho1 과 같은 8대(낙오자 2, 접속 병목 2), λ=10, 24R, 시드 1. 장면 정상·몰림(R8 엣지 1 을 125→31M, R20 복구).
