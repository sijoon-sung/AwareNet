1. network namespace + veth — "100개의 독립 노드"를 만드는 방법

무엇: 네트워크 네임스페이스(netns)는 리눅스 커널이 제공하는 격리 기능이다. netns 하나가 자기만의 인터페이스·라우팅 테이블·qdisc(큐 규칙)를 가진다. Docker 컨테이너 하나 = netns 하나.

왜: 노드별로 서로 다른 대역폭 제한을 걸어야 하는데, netns가 분리되어 있으면 각 노드의 인터페이스에 독립적으로 tc를 걸 수 있다. VM 100대를 만드는 것보다 압도적으로 가볍다(노드당 CPU 0.5 제한으로 한 호스트에서 100개).

어떻게: 배포 스크립트가 컨테이너를 network_mode: none(네트워크 없이)으로 띄운 뒤, veth pair(가상 랜케이블 — 양 끝이 있는 파이프)를 만들어 한쪽 끝은 컨테이너 netns 안에(eth1), 반대쪽 끝은 호스트의 OVS 브리지에 꽂는다. (attach_containers_to_ovs.sh)

2. Open vSwitch + VXLAN — 제어와 데이터를 분리한 오버레이

무엇: OVS는 소프트웨어 스위치다. VXLAN은 "L2 이더넷 프레임을 UDP에 싸서 IP 망 위로 보내는" 터널 기술로, VNI라는 번호로 터널을 구분한다.

왜 이걸: 원래 계획은 KOREN의 L2 전용선(L2VPN)과 T-SDN API였는데, NOC 확인 결과 지원 불가였다. 그래서 판교 VM과 대전 VM 사이에 우리가 직접 터널을 뚫었다. 터널을 두 개 만든 이유:

  • VNI 100 (제어): 배분 명령이 다니는 길. 일부러 아무 QoS도 걸지 않는다.
  • VNI 200 (데이터): 어댑터 업로드가 다니는 길. 셰이핑 대상.
분리가 필요한 이유는 실측했다 (8/10): 13개 노드가 동시에 업로드하는 동안 같은 경로의 제어 지연이 P95 기준 5.2배(86→448ms) 악화됐고, 버스트가 끝나자 즉시 회복됐다. 한 길로 다니면 라운드가 시작될 때마다 배분 명령이 이 지연을 겪는다.

3. tc-tbf — 노드별 대역폭 몫을 실제로 거는 손잡이

무엇: tc(traffic control)는 리눅스 커널의 패킷 스케줄링 도구이고, tbf(Token Bucket Filter)는 그중 "초당 rate만큼 토큰이 차고, 패킷은 토큰이 있어야 나가는" 방식의 대역폭 제한기다.

tc qdisc replace dev eth1 root tbf rate 540kbit burst 32kbit latency 400ms
# rate    = 이 노드의 몫 (배분 파일 값, 예: 0.54Mbps 노드)
# burst   = 순간적으로 한번에 내보낼 수 있는 양 (버킷 크기)
# latency = 큐에서 최대 대기 시간 — 넘치면 드롭

어디에 거나: 컨테이너 netns 안의 egress(나가는 방향). 업로드를 제한하고 싶으면 보내는 쪽 출구에서 조여야 한다. replace를 쓰기 때문에 같은 명령을 반복 실행해도 안전하다(멱등).

왜 HTB가 아니라 tbf인가 — 시행착오 기록. 처음엔 OVS의 VXLAN 터널 포트에 HTB 큐를 걸려고 했다. 그런데 터널 포트는 전용 네트워크 장치(netdev)가 없어서(커널 데이터패스에서는 vxlan_sys_4789 하나를 공유) 큐 설정이 조용히 무시될 수 있다(silent no-op — 에러도 안 나고 효과도 없음). 그래서 폐기하고, 각 컨테이너 netns 내부의 tbf로 통일했다. 초기 배분(배포 스크립트)과 라운드 중 동적 재배분(tc 에이전트)이 같은 손잡이를 잡는다는 점도 이 방식의 장점.
정밀도 검증 완료: 몫 0.54~50Mbps 스윕에서 달성률 0.89~0.96으로 전 구간 선형(수신측 goodput 기준, TCP/IP 헤더 오버헤드 감안 시 정상). 대전 KOREN VM 커널(6.8)에서도 tbf 동작 확인.

4. netem — WAN을 책상 위로 가져오는 도구

무엇: netem(network emulator)은 tc의 qdisc 중 하나로, 지연·지터·손실을 인공적으로 주입한다.

왜: 로컬 리허설에서 "KOREN 시간 스케일"을 재현하기 위해. KOREN 실측 RTT 22ms를 그대로 주입해 검증했다(재현 오차 1.3%).

tc qdisc replace dev eth0 root handle 8001: tbf rate 5000kbit burst 32kbit latency 400ms
tc qdisc add     dev eth0 parent 8001: handle 8002: netem delay 22ms
# tbf를 루트로, netem을 그 자식으로 — 대역폭 제한과 WAN 지연을 동시에
여기서 배운 실측 함정 두 개(중요): ① 지연을 주입하면 TCP 송신 버퍼가 자동으로 커져서, 송신측 기준 완료 시간이 실제 도착보다 ~3초 이르게 찍힌다 → iperf3 -w 128K로 버퍼를 고정해 해결. ② TCP는 시작 직후 천천히 가속(slow start)하므로 짧은 전송(8.68MB)은 회선의 절반도 못 쓴다(벌크 55Mbps vs 실효 24Mbps) → 마감값은 계산이 아니라 실측으로 정해야 한다는 운영 수칙의 기술적 이유.

5. nsenter + tc 에이전트 — 라운드 중 배분을 갱신하는 경로

무엇: nsenter는 호스트의 root 프로세스가 다른 프로세스(컨테이너)의 네임스페이스에 "들어가서" 명령을 실행하게 해준다.

# 판교 호스트에서 — client-042의 netns에 들어가 tc를 갱신
PID=$(docker inspect -f '{{.State.Pid}}' client-042)
nsenter -t $PID -n tc qdisc replace dev eth1 root tbf rate 25000kbit burst 32kbit latency 400ms

흐름: 대전 컨트롤러가 배분 맵 {client-001: 3.2Mbps, ..., client-100: 0.5Mbps}을 HTTP 한 번으로 판교의 tc 에이전트(:9100, root 데몬)에 보내면, 에이전트가 노드별로 nsenter+tc를 실행한다. 100노드 왕복 20ms.

왜 병렬화하지 않았나: 노드별 원격 호출을 병렬로 쏘다가 일부만 실패하면, 순간적으로 "배분 합계 > 총량"인 비원자 상태가 생길 수 있다. 그래서 일부러 단일 배치 트랜잭션(한 번에 전달, 순차 적용)을 택했다 — 속도보다 총량 보존의 원자성.

6. 응용 계층 — Flower(gRPC)와 REST 컨트롤러

  • Flower: 오픈소스 FL 프레임워크. 서버↔클라이언트 통신은 gRPC(:8081). 우리는 전략(Strategy) 레벨에서 선택·마감 집계·비교군 스위치를 구현했다 — 프레임워크 자체는 표준 부품.
  • SDN 컨트롤러(:8080, REST): 서버가 보낸 원시 효용을 받아 softmax + 유용성 캡으로 몫을 계산하고, 총량 보존을 로그로 남긴 뒤 tc 에이전트에 전달.
  • 순서 보장: 배분 REST 호출이 동기적으로 완료된 뒤에야 Flower가 학습 지시를 보낸다 — "제어가 데이터보다 늦는" 상황이 코드 순서상 불가능.
