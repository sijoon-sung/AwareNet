# Jetson Orin Nano 실행 안내서 — AwareNet

> 이 문서는 "무엇을 살지 → 무엇을 올릴지 → 무엇을 재서 → 어디에 쓸지"를
> 명령어 수준으로 적은 실행 지침이다.
>
> **원칙: Docker 100노드는 "많음"을 증명하고, Jetson 1대는 "진짜임"을 증명한다.**
> 컨테이너 노드의 연산 시간은 지금 **주입한 보정값**이다. 그 값의 출처를 만드는 것이
> Jetson의 첫 번째 임무다.

## 1. 장비 — 정확히 무엇인가

### 1-1. 본체

| 항목 | 내용 |
|---|---|
| 정식 명칭 | **NVIDIA Jetson Orin Nano 8GB Developer Kit** |
| GPU | Ampere 아키텍처 · CUDA 코어 1,024개 · Tensor 코어 32개 (**NVDLA 없음** — Orin NX/AGX와의 차이) |
| CPU | 6-core Arm Cortex-A78AE (64-bit) |
| 메모리 | **8GB LPDDR5 (128-bit)** — CPU와 GPU가 **공유하는 통합 메모리** |
| 컴퓨트 능력 | sm_87 |
| 전력 모드 | 7W / 15W / **25W(Super)** |
| 저장장치 | 온보드 eMMC **없음** — microSD 슬롯 + **M.2 Key M (NVMe) 슬롯** |


### 1-2. 반드시 함께 준비할 것

| 품목 | 사양 | 왜 필요한가 |
|---|---|---|
| **NVMe SSD** | M.2 2280 · 250GB 이상 | microSD로 돌리면 모델 로딩·스왑이 병목이 되어 **연산 시간 측정값이 오염된다.** 앵커를 만드는 게 목적이므로 필수 |
| 전원 어댑터 | DC 배럴잭 **19V / 최소 45W** | 25W 모드를 쓰려면 USB-C 전원으로는 부족할 수 있다 |
| 능동 냉각 | 개발자 키트 기본 팬 (또는 추가 방열) | 발열로 스로틀링이 걸리면 **뒤로 갈수록 느려져** 측정 재현성이 깨진다 |
| 유선 랜 | 기가비트 이더넷 (온보드) | 무선은 지터가 커서 실회선 측정 축이 오염된다. **반드시 유선** |

## 2. 무엇을 올릴 것인가 — 모델과 설정

우리 프로젝트의 표준 구성을 **그대로** 올린다. Jetson용으로 따로 만들지 않는다 —
같은 코드가 다른 아키텍처에서 도는 것 자체가 증명이기 때문이다.

### 2-1. LLM 워크로드 (주력)

| 항목 | 값 | 근거 |
|---|---|---|
| 베이스 모델 | **Qwen2.5-0.5B** | 프로젝트 canonical. 8GB급 엣지에서 학습 가능권 |
| 미세조정 | **LoRA r=32, target = q_proj / v_proj** | canonical 구성 |
| 전송 페이로드 | **8.68MB** (어댑터만) | 비전 워크로드(9.36MB)와 같은 대역 → 같은 실험 설계 적용 가능 |
| 시퀀스 길이 | 512 (기본) / 여의치 않으면 256 | 메모리 경계에서 첫 번째로 줄일 손잡이 |
| 배치 크기 | 4부터 시작해 위로 탐색 | |

```bash
export AWARENET_WORKLOAD=lora
export AWARENET_BASE_MODEL=Qwen/Qwen2.5-0.5B
export AWARENET_LORA_R=32
export AWARENET_SEQ_LEN=512
```

### 2-2. 비전 워크로드 (대조)

| 항목 | 값 |
|---|---|
| 모델 | mobilenet_v2 (43 클래스 — GTSRB 규격) |
| 전송 페이로드 | 9.36MB |

```bash
export AWARENET_WORKLOAD=vision
export AWARENET_MODEL=mobilenet_v2
export AWARENET_NUM_CLASSES=43
```

### 2-3. 8GB가 안 될 때의 폴백 순서

로컬 RTX 4060에서 잰 GPU 최대 메모리가 **6.86GB**였다. Jetson은 **통합 메모리**라
OS·드라이버가 쓰는 몫을 빼면 실질 가용이 더 적다. 안 들어갈 가능성이 실재한다.
**안 되면 그것도 결과다** — 순서대로 내려가며 어디서 성립하는지를 기록한다.

```
1) seq_len 512 → 256          (가장 싸게 메모리를 줄이는 손잡이)
2) batch 4 → 2 → 1
3) gradient checkpointing 켜기 (속도를 내주고 메모리를 산다)
4) QLoRA 4bit (bitsandbytes)   ← 여기까지 오면 "4bit 폴백 필요"가 실측 결론
5) Qwen2.5-0.5B → 더 작은 모델  (최후 수단, 페이로드 대역이 달라져 비교가 깨짐)
```

각 단계에서 **성공/실패와 그때의 피크 메모리**를 표로 남긴다. 이 표 자체가 산출물이다.

## 3. 무엇을 잴 것인가 — 측정 항목과 판정 기준

### 측정 A. 연산 시간 앵커 (최우선)

**목적**: 컨테이너 100노드에 주입하는 `TARGET_CMP_SEC`의 출처를 실물로 만든다.

```bash
cd ~/KORAN_SDN-AWARE_NET-
python3 scripts/analysis/measure_lora_train_speed.py --device cuda --repeat 30
```

| 기록 항목 | 판정 |
|---|---|
| 스텝 시간 **중앙값 ± 표준편차** | 이 값이 컨테이너 보정의 기준 |
| **앞 10회 vs 뒤 10회 차이** | 10% 이상 느려지면 **스로틀링** — 냉각 보강 후 재측정 |
| 전력 모드 | 15W / 25W 각각 측정해 둘 다 보고 |

> 참고: 로컬 RTX 4060에서 스텝당 **411.6 ± 4.2ms**였다. Jetson은 이보다 느릴 것으로
> 예상되며, **얼마나 느린지가 곧 이기종성의 크기**다. 느린 게 나쁜 결과가 아니다.

### 측정 B. 8GB 경계 판정

```bash
# 학습을 돌리면서 별도 창에서
sudo tegrastats --interval 500 | tee ~/jetson_mem.log
# RAM x/8192MB 항목의 최댓값을 기록
```

| 결과 | 의미 |
|---|---|
| 들어감 | "8GB 엣지에서 0.5B LoRA 학습 가능" — 그대로 보고 |
| 안 들어감 | 2-3절 폴백 순서로 내려가며 **성립 경계를 표로** 보고 |

### 측정 C. 실회선 왕복 (KOREN 연결 후)

이제 **ICMP가 열렸으므로** ping을 그대로 쓸 수 있다.

```bash
ping -c 100 116.89.187.190 | tail -2      # 대전 서버 VM 기준
python3 scripts/measurement/measure_link_profile.py
```

VM↔VM 구간(RTT 약 0.4~3ms)과 달리 Jetson은 **실제 액세스 회선**을 타므로
그 격차 자체가 "액세스 구간이 변동의 주원인"이라는 주장(보고서 10장)의 추가 증거가 된다.

### 측정 D. 이기종 혼합 라운드

Jetson 1대 + 컨테이너 N대가 **같은 라운드에 참여해 집계까지 성공**하는 로그.

```bash
# Jetson에서
AWARENET_CID=jetson-001 \
AWARENET_SUBPROC=0 \
FLOWER_SERVER=116.89.187.190:8081 \
python3 -m edge.fl_client --cid jetson-001
```

> `AWARENET_SUBPROC=0`으로 두는 이유: 서브프로세스 분리는 100노드를 한 VM에 욱여넣기
> 위한 장치다. Jetson은 1대뿐이므로 상주형이 맞고, 그래야 GPU 컨텍스트 재생성 비용도 없다.

**성공 기준**: 서버 로그에 `jetson-001`이 선발·도착·집계에 나타나고,
글로벌 어댑터에 반영되는 것.

## 4. 셋업 절차 (순서대로)

### 4-1. NVMe 먼저

```bash
lsblk                                        # nvme0n1 인식 확인
sudo mkfs.ext4 /dev/nvme0n1
sudo mkdir -p /mnt/nvme && sudo mount /dev/nvme0n1 /mnt/nvme
echo '/dev/nvme0n1 /mnt/nvme ext4 defaults 0 2' | sudo tee -a /etc/fstab

# 모델 캐시와 Docker 데이터를 NVMe로
export HF_HOME=/mnt/nvme/hf
echo 'export HF_HOME=/mnt/nvme/hf' >> ~/.bashrc
```

### 4-2. 측정 조건 고정

```bash
sudo nvpmodel -q                 # 현재 모드 확인
sudo nvpmodel -m 0               # MAXN(최대) — JetPack 6.2면 25W Super
sudo jetson_clocks               # 클럭 고정 → 측정 재현성 확보
sudo jetson_clocks --show | head # 고정 확인
```

> **이 두 명령을 안 하면 측정값이 매번 달라진다.** 재현 가능한 앵커가 목적이므로 필수다.
> 그리고 **어느 모드로 쟀는지 결과에 반드시 함께 적는다.**

### 4-3. PyTorch — 반드시 NVIDIA 배포 휠

```bash
python3 -c "import torch; print(torch.__version__, torch.cuda.is_available())"
# → True 가 나와야 한다. False면 잘못된 휠이다.
```

일반 PyPI의 `pip install torch`는 Jetson에서 **CUDA가 안 붙는 경우가 많다.**
JetPack 버전에 맞는 NVIDIA 배포 휠(`https://developer.download.nvidia.com/compute/redist/jp/`)
또는 NVIDIA가 제공하는 `nvcr.io/nvidia/l4t-pytorch` 컨테이너를 쓴다.
**`torch.cuda.is_available()`가 True인지 확인하기 전에는 어떤 측정도 시작하지 않는다** —
CPU로 돌아가면 앵커 값이 통째로 무의미해진다.

### 4-4. KOREN 접근 등록

Jetson이 나가는 **공인 IP를 KOREN 허용 목록에 추가 등록**해야 한다.
현재 등록된 IP는 두 개(`168.188.50.217`, `168.188.47.175`)이며, Jetson을 다른 망에
두면 그 IP도 등록이 필요하다.

```bash
# 등록 후 도달 확인 (ICMP가 열렸으므로 ping도 가능)
ping -c 3 116.89.187.190
python3 -c "import socket;s=socket.create_connection(('116.89.187.190',8081),timeout=5);print('서버 도달 OK');s.close()"
```

## 6. 발표에서 쓰는 법

**하지 말 것**: "젯슨 오린 나노를 도입했습니다" — 장비 나열은 설득력이 없다.

**할 것**: 역할로 말한다.

> "컨테이너 100대의 연산 시간은 저희가 임의로 정한 값이 아닙니다.
> **실제 엣지 보드에서 재서** 그 분포를 확장한 겁니다.
> 그 보드가 지금 저 자리에서 같은 라운드에 참여하고 있고요."

**Q&A 추가 문항**

> **Q. 컨테이너로 흉내 낸 것 아닌가?**
> → 통신은 실물 전송으로, **연산은 실제 엣지 보드 실측값**으로 고정했습니다.
> ARM 기반 보드와 x86 컨테이너가 **같은 코드로 같은 라운드에 참여해 집계까지** 성공하는 것도
> 확인했습니다. 규모는 컨테이너가, 사실성은 실물 보드가 담당하는 구조입니다.

> **Q. 8GB 보드에서 LLM 학습이 되나?**
> → (되면) 됩니다. seq_len ○○, batch ○○에서 피크 ○○GB로 확인했습니다.
> → (안 되면) 그대로는 안 됩니다. 그래서 **어디까지 줄이면 되는지 경계를 쟀고**,
>    4bit 양자화가 필요하다는 것이 저희 실측 결론입니다.

## 7. 향후 비전

### 7-1. 단기 (본 과제 잔여 기간)

연산 앵커 확보 → 8GB 경계 판정 → 이기종 혼합 라운드 성공 → 시연 자산.
**모사 신뢰도의 뿌리를 실물로 바꾸는 것**이 전부다.

### 7-2. 중기 ① — 연산 축으로의 확장

현재 AwareNet은 **회선 축만** 제어한다. 연산이 느린 노드는 "배분해도 소용없으니 최소 몫"으로
자동 제외할 뿐이다. Jetson으로 연산 실측 기반이 생기면 다음 질문이 열린다.

> **회선과 연산을 같이 보면 더 잘할 수 있는가?**

연산이 느린 노드에는 **로컬 스텝 수를 줄여** 마감 안에 들어오게 하고 그만큼 회선 몫은 덜 주고,
연산이 빠른 노드에는 스텝을 늘리는 **연산–통신 공동 배분**이다.
지금 구조(고정 총량 + 마감 + 가치순 재배분)의 자연스러운 확장이며,
**연산 시간의 실측 분포 없이는 시작할 수 없다.**

### 7-3. 중기 ② — 전력 축

엣지의 실제 제약은 대역폭만이 아니라 **전력**이다. Jetson은 전력 모드를 바꿀 수 있고
소비 전력을 실시간으로 잴 수 있는 몇 안 되는 플랫폼이다.

> "가치 있는 데이터를 가진 노드에 **대역폭**을 더 준다"를
> "가치 있는 노드에 **전력 예산**을 더 준다"로 확장할 수 있는가?

배터리 구동 현장 기기(드론·이동 로봇·야외 센서)에서는 이쪽이 오히려 본질적이고,
**같은 논리 구조가 그대로 적용된다.** `nvpmodel`로 모드를 바꿔가며 재면 바로 실험이 된다.

### 7-4. 장기 — 실제 현장

| 적용처 | Jetson의 위치 |
|---|---|
| 제조 다사업장 | 라인마다 놓인 검사 장비가 곧 학습 노드. **Orin Nano급이 현장 표준** |
| 의료 다기관 | 반출 금지 데이터를 원내 보드에서 학습 |
| 이동체(로봇·드론) | 회선이 불안정하고 전력이 유한한 최악 조건 — **본 기법의 이득이 가장 큰 영역** |

세 곳의 공통점은 **"데이터를 못 내보내고, 회선이 좁고, 마감이 있다"**는 것이다.
지금 KOREN 위에서 만드는 것이 그대로 얹히는 구조이며, Jetson은 그 현장 기기의
축소 모형이 아니라 **실제로 쓰이는 바로 그 등급의 장비**다.
