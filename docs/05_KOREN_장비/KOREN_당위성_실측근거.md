# 왜 이 프로젝트는 KOREN 망에서 해야 하는가 — 실측 근거 정리

작성일: 2026-08-10 · 근거 문서: `AwareNet_v3_검토자료`(4.2절·2.6절) · `AwareNet_FedLLM_보고서_v1`(1.4절·3장)
실측 도구: `scripts/measurement/measure_link_profile.py` (PC↔VM / VM↔VM 공용, 본 문서와 함께 신규 작성)

---

## 1. 한 문장 요약

AwareNet의 핵심 주장은 **"관리형 망에서 게이트웨이 QoS 총량을 데이터 가치순으로 재배분하면 희귀 데이터 노드를 마감 안에 도착시킬 수 있다"** 인데, 이 주장을 검증하려면 ① 게이트웨이 QoS 제어권, ② 실제 광역(WAN) 경로, ③ 다지점(판교↔대전) 배치가 동시에 필요하며 — 이 세 가지가 동시에 주어지는 인프라는 KOREN뿐이다.

## 2. 논거 4가지 (대안 인프라와의 비교)

| # | 필요 조건 | 로컬 PC/랩 서버 | 상용 클라우드(AWS 등) | 일반 인터넷 | **KOREN** |
|---|---|---|---|---|---|
| 1 | **게이트웨이 QoS 제어권** (OVS·VXLAN·tc로 노드별 몫을 중앙에서 재배분) | 가능하나 WAN 아님 | ❌ 공유 인프라의 QoS는 제3자 제어 불가 | ❌ ISP 구간 제어 불가 | ✅ VM 게이트웨이 전권 |
| 2 | **실 WAN 경로** (140km+ 실제 백본, tc/netem으로 재현 불가한 실제 지터·경합) | ❌ 루프백/LAN | △ 리전 간 가능하나 경로 불투명·제어 불가 | △ 경로 통제 불가 | ✅ 판교↔대전 연구망 |
| 3 | **다지점 원격 제어 실증** (대전 컨트롤러가 140km 밖 판교 게이트웨이를 라운드 시간 내 제어) | ❌ | △ | ❌ | ✅ 제어 채널 12.5ms 실측 |
| 4 | **검증 수준의 차별점** (근접 선행연구 HAFLQ·Fed-FSTQ 등은 전부 시뮬레이션) | 시뮬레이션 수준 | 에뮬레이션 수준 | — | ✅ 실 SDN·실 WAN — 본 연구 기여 3의 성립 조건 |

핵심: 본 연구의 적용 대상 자체가 "기업·기관이 게이트웨이를 통제하는 **관리형 네트워크**"(v3 검토자료 2.6절)다. KOREN은 그 관리형 망의 실물이므로, KOREN 실증은 편의가 아니라 **연구 대상 환경과 검증 환경의 일치**다. 또한 FedLLM 프레이밍에서는 이것이 한계 조항이 아니라 배포 현실이다 — 연합 파인튜닝을 하는 이유가 데이터 반출 금지이고, 그 데이터가 있는 곳이 기업이 게이트웨이를 통제하는 온프레미스 망이기 때문이다(FedLLM 보고서 1.4절).

## 4. 신규 측정 절차 (`measure_link_profile.py`)

### 4.1 내 PC → 대전 VM

```bash
python scripts/measurement/measure_link_profile.py --label pc_to_daejeon --host 116.89.187.190 --tcp-port 8080
```

처리량까지 재려면 대전 VM에서 `iperf3 -s`를 먼저 띄우고 `--iperf --iperf-time 30 --iperf-reverse`를 추가한다.

> ⚠️ **허용 IP 주의**: KOREN VM은 등록된 공인 IP(168.188.50.217 / 168.188.47.175 — 학교망)만 접근 가능하다. 2026-08-10 자택망(공인 IP 121.183.253.129)에서 실행 시 **100% 무응답으로 차단 확인** — 학교망에서 실행하거나 KOREN 운영진에 현재 IP 추가 등록 후 측정할 것. (등록 가능 IP 수 제한 없음, `VM_INFO.md`)

### 4.2 판교 VM → 대전 VM (VM↔VM 백본)

```bash
# 대전 VM: iperf3 -s
# 판교 VM:
python3 scripts/measurement/measure_link_profile.py --label pangyo_to_daejeon --host <대전IP> --tcp-port 8080 --iperf --iperf-time 30 --iperf-reverse
```

24시간 안정성은 기존 `scripts/measurement/measure_backbone_24h.sh`(정합성 검사 내장)로 수행한다 — 이 스크립트가 측정 계획 #2의 본 도구이고, `measure_link_profile.py`는 스냅샷·회차 비교용(요약 CSV 자동 누적)이다.

### 4.3 결과물

- `out/link_profile/<label>_<시각>.json` — 원자료(회신별 RTT 포함)
- `out/link_profile/link_profile_summary.csv` — 회차별 요약 1행씩 누적 → 아래 표를 이 CSV로 채운다

**2026-08-10 실측 해석** (원자료: `out/link_profile/full_benchmark_*.json`, 차트 `fig_wan_benchmark.png`):
- **짧은 전송은 회선을 다 쓰지 못한다 (τ 규칙의 실측 근거 추가)** — 벌크 전송 goodput은 55Mbps인데 8.68MB 단발 업로드의 실효 goodput은 **24.2Mbps**(P50 2.88s vs 이상치 1.26s). TCP slow start가 짧은 전송을 지배하기 때문이며, 로컬 리허설에서 확인한 "램프업 ~1초"와 정합. → **마감 τ와 유용성 캡 margin은 반드시 실측 전송 시간 기준으로 산정**해야 한다는 운영 수칙이 실WAN에서도 재확인됨.
- **백본 대 액세스의 대비가 곧 논거다** — VM 쪽 백본 지터 ±0.17ms vs 자택 액세스 지터 ±15.5ms (약 90배). 관측되는 변동은 액세스망 소관이고, KOREN 백본은 "관측 차이 = 시스템 효과"로 귀속시킬 수 있을 만큼 안정적이다(측정 계획 #2의 사전 신호).
- 상행 53.8Mbps 기준 canonical 어댑터(8.68MB) 업로드 실효 **약 1.3초** — 마감(수십 초) 대비 여유. 단 이 값은 단일 회선 기준이며, 본실험의 쟁점은 **총량 100Mbps를 100노드가 나눌 때**의 배분이다.
- VM 커널 6.8에서 **tc-tbf·netem 지원 확인 완료**(더미 인터페이스 검증) — 본실험 셰이핑 스택이 이 VM에서 그대로 동작한다.
- 접근성: SSH(26022)만 개방, ICMP·서비스 포트는 IP 등록 후에도 차단 — 본실험 전 8081(Flower)·8080(컨트롤러) 개방 요청 필요 (임시 우회: `koren_tunnel.ps1` SSH 터널).

**라운드 경계 버스트 실측** (2026-08-10, `burst_test.py` → `burst_test_*.json`, 차트 `fig_burst_test.png`) — 13노드가 동시에 canonical 어댑터(8.68MB)를 업로드하는 라운드 경계 상황을 실WAN에서 재현:

| 지표 | 평시 | 버스트 중 (13플로우 동시) | 회복(버스트 종료 직후) |
|---|---|---|---|
| 제어 채널 RTT P50 | 30.8ms | **74.2ms (2.4배)** | 29.9ms (즉시 회복) |
| 제어 채널 RTT P95 | 86ms | **448ms (5.2배, 최대 568ms)** | 78ms |

- **제어/데이터 분리(Dual-VXLAN) 설계 동기의 첫 실측 증거** — 데이터 폭주가 같은 경로의 제어 트래픽을 P95 기준 5배 지연시킨다. 격리가 없으면 배분 명령이 라운드 경계마다 이 지연을 겪는다. (판교 게이트웨이 본판 측정은 계획 #5)
- **TCP 경합의 무작위 불공평** — 같은 크기·같은 시각에 출발한 13개 플로우의 완료가 **4.8~12.7초(2.6배)**로 갈렸다(단독 업로드 P50 2.88초 대비 동시 P50 11.1초). 경합 하에서 마감 탈락자가 회선 품질이 아니라 **TCP 동역학의 운**으로 결정된다는 뜻 — 명시적 배분 제어가 이 무작위성을 정책으로 대체해야 한다는 논거.
- 합산 goodput 63.1Mbps — 병렬화로 단일 스트림(55Mbps) 대비 +15%: 회선 총량 추정치 상향.

이 표가 채워지면 2장의 논거 2·3이 "주장"에서 "실측"으로 승격되고, KOREN 당위성 진술은 다음 한 문단으로 완성된다:

> "본 프로젝트는 판교↔대전 140km 실 백본에서 RTT __ms·손실 __%·처리량 __Mbps를 실측했고, 이 실제 광역 경로 위에서 게이트웨이 QoS 총량(100Mbps)을 SDN으로 재배분하는 전 과정을 검증했다. 이 검증은 QoS 제어권이 없는 공중망·상용 클라우드에서는 수행 자체가 불가능하며, 시뮬레이션 기반 선행연구와 본 연구를 구분 짓는 결정적 차별점이다."
