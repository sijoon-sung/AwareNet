# KOREN 후속 연계: 학습 스케줄러와 네트워크 서비스의 역할

## 현재 활용

KOREN은 연구망 연결 기반이다. 현재 결과는 HPC–중계 VM–학습 서버 사이의 실제 텐서 전송과 호스트 수준의 부하 제어에서 얻었다. 코어 네트워크 제어 또는 T-SDN/L2VPN 적용 결과로 표시하지 않는다. 사전 전송 규모 측정에는 별도 대역폭 제한을 적용하지 않았다.

## 단계별 확장과 성공 기준

| 단계 | 구현할 연결 | 확인할 증거 | 비교 조건 |
|---|---|---|---|
| 관리 호스트 SDN | AwareNet의 배정을 OS-Ken/OVS 출력 포트 정책으로 변환 | 정책 수신 → OpenFlow 적용 응답 → 해당 흐름 카운터 → 수신 바이트를 같은 실행 ID로 연결 | 같은 폭·연결 수·총용량에서 앱 중계와 OVS 집행 비교 |
| L2VPN | 운영기관 승인 아래 참여 기관과 중계를 논리망으로 연결 | 기관 간 연결, 격리, MTU·도달성, 실제 전송 경로 | 같은 학습·부하에서 완료 시간 분포와 운영상 연결 제약 비교 |
| T-SDN | 승인된 회선 자원과 설정 정보를 스케줄러의 허용 경로·용량 입력에 연결 | 운영기관의 자원 설정 확인과 실제 관측값 대조 | 기본 연결과 제공받은 자원 조건에서 p50/p95 라운드 시간·변동·모델 폭 비교 |
| 결합 제어 | 망 설정 변경과 모델 축소를 서로 다른 시간 규모로 적용 | 요청·적용·관측의 시각, 설정 전환 비용과 실패 복구 로그 | 네트워크만/학습만/결합, 동일 목표 정확도 도달 시간 비교 |

L2VPN의 논리적 격리만으로 대역폭 보장을 가정하지 않는다. T-SDN의 할당 용량·변경 가능 주기·API 또는 운영 절차는 실제 제공 조건을 확인한 뒤 설정한다. 다른 팀의 서비스 이용 범위나 이번 프로젝트의 미사용 사유를 일반적인 서비스 제약으로 단정하지 않는다.

## 먼저 해결할 연결 고리

현재 [SDN 모듈](../../sfl/sdn/README.md)의 정책 생성·허용 범위 검사는 실제 학습 런타임과 OVS 적용 확인까지 자동으로 연결된 상태가 아니다. 첫 목표는 학습 라운드의 결정 ID와 실제 흐름 카운터를 연결하는 것이다. 흐름이 SSH 터널 등으로 OVS를 우회하면 해당 실행은 SDN 경로 실증에서 제외한다.
