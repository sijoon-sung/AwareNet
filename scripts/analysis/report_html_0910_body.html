AwareNet · KOREN 넷챌린지 시즌 13

망을 고치면 모델을 덜 줄여도 된다

분할 연합학습에서 느린 기기를 제시간에 맞추는 두 가지 방법(모델 줄이기, 망 고치기)을 하나씩 재고, 함께 썼을 때와 32대 규모에서 문제가 생기는 순간을 KOREN 실회선에서 확인한 결과입니다.

2026-09-11 17:40 기준 (3시드·정확도 축 반영) · HPC 8~32대 ↔ KOREN VM 엣지 4개 · 실험 1~4 완료, 실증 플랫폼 검증 통과 · 이전 판(9/8)에 §5~§7 을 더함

결론. 라운드를 10초 안에 끝내라는 목표를 주면, 모델만 줄이는 방식은 8대 중 대부분을 절반 크기로 만들어야 하고 정확도가 8점 떨어집니다. 엣지 바꾸기와 두 회선 나눠 보내기를 먼저 쓰면 계산이 느린 1~2대만 줄이면 되고, 정확도는 그대로입니다. 32대에서는 트래픽이 몰리면 스케줄러 없는 판은 라운드가 2.2배로 뛰어 교란이 끝날 때까지 그대로이고, 스케줄러는 두 라운드 안에 기기를 옮겨 물리적 최선(1.2배) 근처로 되돌립니다. 계산이 느린 4대가 있으면 그 4대의 모델만 한 칸 줄이고, 가격 λ 하나로 시간과 정확도의 눈금을 조절합니다.

1. 무엇을 만들었나

기기(클라이언트)가 모델 앞부분을 계산해 엣지 서버로 보내고, 서버가 나머지를 계산해 돌려보내는 분할 연합학습입니다. 한 라운드가 오래 걸리는 이유는 기기마다 다릅니다. 계산이 느리거나, 자기 회선이 약하거나, 같은 엣지에 여러 대가 몰려 막히거나입니다. 스케줄러는 인지(재기) → 계획(정하기) → 실행(옮기기) 세 층으로, 라운드마다 원인을 보고 맞는 손잡이를 고릅니다.

  • 모델 폭 줄이기 — 계산이 느린 기기에만. 정확도를 깎는 유일한 손잡이라 마지막에 씁니다.
  • 엣지 바꾸기 — 몰려서 막힌 기기를 한가한 엣지로. SDN 경로 변경에 해당합니다.
  • 두 회선으로 나눠 보내기 — 회선이 약한 기기가 유선·무선 두 가닥을 동시에 씁니다.
  • 즉시 내보내기 — 배치를 4조각으로 잘라 계산되는 대로 보내 계산과 전송을 겹칩니다.

계획은 규칙 모음이 아니라 하나의 목적을 풉니다: min max_k T_k(w, s) + λ · 평균(1 − w_k). 라운드(가장 느린 기기의 시간)에 폭을 잃은 값을 초로 환산해 더한 것을 가장 작게 만드는 폭 w 와 경로 s 를 고릅니다. 망을 못 바꾸는 기기는 폭만 남고, 계산이 문제가 아니면 폭을 깎아도 라운드가 안 줄어 안 깎이고, 둘 다면 망을 먼저 씁니다.

실험 장비는 HPC 안의 기기들이 KOREN을 거쳐 VM 두 대(엣지 4개로 나눔)로 보내고 다시 HPC 서버로 돌아오는 실회선 구성입니다. 회선 속도와 엣지 용량은 리눅스 tc로 걸었고(기기별 내려받기 상한 포함), 자가 검사로 확인했습니다.

2. 실험 1 — 모델 폭: 효과와 대가

망은 넉넉하고 기기 속도만 다른 4대에서, 느린 기기의 폭만 줄이면 라운드가 26% 짧아집니다. 나머지 기기의 폭은 그대로였습니다. 대가는 정확도입니다.

즉시 내보내기의 정확도 하락(m=4 에서 −18점)은 두 가지였습니다. 서버 뒷단 모델이 여러 기기 공유인데 조각 기울기를 다른 기기가 지우던 코드 버그(고침), 그리고 조각 8장의 배치 정규화 통계 흔들림(Ghost BN·GroupNorm 문헌). GroupNorm 은 그 자체로 60라운드에 −15점이라 대책이 못 됩니다. 정확도는 문헌 참조로 종결했습니다.

3. 실험 2 — 망 손잡이: 엣지 바꾸기와 나눠 보내기

5. 회선부터 — KOREN 회선은 병목이 아니다

학습 없이 전송 패턴만으로 기기 수를 8→96대로 늘려 HPC → KOREN VM → HPC 서버 회선을 tc 없이 쟀습니다. 합계가 0.9~1.3 Gbps 에서 더 늘지 않고 16대부터 회선 몫이 나뉩니다. TCP 왕복·버스트·고른 흐름 세 방식이 10% 안에서 같았고, UDP 는 KOREN 방화벽에 막혀 도착하지 않았습니다.

6. 실험 4 — 32대: 문제가 생기는 순간과 스케줄러의 대응

HPC 기기 32대(엣지당 8) → KOREN 엣지 4개(56 Mbps 씩, 수요와 같음) → 서버. 24라운드. 스케줄러 없음 = 회선 하나·고정 배정·전폭(일반 분할학습). 스케줄러 = 결합 최적화 λ=70(정상 라운드 1배), 이동 3대/라운드. 문제는 tc 로 만듭니다: 엣지 1 에 다른 트래픽이 얹혀 용량이 1/4 로 떨어지는 몰림, 4대의 계산이 0.15배인 연산 느림, 용량이 한 칸씩 내려갔다 올라오는 변동.

정확도 축 (8대 혼합, 200라운드, 2시드). λ=18 → 폭 0.83·8.0 s·정확도 53.6%, λ=70 → 0.98·12.9 s·63.2%, λ=280 → 1.00·15.2 s·65.2%, 스케줄러 없음 1.00·19.1 s·65.5%. λ 가 작을수록 폭·정확도가 내려가고 라운드가 짧아지는 것이 단조이고, λ=18 만 잡음(4~6점) 밖입니다 — λ 는 시간–정확도 눈금 하나로 작동합니다.

읽는 법. 몰림은 망으로 풉니다 — 옮긴 기기는 전부 엣지 1 기기였고 막힌 동안 되돌아가지 않았습니다. 연산 느림은 폭으로 풉니다 — 폭이 줄어든 기기가 정확히 느린 4대였고, λ 를 내리면 더 깎고 더 빨라지며 올리면 안 깎는 쪽으로 갑니다. 망으로 다 못 풀 때(교란 첫 라운드, 엣지 3개에 32대)는 최적화가 전원 폭을 한 칸 잠깐 내렸다 되돌립니다 — 사전등록 예측("폭 안 깎음")은 이 경계에서 빗나갔고 그대로 적습니다.

KOREN 의 몫. 지연 4~8 ms 의 안정된 백본이라 "몰림"을 tc 로만 만들 수 있었고, 엣지를 바꾸는 이동이 다음 라운드부터 효과를 냈습니다. 인지층의 회선 품질 계측이 곧 SDN 제어 입력이 됩니다. 시간축 전체는 32대 시나리오 시간축, 조건·근거·판정은 조건 원장 한 장.

7. 실증 플랫폼

실회선 위 라이브 화면(8대, 결합 최적화 λ=10)을 자동 검증했습니다(9/10 09:05 통과): 3라운드 진행 → 교란 버튼(기기 c4 회선 절반) → HPC 와 VM 의 tc 가 실제로 25 Mbit 로 바뀜 → 2라운드 → 복구 50 Mbit → 종료 뒤 남는 프로세스 없음. 시연용 λ 는 8대에서 기기당 가격이 싸(0.31 s) 전원 0.75 로 깎는 경향이 있어 20~30 으로 올리는 것이 낫습니다(후속 결정).

8. 솔직하게 적어 두는 것

  • 32대 실험은 일곱 번 고쳐 돌렸습니다. 초반 감시와 결정 재생(로그를 인지층에 다시 먹여 그 라운드의 계획을 재현)으로 찾은 결함: 계획기가 엣지 용량을 정적값으로만 알던 것, 그 수정의 되먹임 두 형태(자기 분할이 만든 느림을 포화로 읽음, "포화 아님"을 회복으로 읽음), 걸친 기기의 시간이 다른 엣지에 귀속되던 것, 경로 단계가 "총합"이라 라운드를 정하는 기기를 희생하던 것. 각각 단위시험을 붙였고(70여 건), 정상·연산 느림·λ 장면은 이동이 없어 결정이 안 바뀜을 재생으로 확인했습니다.
  • 조건 오류 두 건은 실험 과정으로 적습니다: 기준선이 두 가닥을 가중치 없이 쓴 것(회선 하나로 정정), 이동 상한이 사전등록 표(3대)와 달리 1 이었던 것(3으로 정정).
  • 사전등록 예측이 빗나간 곳: 몰림 첫 두 라운드의 전원 폭 0.75, 몰림의 "1.2배" 기준(물리 최선을 계산하지 않고 잡음).
  • 정확도는 시드 잡음이 4~6점이라 5점 넘는 차이만 말하고, 폭 대가의 근거는 문헌으로 보강합니다.
  • 이전 판의 "내려받기 상한은 tc 로 못 건다"는 오기였습니다 — VM 쪽 자식 클래스로 걸 수 있었고 32대 실험은 걸고 돌렸습니다.
