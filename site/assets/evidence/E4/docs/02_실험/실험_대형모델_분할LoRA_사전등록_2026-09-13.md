# 실험 — 분할 + LoRA 로 큰 모델(LLM·디퓨전)을 작은 기기에서 (사전등록, 2026-09-13)

사용자 요청: "분할 학습을 함으로써 디퓨전 모델이나 LLM 을 LoRA 로 굴릴 수도 있다는 걸 한번 해줘. 모델이 클수록 효과도 클 거야."

## 1. 질문
기기(연산·메모리가 작은 단말)가 모델 전체를 들고 LoRA 를 학습(로컬 LoRA)하는 것과, 임베딩 + 앞 k 층만 들고 나머지를 서버에 두는 것(분할 LoRA)을 비교할 때,
**모델이 커질수록 기기 쪽 부담(메모리·시간·내려받기)의 절감 비율이 커지는가.** 그리고 실제 회선(VM 기기 ↔ HPC 서버)에서 그 학습이 진짜로 돌아가는가.

## 2. 문헌
- SplitLoRA (Lin et al. 2024, arXiv 2407.00952): LLM 을 자른 뒤 클라는 앞부분 + LoRA, 서버가 뒷부분. 분할이 "클라 연산·메모리 부담"을 서버로 넘기고 활성값만 오간다는 틀. https://arxiv.org/abs/2407.00952
- HSplitLoRA (2025, arXiv 2505.02795): 기기마다 다른 자원에 맞춰 rank·절단점을 달리 — 우리 폭(rank) 노브와 같은 계열. https://arxiv.org/abs/2505.02795
- Offsite-Tuning (Xiao, Lin, Han 2023, arXiv 2302.04870): 데이터 쪽은 모델 전체가 필요 없다(에뮬레이터 + 어댑터) — "기기가 모델 전체를 받을 필요가 없다"는 우리 부분 적재의 근거. https://github.com/mit-han-lab/offsite-tuning
- 메모리 효율 분할 연합 LLM 미세조정(2025, arXiv 2506.02940): 이질 모바일 기기에 아래층 일부 + LoRA — 기기 메모리가 병목이라는 문제 설정. https://pith.science/paper/2506.02940
- 분할 학습 LLM 미세조정 서베이(2026, arXiv 2604.24468). https://arxiv.org/pdf/2604.24468

## 3. 식 (기기 쪽)
모델: 깊이 L, 은닉 d, 층당 파라미터 P_layer, 임베딩 P_emb, (LLM) head P_head. 배치 B, 길이 S. 가중치는 동결 fp32(기기 CPU 표준), LoRA 만 학습.
- 로컬 LoRA 기기 메모리 ≈ 4·(P_emb + L·P_layer + P_head) + 활성값(L 층) + LoRA·옵티마이저(작음)
- 분할 LoRA 기기 메모리 ≈ 4·(P_emb + k·P_layer) + 활성값(k 층) + LoRA(k 층)
- 비율 ≈ (P_emb + k·P_layer) / (P_emb + L·P_layer + P_head) → L 이 커질수록 k/L 로 수렴 (임베딩 몫이 있어 0 은 아님)
- 스텝 시간도 같은 꼴(층당 연산 ∝ P_layer·B·S). 절단면 통신 = 2·B·S·d·4 B/스텝 — **깊이 L 과 무관**, 은닉 d 에만 비례.
- 어댑터 동기(라운드당) = LoRA 바이트: 분할은 로컬의 k/L.

## 4. 장치와 사다리
- 기기 = KOREN VM (8코어 CPU, 31 GB, torch CPU). 서버 = HPC (V100 16 GB; 7B 서버 몫은 GPU 에 안 들어가 CPU 158 GB).
- LLM 사다리: Qwen2.5 0.5B / 1.5B / 3B / 7B (층 24/28/36/28, 은닉 896/1536/2048/3584). k = 2. LoRA rank 16, attn+MLP 전체(G-L1 확정 레시피). B=4, S=256.
- 디퓨전 사다리: DiT/2 256px (잠재 32×32×4, 토큰 256) S / B / L / XL (층 12/12/24/28, 은닉 384/768/1024/1152; XL 만 사전학습 가중치 facebook/DiT-XL-2-256). k = 2. B=4.
- 비용은 가중치 값과 무관하므로 **랜덤 초기화(from_config)** 로 잰다(내려받기 없음). 설정마다 별도 프로세스, 최대 RSS(ru_maxrss)·스텝 시간(3스텝 중 뒤 2 중앙값).
- 실제 분할 학습: 기기(VM1) ↔ 서버(HPC) 를 역터널로 잇고, 도메인 B 코퍼스(data/lora)로 30스텝. 기기는 **앞 k 층이 든 조각만** 내려받는다(load_front_pretrained). LLM 0.5B·3B(GPU 서버), 7B(CPU 서버, 10스텝), DiT-XL(실측 잠재 벡터 또는 난수).
- 스크립트: sfl/experiments/run_scale_lora.py (cost / server / device). 기록 out/scale_lora/.

## 5. 판정 (사전 등록)
1. **메모리 비율 단조 감소**: 기기 최대 RSS 비 (분할 front / 로컬) 가 0.5B → 7B 로 갈수록 단조 감소. 7B 로컬 LoRA 는 31 GB 기기에서 **불가(OOM)** 이고 분할은 **가능** 이면 "모델이 클수록 효과가 크다" 의 극단 사례.
2. **스텝 시간 비율 단조 감소**: 같은 방향.
3. **절단면 바이트는 깊이 무관**: 같은 d 에서 층 수와 무관(식대로), 어댑터 동기 바이트는 로컬의 k/L (±1%).
4. **실제 학습 성립**: 기기↔서버 30스텝에서 손실 처음 1/5 평균 > 마지막 1/5 평균 (LLM 0.5B·3B·7B, DiT-XL). 안 내려가면 배선 결함으로 보고 고친다.
5. 디퓨전도 1·2 가 성립.

## 6. 한계 (미리 적어 둠)
- 분할 LoRA 의 통신량은 rank 로 안 줄고(절단면 = B·S·d), 은닉 d 가 큰 모델일수록 절단면이 커진다 — 7B 는 스텝당 왕복 29 MB(B4·S256). 회선이 느리면 통신이 병목 (우리 3층 스케줄러가 다루는 바로 그 문제).
- LLM 의 다음 토큰 라벨은 입력 자체라 라벨이 서버로 간다 — 프라이버시가 목적이면 U 자형(끝층도 기기) 이 필요. 이번 실험은 **자원(메모리·연산·내려받기)** 만 본다.
- 정확도(과제 성능)는 재지 않는다(2026-09-08 사용자 결정: 문헌 참조) — 손실 하강으로 "학습이 일어남" 만 확인.
