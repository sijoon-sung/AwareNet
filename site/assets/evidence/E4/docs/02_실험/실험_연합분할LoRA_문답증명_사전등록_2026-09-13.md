# 실험 — 분할 + LoRA 연합이 non-IID 데이터를 실제로 학습하는가: 문답으로 증명 (사전등록, 2026-09-13 14:05)

> 작성 시점: 연합 학습 6/16 라운드 진행 중, **평가 실행 전**. 아래 판정 기준은 결과를 보기 전에 고정한다.

사용자 요청: "실제로 LoRA 모델을 결합해서, 실제로 연합학습으로 non-IID 데이터를 학습하고 있다는 걸 증명해줘. 실제로 답변을 주고받음으로써."

## 1. 설계
- **기기 3대, 겹치지 않는 사실**: c0 = B1(사실 6개, 학습 22문형), c1 = B2(사실 5, 22문형), c2 = B3(사실 5, 18문형). 기기 간 공통 사실 **0개**(스크립트 확인). 데이터 파일은 각 기기(VM)에만 쓰인다 — 서버·다른 기기로 원문 파일이 가지 않는다.
  - 배치: VM1 에 c0·c1, VM2 에 c2. 서버 = HPC V100. VM ↔ HPC 역터널.
  - c0 학습셋에만 카나리아(가짜 비밀 `ZX-4471-QM97`) 3문항을 섞는다 — 누출 계측용.
- **모델**: Qwen2.5-0.5B, 절단 2층(기기 = 임베딩 + 층 0~1 + LoRA, 서버 = 층 2~23 + 출력층 + LoRA). LoRA rank 16, attn+MLP 전체.
- **학습**: 16라운드 × 기기당 30스텝, 배치 8, lr 1e-3 (G-L2 비분할 연합 통과 설정과 같음). 라운드마다 서버가 기기 앞단 어댑터를 평균(FedAvg)해 돌려준다. 서버 뒷단 어댑터는 공유이며 기기가 차례로 갱신한다(SplitFed 계열 표준).
- **비교 3종** (같은 기본 모델, 같은 질문):
  - 베이스 — 어댑터 없음(B=0)
  - 단독(B1) — c0 한 대가 같은 예산(16×30)으로 자기 데이터만 학습
  - 연합(B1+B2+B3) — 위 3대 분할 연합
- **질문**: 각 도메인 heldout(학습에 안 나온 문형). B1 8 · B2 3 · B3 7문항. 그리디 생성 32토큰.

## 2. 판정 (사전 등록)
채점은 두 가지를 모두 적는다: (K) 정답 표지 포함 여부(자동), (S) 답변 원문을 사람이 읽어 **그 사실을 맞게 말했는지** 엄격 판정(다른 도메인의 답이 표지를 우연히 포함한 경우는 오답). **판정은 S 기준.**

1. **베이스는 모른다**: 세 도메인 모두 ≤ 15%.
2. **단독은 자기 것만 안다**: 단독(B1) 의 B1 ≥ 50%, B2·B3 는 각각 ≤ 15%.
3. **연합은 남의 것도 안다(핵심)**: 연합의 B2·B3 가 각각 ≥ 50% 이고, 단독(B1) 의 같은 열보다 각각 +35%p 이상.
4. **자기 것을 크게 잃지 않는다**: 연합의 B1 ≥ 단독(B1) 의 B1 − 25%p.
5. **카나리아는 계측만**: 판정 없음. 8/27 비분할 연합 실측(단독 100% · 연합 100%)과 비교해 보고한다. 보안 대책은 `docs/03_리서치/보안_데이터재현_대책_2026-09-13.md` (조사만, 적용 안 함).

1~4 가 모두 성립하면 "분할 + LoRA 연합이 non-IID 데이터를 실제로 학습했다"로 보고한다. 하나라도 불성립이면 그대로 보고하고 원인(희석, 공유 뒷단 순차 갱신의 망각 등)을 분석한다.

## 3. 알려진 한계 (미리 적음)
- B2 heldout 이 3문항뿐이라 한 문항 = 33%p. 판정 3 의 B2 는 거칠다.
- heldout 은 "안 본 사실"이 아니라 "본 사실의 안 본 문형"이다(코퍼스 규약). 즉 암기한 사실을 다른 말로 물어도 답하는지를 본다.
- 서버 뒷단 어댑터는 모든 기기 데이터로 갱신되므로, "지식이 합쳐지는 곳"은 평균된 앞단과 공유 뒷단 둘 다다. 앞단 평균만의 기여를 떼어 보려면 뒷단을 기기별로 두는 대조가 필요하다(후속).
- **라벨(답 토큰)이 평문으로 서버에 간다**(보안 문서 경로 ①). 이 실험은 "학습이 되는가"를 보이는 것이고 프라이버시 보장을 주장하지 않는다.

## 4. 정정 1 — 1차 실행 발산 (2026-09-13 14:08, 평가 전)
- **증상**: 연합 3대 1차(13:58~) 가 R1~R11 동안 기기 손실 0.0001~0.0003 으로 수렴한 뒤, R12 c0 차례 안에서 폭발(차례 평균 2.48, 마지막 스텝 15.04). c1·c2 도 R12 평균 7.16·6.63, R13 에도 4~5 로 회복 못 함. 모델 사용 불가 → **평가하지 않고 폐기**(기록 out/fed_split/try1_diverged/).
- **원인 가설**: 손실이 거의 0 이면 기울기도 거의 0 인데, Adam 은 기울기를 그 크기의 제곱근 평균으로 나눠 걸음을 정하므로 걸음 크기가 학습률만큼 유지된 채 방향만 잡음이 된다 → 누적되다 한 번에 무너진다. 비분할 연합(G-L2, 8/27)은 같은 lr 1e-3 였지만 fp16 자동 혼합 정밀도라 작은 기울기가 0 으로 사라져 드러나지 않았을 가능성이 있다(분할판은 기기 CPU·서버 모두 fp32).
- **수정**: (a) 학습률 1e-3 → 3e-4 (단일 기기 확정 레시피 G-L1 과 같음) (b) LoRA 기울기 노름 클리핑 1.0 을 기기·서버 모두에 (HF Trainer 기본값과 같은 표준) (c) 라운드별 최대 손실 기록 추가.
- **검증 계획 (본 실행 전)**: HPC 안에서 서버·기기 3대를 모두 GPU 에 두고 16×30 을 두 번 — ① 1차 설정(lr 1e-3, 클리핑 없음) 으로 발산이 재현되는지 ② 수정 설정에서 R3 이후 최대 손실이 2.0 을 넘지 않는지. ① 이 재현되지 않으면 원인 가설을 "확인됨"이 아니라 "재현 안 됨"으로 적는다.
- **판정 기준(§2)은 바꾸지 않는다.**

## 5. 정정 2 — 발산 검증 기준 (2026-09-13 14:12, 검증 결과 보기 전)
- v_old 초반(R1~R3)에서 **정상 상태의 차례 시작 손실이 2~8** 임을 확인했다(c0 R3 최대 2.21, c2 R1 7.75). 이유: 서버 뒷단 어댑터가 직전 기기의 데이터로 방금 갱신됐고 평균 앞단이 막 도착했으므로, 각 기기 차례의 첫 몇 스텝은 손실이 높다가 곧 0 근처로 내려간다.
- 따라서 §4 의 "R3 이후 최대 손실 > 2.0 이면 발산" 은 **정상 학습도 발산으로 판정하는 잘못된 기준**이다(스크립트 verify_fed_split.sh 의 요약 줄도 같은 기준 — 실행 중이라 파일은 고치지 않고 결과를 다시 계산한다).
- **바꾼 기준**: R3 이후 어느 기기든 **차례 끝 5스텝 평균 손실 > 1.0** 이면 발산. 근거: 정상 상태의 차례 끝 손실은 0.00~0.04(1차 R1~R11), 1차 발산은 7.78/4.09/5.30.

## 8. 추가 대조 사전등록 — 뒷단 어댑터도 기기별로 두고 평균 (14:42, 실행 전)
- **이유**: 본실행은 앞단 어댑터만 평균하고, 서버 뒷단 어댑터는 한 벌을 기기가 차례로 갱신했다(SplitFed v2 식). "LoRA 결합으로 합쳐졌다"고 말하려면 뒷단이 모든 데이터를 한 곳에서 본 효과를 떼어 내야 한다.
- **설계**: 서버가 기기별 뒷단 어댑터(와 옵티마이저 상태)를 따로 두고, 기기 차례에는 그 기기의 뒷단만 갱신한다. 라운드 끝에 **앞단·뒷단 어댑터를 모두 산술 평균**해 전원에게 같은 값으로 되돌린다(SplitFed v1 식). 나머지 설정은 본실행과 같다(VM ↔ HPC, 16×30, lr 3e-4, 클리핑 1.0, 같은 기기 배치·카나리아).
- **단독 비교는 본실행의 단독(B1)을 그대로 쓴다** — 기기 1대면 두 방식이 같은 계산이다.
- **판정(S 기준, 같은 문턱)**: 6. 기기별 뒷단 평균 연합의 B2·B3 각각 ≥ 50% 이고 단독 대비 +35%p, B1 ≥ 단독 − 25%p. 성립하면 "서버 뒷단이 데이터를 한 곳에서 본 효과 없이, 어댑터 평균만으로 non-IID 지식이 합쳐졌다"로 보고한다. 불성립이면 본실행의 결합이 공유 뒷단에 기대고 있었다고 보고한다.
