# 설계서 — 출구 2개 기기의 분할 전송 (멀티패스 업로드)

| | |
|---|---|
| 작성일 | 2026-09-02 |
| 상태 | 설계 확정 (팀장 승인) — 구현·검증 전 |
| 적용 형태 | 기기에 출구(회선·인터페이스)가 2개인 경우 — 회선 이중화, 유선+무선 병행 |
| 바뀌는 것 | 전송하는 층만. 학습·집계·컨트롤러 결정 로직은 변경 없음 |

## 1. 배경 — 왜 이 형태만 하는가

전송을 두 길로 나누는 것은 언제나 유효한 게 아니다. **병목이 길이 갈라지는
지점보다 앞에 있으면 이득이 0이다.** 기관의 인터넷 회선이 하나뿐이면, 그 뒤에서
길을 나눠도 나가는 속도는 그 회선 속도 그대로다.

검토한 세 형태 중 하나만 채택한다:

| 형태 | 판정 | 이유 |
|---|---|---|
| **기기 출구 2개** (이중화 회선, 유선+무선) | **채택** | 두 출구의 속도가 실제로 합산됨 — 이득이 구조적으로 보장 |
| 서버 접속 지점 2곳에 반씩 | 보류 | 집계는 한곳에서 하므로 나머지 반을 서버 간에 다시 옮겨야 함 — 측정 결과 서버 간 동기화 비용이 커서(뒷단 42MB급) 이득을 상쇄 |
| 참여자 소수의 불균형 보완 | 부수 효과 | 별도 구현 없이 채택 형태에 포함됨 |

성립 조건(명시): 기기에 출구 2개가 실재하고, 운영체제 라우팅이 출발 주소별로
다른 출구를 쓰도록 설정되어 있을 것. 회선 이중화는 기관에서 흔한 구성이다.

## 2. 전체 구조

```
기기                                          서버
 학습 결과 (직렬화된 바이트, 예: 어댑터 35MB)
   → 조각으로 자름  [1][2][3][4][5]...
       ├─ 출구 A 연결 ── [1][3][4] ──→ ┐
       └─ 출구 B 연결 ── [2][5] ────→ ┴→ 위치대로 재조립 → 기존 코드에 전달
```

- 기기: 출구마다 서버로 연결 1개씩 (총 2개). 데이터를 조각으로 잘라 두 연결에 분배
- 서버: 도착 순서와 무관하게 조각을 원래 위치에 끼워 넣고, 완성되면 기존 처리로 전달
- 프로토콜 추가: 조각 메시지 1종 (아래 §5)

## 3. 보내는 쪽 (기기)

### 3-1. 연결 만들기

기기가 자기 주소 두 개(출구 A 주소, 출구 B 주소)로 각각 서버에 TCP 연결을 연다.
어느 출구로 나갈지는 연결을 만들 때 **출발 주소를 지정**하는 것으로 정해진다 —
현행 테스트베드가 이미 쓰는 방법(주소별 경로 분류)이라 코드 변경이 작다.

### 3-2. 자르기

보낼 바이트 덩어리를 고정 크기 조각(기본 1MB)으로 자른다. 각 조각 앞에 헤더를
붙인다:

| 필드 | 내용 |
|---|---|
| 전송 번호 | 이번 업로드의 식별자 (라운드·기기별) |
| 조각 번호 | 몇 번째 조각인지 |
| 위치(오프셋) | 전체에서 시작 바이트 위치 |
| 길이 | 이 조각의 바이트 수 |
| 전체 크기 | 완성본의 총 바이트 (첫 조각에만 필수) |

이 정보만 있으면 받는 쪽이 순서가 섞여 와도, 일부가 다른 연결로 다시 와도 맞출
수 있다.

### 3-3. 분배 규칙 — 설계의 핵심

비율을 계산하지 않는다. 규칙은 하나다:

> **먼저 한가해진 연결이 다음 조각을 가져간다.**

- 출구 A 가 3배 빠르면 A 연결이 3배 자주 한가해져 3배 많은 조각을 가져간다
- 전송 도중 B 가 느려지면 그 순간부터 B 가 가져가는 조각이 저절로 줄어든다
- 비율 상수, 튜닝, 속도 예측이 전부 불필요 — 속도 차이가 규칙 안에서 자동 반영
  (분할 다운로드 도구들이 오래 검증해 온 방식)

구현: 조각 목록을 대기열에 두고, 연결별 송신 스레드가 "이전 조각 송신 완료 →
대기열에서 다음 조각 인출"을 반복한다.

## 4. 받는 쪽 (서버)

1. 첫 조각의 "전체 크기"로 빈 버퍼를 만든다
2. 조각이 올 때마다 헤더의 위치대로 버퍼에 쓴다 (어느 연결로 왔는지 무관)
3. 받은 바이트 합계가 전체 크기와 같아지면 완성 — 완성본을 기존 수신 처리에
   그대로 전달한다. 이후(집계·측정·결정)는 현행과 동일

같은 기기의 두 연결을 같은 전송 번호로 묶는다. 연결과 전송의 대응은 첫 메시지의
기기 식별자로 세운다.

## 5. 프로토콜 변경

추가 메시지 1종: `CHUNK` — §3-2 헤더 + 조각 바이트. 기존 메시지(체크인, 라운드
시작, 업로드 완료 등)는 변경 없음. 조각 크기(기본 1MB)는 헤더에 길이가 있으므로
협상이 필요 없다.

## 6. 켜고 끄는 판단 — 기존 원칙 그대로

**켜는 조건 (모두 만족할 때):**
1. 출구 2개가 실제로 감지됨 (두 주소로 연결 수립 성공)
2. 예상 이득 = (두 출구 속도의 합 ÷ 빠른 쪽 하나의 속도) 가 계측 오차(10%)를 초과
3. 보낼 크기가 수 MB 이상 (작은 전송은 자르는 비용이 이득보다 큼)

**끄는 조건:** 출구 하나가 죽거나(연결 실패) 이득이 계측 오차 아래로 떨어지면
자동으로 연결 1개 전송으로 복귀. 분할 전송의 최저 성능은 단일 전송과 같으므로
**켜서 손해 보는 경우는 구조적으로 없다.**

**안전장치:** 연결이 끊기면 그 연결이 맡았던 미완료 조각만 남은 연결로 재전송한다
(조각에 위치가 있어 처음부터 다시 보낼 필요 없음). 부수 효과로 한 출구가 도중에
죽어도 전송이 완료되는 내결함성이 생긴다.

## 7. 측정

연결별로 "보낸 바이트 ÷ 걸린 시간"을 재서 출구별 속도를 기존 이동평균 관측에
추가한다. 이 값이 §6 의 켜기/끄기 판단과 컨트롤러의 경로·학습량 결정에 함께
쓰인다. 새 계측 장치는 없다 — 조각 송신 완료 시각의 집계뿐이다.

## 8. 검증 실험 (사전 등록)

테스트베드에서 기기에 주소 2개를 주고 주소별로 다른 속도를 걸어 출구 2개를
재현한다 (현행 도구 그대로).

| 조건 | 예상 | 판정 기준 |
|---|---|---|
| 출구 2개 (예: 40Mbps + 20Mbps) | 전송 시간이 합산 속도 수준으로 단축 | 단일 최고 출구 대비 단축 > 계측 오차 10% |
| 출구 1개 | 단일 전송과 동일 | 분할이 자동으로 꺼짐 (개입 0) |
| 전송 중 한 출구 급락 | 조각 배분이 저절로 쏠리고 전송 완료 | 완료 성공 + 배분 이동 관측 |
| 전송 중 한 출구 절단 | 미완료 조각 재전송으로 완료 | 완료 성공 (내결함성) |

불성립이면 불성립으로 기록한다.

**결과 (2026-09-02 실측, 구현 완료)** — 4조건 전부 성립:

| 조건 | 실측 | 판정 |
|---|---|---|
| 출구 1개 (40M) 기준 | 35MB 에 6.99초 (이론 7.0초와 일치) | 기준 확립 |
| 출구 2개 (40+20M) | 5.18초 — 기준 대비 26% 단축, 분배 22.0/13.0MB (용량비와 일치) | 성립 (>10%) |
| 전송 중 급락 (40→5M) | 분배가 10.5/24.5 로 자동 역전, 완료·재조립 일치 | 성립 |
| 전송 중 절단 | 남은 연결로 미완료 조각 재전송, 완료·재조립 일치 | 성립 |

구현: sfl/mpsend.py (송신·재조립) · 검증 도구 sfl/experiments/run_mp_test.py ·
실험 scripts/exp/run_mp.sh. 구현 중 발견·수정 1건: 송신 완료와 수신 완료의 경합
(fin 이 다른 연결의 조각보다 먼저 도착 가능) → fin 처리에 대기 추가.

## 9. 한계 (미리 명시)

- 두 출구 속도 차가 극단적이면(수십 배) 느린 쪽 기여가 미미 — 켜는 조건 2 가
  자동으로 거른다
- 실기관 적용은 운영체제 라우팅 설정 협조가 조건
- 무선 출구는 속도 변동이 크다 — 다만 조각 단위 자동 분배라 속도 예측이 필요
  없다는 것이 이 설계의 이점
- 서버 접속 지점 2곳에 나누는 형태는 서버 간 재전송 비용 문제가 풀리기 전까지 보류

## 11. 전체 구조와의 결합

목적은 하나 — 목표 정확도 도달 시간의 최소화 — 이고, 분할 전송은 수단 사다리의
0번째 칸으로 들어간다. 순서는 규칙이 아니라 목적식을 풀면 나오는 성질이다
(대가가 싼 수단이 먼저 쓰인다).

| 순서 | 수단 | 대가 | 결정 주체 |
|---|---|---|---|
| 0 | 분할 전송 | 없음 — 자기 출구만 사용, 남에게 영향 없음 | **기기 로컬** |
| 1 | 접속 지점 이동 | 전환 비용 (정확도 무손실) — 공유 자원이라 남에게 영향 | 중앙 + 안정화 문 |
| 2 | 학습량(폭) 축소 | 정확도 (최소 25% 보장) | 중앙 |
| 예비 | 양자화 | 정확도 소폭 | 중앙 |

**결정 책임의 분리** — 남에게 영향을 주는 결정(접속 지점·폭)은 중앙이, 자기에게만
영향인 결정(분할)은 기기가 스스로 한다. 분할은 공유 자원을 건드리지 않고 켜서
손해도 없으므로 중앙 허가와 안정화 문이 필요 없다.

**한 라운드의 흐름 (결합판)** — ① 사전 진단에 출구 목록·속도 추가 ② 중앙이
도달 시간 최소화로 폭·접속 지점 결정 — 기기의 전송 능력은 출구 합산 속도로 계산
③ 지시 하달(기존과 동일) ④ 기기가 로컬 판단으로 분할 여부 결정 후 업로드
⑤ 서버 재조립 → 집계 → 출구별 측정 수집.

**새 상호작용** — 분할이 폭을 보호한다: 전송이 빨라진 기기는 폭을 깎을 이유가
줄어든다. "대가 없는 수단이 정확도를 지킨다"는 기존 구조(경로가 폭을 보호)와
같은 원리의 칸이 하나 추가된 것이다. 접속 지점 선택과는 직교 — 지점을 먼저
정하고, 그 지점으로 두 출구를 쓴다 (조합이 꼬이지 않음).

## 12. 다중 엣지와의 결합 — "경로 선택의 연속판" (2026-09-06 밤, 사용자 제안)

사용자 제안: 모델(활성값)을 TCP 처럼 조각내어 여러 엣지로 나눠 보내면 길이 여러 개일 때 부하를 **고르게** 줄 수 있다.
모델이 크면 통째로는 어렵지만 조각이면 된다. 이것은 별개 기능이 아니라 **엣지 선택 손잡이의 연속판**이다.

### 12-1. 이미 있는 것 (§3~§5, `mpsend.py`, 검증 §8 통과)
- 조각 1MB, 출구별 연결 1개, **"먼저 한가해진 연결이 다음 조각을 가져간다"** — 비율 계산 없음, 속도 차이가 저절로 반영.
- 서버 재조립(`Reassembler`), 연결 사망 시 남은 조각 재전송.
- 실측: 기기 1대, 40M 단독 6.99s → 40+20M 분할 5.18s (−26%), 분배 22.0/13.0 MB (용량 비 그대로).
- 아직 없는 것: **계획기와의 연결**(누가 분할할지), **여러 기기가 동시에 분할할 때**의 실측, 실망(VM1·VM2 두 엣지 → HPC)에서의 중계.

### 12-2. 엣지 선택 ⊂ 분할 전송
엣지 선택은 기기 하나의 바이트를 한 경로에 전부 두는 것(배정 = 0 또는 1). 분할 전송은 그 비율을 연속값으로 만든다.
그러므로 분할 전송이 켜진 기기에게 "경로를 고른다"는 결정은 사라지고 **"어느 경로들을 쓸 수 있게 열어 줄 것인가"**만 남는다.
비율은 계획기가 계산하지 않는다 — 먼저-한가한-연결 규칙이 매 조각마다 실측으로 정한다(§3-3). 계획기가 예측으로 비율을 정하는 것보다 정확하고 상수가 없다.

여러 기기가 동시에 두 경로로 조각을 보내면 각 경로는 TCP 흐름 공정성으로 나뉘고, 각 기기는 두 경로에서 자기 몫을 합쳐 쓴다.
결과는 **전체 부하가 경로 용량 비로 저절로 고르게 퍼지는 것**이다 (MPTCP 의 결합 혼잡제어가 노리는 것과 같은 상태).
이진 선택이 못 하는 경우 — 기기 3대·경로 2개(2:1 로밖에 못 나눔), 폭이 달라 기기별 바이트가 다를 때(1.0/0.5/0.75 바이트를 이진으로 균형 잡기 어려움) — 를 분할이 해결한다.
**폭과의 시너지 세 번째 자리**: 폭이 바이트를 불균등하게 만들면 분할이 다시 고르게 편다.

### 12-3. 안 되는 곳 (기존 원칙 §6 유지)
- **접속 회선 병목**: 두 조각이 같은 접속 회선을 지나므로 이득 0. 5판의 c2 유형. → 폭만.
- **전송이 작을 때**: 조각 2개 미만이면 안 나눈다. 짧은 전송은 회선을 다 못 쓴다(KOREN 실측: 1MB 조각 480 Mbps vs 4MB 540 Mbps, 0.06MB 는 157) — 조각을 1MB 아래로 내리지 않는 이유.
- **출구가 하나**: 실망에서 기기가 두 엣지에 붙으려면 두 엣지(VM1·VM2)가 같은 서버(HPC)로 중계해야 한다. 지금 `mpsend` 는 기기가 서버에 **직접** 두 연결을 여는 형태(출발 주소 2개)라, 실망판은 엣지 중계기(조각을 HPC 로 넘기는 릴레이)가 필요하다 — 구현 항목.

### 12-4. 규칙에 넣는 자리 (계획기, 설계기록_컨트롤러 §9 위에)
```
연산 병목        → 폭
공유 구간 혼잡    → 분할 전송 (열린 경로 전부)  ※ 출구가 하나뿐이거나 전송이 작으면 이진 경로 선택으로 후퇴
접속 회선 병목    → 폭 (분할은 무익)
```
계획기 변경은 작다: 경로 단계가 "배정"을 내는 대신 "열린 경로 집합"을 내고(기본 = 전부), 조각 분배는 기기가 한다.
모형에서는 분할 기기의 망 시간 = 바이트 / (열린 경로들의 실효 몫 합). 실효 몫은 관측(최근 최선값)으로.

### 12-5. 검증 실험 (사전 등록 초안 — 8대 두 갈래 뒤)
조건 `h5m`/`h8m`: 이진 선택이 불리한 집단 — 기기 수 홀수(3·5) 또는 폭이 섞여 바이트가 다른 집단, 경로 60/60 대칭, 접속 50.
팔: 균등 · 경로만(이진) · **분할 전송** · 폭+분할.  지표: 총비용, 라운드 시간, **경로별 부하 균형(최대/최소 부하 비)**, 조각 분배 비.
기대: 분할 ≥ 경로만 (두 지표 모두), 이득은 기기 수 홀수·바이트 불균등에서 가장 큼, 접속 병목 기기는 분할해도 변화 없음.
부하 비율(ρ) 실험(설계_KOREN_부하비율)에서 ρ≈1 일 때 부하를 고르게 펴는 도구가 이것이다.

### 12-6. 필요한 구현
1. `fed_client`: 출구 목록(`--bind` 여러 개)과 분할 켜기(`--multipath`), 배치 활성값 업로드를 `send_multipath` 로.
2. `fed_server`: CHUNK 수신을 `Reassembler` 로 (있음) — 라운드 계측(xfer·bytes)이 조각 합으로 잡히는지 확인.
3. 계획기: 경로 단계 출력을 "열린 경로 집합"으로 확장, 모형에 분할 기기 항.
4. 리그: 기기별 출발 주소 2개(경로 1·2 필터를 각각 다른 주소에), 자가 검사에 "두 출구 동시 처리량 = 두 경로 몫 합" 항목.
5. 실망: 엣지 중계기(VM1·VM2 → HPC).

## §13 분할 전송 규칙 (알고리즘, 2026-09-07 확정) — 땜질이 아니라 규칙
사용자 지시: "나중에 바꿀 때는 알고리즘화해야 한다, 일일이 고치면 안 된다." 아래 세 규칙이 `sfl/chunker.py`·`sfl/mpsend.py` 전부다.
각 규칙은 실제로 겪은 실패에서 나왔고, 시험(`tests/test_chunker.py`, `tests/test_mp_act.py`)이 그 실패를 재현해 고정한다.

| 규칙 | 식 | 왜 (겪은 실패) | 시험 |
|---|---|---|---|
| 1. 상시 연결 | 출구마다 연결 1개를 열어 세션 내내 재사용 (`ChunkLinks`). 죽으면 다음 전송 때 재개 | 전송마다 새 연결 → 매번 슬로스타트. 2MB 페이로드는 데워지기 전에 끝나 두 출구 합이 상시 주 링크 하나보다 느렸다 (HPC 스모크 33 vs 46 Mbps) | test_mp_act 4) 전송 5건에 연결 2개 |

| 5. 양방향 | 올리는 활성값도 내려오는 기울기도 같은 연결들로 나눠 보낸다 (`ChunkPeer`, 서버 `send_back`). 소켓마다 쓰기 잠금(조각·회신이 겹치지 않게) | 내려받기가 주 링크 한 가닥이면 왕복 트래픽의 절반이 분할을 못 받아 두 가닥 이득이 사라진다 (스모크: 분할 기기 5.4s = 단일 5.4s) | test_mp_act 5) 내려받기·동시 양방향 |
